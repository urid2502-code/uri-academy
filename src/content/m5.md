## מה זה Database, ולמה לא פשוט לשמור בקובץ?

עד עכשיו שמרנו משימות במערך בזיכרון – וכל פעם שהשרת עלה מחדש, הכל נמחק. **Database** (מסד נתונים) הוא תוכנה שכל התפקיד שלה הוא **לשמור מידע לאורך זמן, ולתת לחפש ולשנות אותו מהר ובבטחה**.

"אבל אפשר לשמור קובץ JSON!" – נכון, עד שיש:
- **שני משתמשים שכותבים באותו רגע** – אחד דורס את השני.
- **מיליון הזמנות** – כדי למצוא אחת צריך לקרוא את כל הקובץ.
- **קריסה באמצע כתיבה** – הקובץ נשאר חצי כתוב ושבור.
- **שאלה כמו "כמה הכנסות היו החודש לפי קטגוריה?"** – צריך לכתוב קוד מיוחד לכל שאלה.

מסד נתונים פותר את כל אלה. בקורס נשתמש ב-**PostgreSQL** ("פוסטגרס") – מסד נתונים חינמי, אמין ופופולרי מאוד.

### אנלוגיה: גיליון אקסל משוכלל

- **Table** (טבלה) = **גיליון** באקסל: `users`, `orders`, `products`.
- **Column** (עמודה) = **כותרת עמודה** עם סוג קבוע: `email` (טקסט), `price` (מספר).
- **Row** (שורה) = **רשומה אחת**: משתמש אחד, הזמנה אחת.

ההבדל מאקסל: מסד הנתונים **אוכף כללים** (אי אפשר לשים טקסט בעמודת מספר), מחזיק **מיליארדי שורות**, ומאפשר לאלפי משתמשים לעבוד יחד בלי לדרוס זה את זה.

### SQL – השפה לדבר עם המסד

**SQL** (Structured Query Language) היא השפה שבה שואלים את המסד שאלות. היא כמעט אנגלית: `SELECT name FROM users WHERE city = 'Haifa'` = "תביא את השמות מטבלת המשתמשים, איפה שהעיר היא חיפה".

> [!tip] SQL היא אחת המיומנויות הכי "עמידות" בתעשייה: נכתבה בשנות ה-70 ועדיין בשימוש בכל חברה. כל מראיין ל-Full Stack ישאל עליה.

## צעד אחר צעד: מהטבלה הראשונה ועד דוחות

### 1. Data Types – לכל עמודה סוג

| Type | מה זה | דוגמה |
|---|---|---|
| `integer` / `bigint` | מספר שלם (bigint לגדולים מאוד) | `42` |
| `numeric(10,2)` | מספר מדויק עם ספרות אחרי הנקודה – **לכסף** | `249.90` |
| `text` | טקסט בכל אורך | `'אורי'` |
| `boolean` | כן/לא | `true` |
| `timestamptz` | תאריך ושעה כולל אזור זמן | `'2026-11-16 15:30+02'` |
| `uuid` | מזהה ייחודי אקראי | `'3f2a...'` |
| `jsonb` | מסמך JSON (נלמד בשיעור הבא) | `'{"color":"red"}'` |

> [!warn] לעולם לא לשמור כסף ב-`real`/`float` – הם לא מדויקים (`0.1 + 0.2` ≠ `0.3`). משתמשים ב-`numeric`, או שומרים **אגורות** ב-`bigint`.

### 2. CREATE TABLE – יצירת טבלה

```sql
CREATE TABLE products (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text NOT NULL,
  price      numeric(10,2) NOT NULL CHECK (price >= 0),
  category   text,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

- `GENERATED ALWAYS AS IDENTITY` – המסד ממספר את השורות בעצמו (1, 2, 3...).
- `PRIMARY KEY` – המזהה הייחודי של כל שורה (נעמיק בשיעור הבא).
- `NOT NULL` – חובה למלא. `CHECK` – כלל שהמסד אוכף. `DEFAULT now()` – ערך אוטומטי.

### 3. CRUD – ארבע הפעולות הבסיסיות

**CRUD** = Create, Read, Update, Delete. ב-SQL:

| פעולה | SQL | דוגמה |
|---|---|---|
| **Create** | `INSERT` | `INSERT INTO products (name, price) VALUES ('מקלדת', 249.90);` |
| **Read** | `SELECT` | `SELECT name, price FROM products;` |
| **Update** | `UPDATE` | `UPDATE products SET price = 199 WHERE id = 3;` |
| **Delete** | `DELETE` | `DELETE FROM products WHERE id = 3;` |

### 4. SELECT לעומק – WHERE, ORDER BY, LIMIT

```sql
SELECT name, price
FROM products
WHERE category = 'מחשבים' AND price < 500   -- סינון שורות
ORDER BY price DESC                          -- מיון: מהיקר לזול
LIMIT 10;                                    -- רק 10 ראשונות
```

אופרטורים שימושיים ב-WHERE: `=`, `<>` (שונה), `<`, `>=`, `AND`, `OR`, `IN ('a','b')`, `BETWEEN 10 AND 20`, `LIKE 'מק%'` (מתחיל ב"מק"), `IS NULL`.

> [!note] `NULL` אומר "אין ערך / לא ידוע". הוא לא שווה לכלום – גם לא ל-`NULL` אחר! לכן כותבים `WHERE category IS NULL` ולא `= NULL`.

### 5. הסכנה הגדולה: UPDATE ו-DELETE בלי WHERE

```sql
DELETE FROM orders;            -- ⚠️ מוחק את כל ההזמנות!
UPDATE users SET role = 'admin'; -- ⚠️ כל המשתמשים הפכו למנהלים!
```

אין "האם אתה בטוח?" ואין סל מחזור. שכחת WHERE – כל הטבלה הלכה.

> [!danger] הרגל שמציל קריירות: **קודם כותבים `SELECT` עם אותו WHERE** ובודקים אילו שורות חוזרות. רק אז מחליפים ל-`DELETE`/`UPDATE`. וב-Production – עושים את זה בתוך Transaction (שיעור 3) כדי שאפשר יהיה לבטל.

### 6. Aggregate Functions – סיכומים

פונקציות שמסכמות הרבה שורות לערך אחד:

| פונקציה | מה עושה |
|---|---|
| `COUNT(*)` | כמה שורות |
| `SUM(price)` | סכום |
| `AVG(price)` | ממוצע |
| `MIN` / `MAX` | הקטן / הגדול ביותר |

**`GROUP BY`** מחלק את השורות לקבוצות ומחשב סיכום **לכל קבוצה** – כמו **Pivot Table** באקסל:

```sql
SELECT category, COUNT(*) AS products, AVG(price) AS avg_price
FROM products
GROUP BY category
HAVING COUNT(*) >= 5        -- סינון על הקבוצות (WHERE מסנן שורות לפני הקיבוץ)
ORDER BY products DESC;
```

> [!tip] מה Senior יודע: SQL הוא שפה **הצהרתית** – אתה אומר **מה** אתה רוצה, לא **איך** להשיג את זה. המסד בוחר לבד את הדרך המהירה ביותר (Query Plan). לכן חישוב כמו "סכום לפי קטגוריה" כמעט תמיד מהיר יותר ב-SQL מאשר לשלוף את כל השורות ל-Node ולחשב ב-JavaScript.

CREATE TABLE orders (

  ('אורי', 'paid', 249.90),
  ('דנה', 'pending', 89.00),
  ('אורי', 'shipped', 1200.00),
  ('יוסי', 'paid', 45.50);

-- 3) ההזמנות ששולמו, מהגדולה לקטנה, רק 10 ראשונות
SELECT id, customer, total
FROM orders
WHERE status = 'paid'
ORDER BY total DESC
LIMIT 10;

-- 4) עדכון בטוח: קודם בודקים מה ישתנה...
SELECT * FROM orders WHERE id = 2;
-- ...ורק אז מעדכנים, עם אותו WHERE
UPDATE orders SET status = 'paid' WHERE id = 2;

-- 5) דוח: כמה הזמנות וכמה כסף לכל לקוח
SELECT customer,
       COUNT(*)   AS orders_count,
       SUM(total) AS total_spent
FROM orders
WHERE status <> 'pending'
GROUP BY customer
ORDER BY total_spent DESC;

-- 6) מחיקה – תמיד עם WHERE!
DELETE FROM orders WHERE status = 'pending' AND created_at < now() - interval '30 days';

## מה קורה בכל חלק?

1. **`CREATE TABLE`** – מגדירים את "הגיליון": שם, עמודות וסוג לכל עמודה. `CHECK (total >= 0)` אומר למסד לדחות כל ניסיון להכניס סכום שלילי – גם אם יש באג בקוד שלנו. המסד הוא קו ההגנה האחרון על הנתונים.
2. **`INSERT ... VALUES (...), (...)`** – מכניסים כמה שורות בפקודה אחת. לא שולחים `id` – המסד מייצר אותו. **שים לב:** טקסט ב-SQL הוא במירכאות **בודדות** (`'paid'`); מירכאות כפולות הן לשמות עמודות וטבלאות.
3. **`SELECT ... WHERE ... ORDER BY ... LIMIT`** – הסדר בכתיבה קבוע: `SELECT` ← `FROM` ← `WHERE` ← `GROUP BY` ← `HAVING` ← `ORDER BY` ← `LIMIT`.
4. **"קודם SELECT"** – ההרגל הבטוח לפני כל שינוי. אם ה-SELECT מחזיר שורה אחת – ה-UPDATE ישנה שורה אחת.
5. **`GROUP BY customer`** – מקבץ את כל ההזמנות של אותו לקוח, ו-`COUNT`/`SUM` מחושבים לכל קבוצה. `AS` נותן שם יפה לעמודה בתוצאה.
6. **`now() - interval '30 days'`** – חשבון תאריכים מובנה: "לפני 30 יום". מוחקים רק הזמנות ממתינות וישנות.

> [!tip] נסה בעצמך: אפשר להריץ PostgreSQL בלי להתקין כלום באתר `db-fiddle.com` (בחר PostgreSQL), או מקומית עם Docker: `docker run -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres` (נלמד Docker במודול 10).

```sql
CREATE TABLE tasks (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title       text NOT NULL CHECK (length(title) BETWEEN 1 AND 200),
  priority    integer NOT NULL DEFAULT 2 CHECK (priority BETWEEN 1 AND 3),
  done        boolean NOT NULL DEFAULT false,
  due_date    date,
  created_at  timestamptz NOT NULL DEFAULT now()
);

INSERT INTO tasks (title, priority, due_date) VALUES
  ('ללמוד SQL', 1, '2026-11-20'),
  ('לקנות חלב', 3, NULL),
  ('לבנות API', 1, '2026-11-25'),
  ('לקרוא על Indexes', 2, '2026-12-01'),
  ('לסדר את החדר', 3, NULL);

-- 1) משימות פתוחות בעדיפות גבוהה, לפי תאריך יעד
SELECT title, due_date FROM tasks
WHERE done = false AND priority = 1
ORDER BY due_date;

-- 2) סימון כבוצעה – קודם SELECT, אחר כך UPDATE
SELECT * FROM tasks WHERE id = 1;
UPDATE tasks SET done = true WHERE id = 1;

-- 3) כמה משימות פתוחות וסגורות לכל עדיפות
SELECT priority, done, COUNT(*) AS cnt
FROM tasks
GROUP BY priority, done
ORDER BY priority, done;

-- 4) מחיקת משימות שבוצעו
DELETE FROM tasks WHERE done = true;
```

**מה למדנו:** `CHECK` ו-`DEFAULT` מעבירים כללים מהקוד אל המסד עצמו; `GROUP BY` על **שתי עמודות** יוצר קבוצה לכל צירוף (עדיפות 1 + פתוח, עדיפות 1 + סגור...); ותמיד `SELECT` לפני `UPDATE`/`DELETE`.

## איך מסדרים נתונים שקשורים זה לזה?

בשיעור הקודם הייתה לנו טבלה אחת. אבל בחנות אמיתית יש **משתמשים**, **הזמנות**, **מוצרים** – והם קשורים: למשתמש יש הרבה הזמנות, בכל הזמנה יש הרבה מוצרים. **Data Modeling** (מידול נתונים) הוא האומנות של לתכנן את הטבלאות ואת הקשרים ביניהן.

### אנלוגיה: ארון תיקים במשרד

- לכל לקוח יש **תיק** עם **מספר לקוח** ייחודי ← **Primary Key**.
- בתיק של כל הזמנה כתוב "שייך ללקוח מספר 17" – לא מעתיקים את כל פרטי הלקוח לכל הזמנה ← **Foreign Key**.
- אם הלקוח עבר דירה, מעדכנים את הכתובת **במקום אחד** – בתיק הלקוח ← **Normalization**.
- כשרוצים "את כל ההזמנות של דנה עם הכתובת שלה", מוציאים את שני התיקים ושמים אותם זה ליד זה ← **JOIN**.

> [!example] באפליקציית צ'אט: `users`, `chats`, ו-`messages`. כל הודעה מצביעה על המשתמש ששלח אותה ועל הצ'אט שבו נשלחה. משתמש משנה את שם התצוגה? משנים שורה אחת – וכל ההודעות שלו מציגות את השם החדש.

בשיעור הזה נלמד גם איך מדברים עם PostgreSQL מתוך **Node.js** – ואיך לעשות את זה בלי לפתוח את הדלת לפרצת האבטחה המפורסמת ביותר: **SQL Injection**.

## 1. Primary Key – תעודת זהות לשורה

**Primary Key** (מפתח ראשי) הוא עמודה (או כמה) שמזהה כל שורה **באופן ייחודי**, אף פעם לא `NULL`, ולא משתנה. בדרך כלל `id` מספרי (`bigint ... IDENTITY`) או `uuid`.

> [!note] למה לא להשתמש באימייל כ-Primary Key? כי אימייל **יכול להשתנות**, וכל הטבלאות שמצביעות עליו יצטרכו להשתנות איתו. עדיף מזהה "טכני" שאין לו משמעות עסקית, ועל האימייל לשים `UNIQUE`.

## 2. Foreign Key – קשר בין טבלאות

**Foreign Key** (מפתח זר) הוא עמודה שמצביעה על Primary Key בטבלה אחרת. המסד **אוכף** את הקשר: אי אפשר ליצור הזמנה למשתמש שלא קיים, ואי אפשר למחוק משתמש שיש לו הזמנות (אלא אם הגדרת מה לעשות – `ON DELETE CASCADE` מוחק גם אותן).

## 3. סוגי קשרים

| קשר | דוגמה | איך ממדלים |
|---|---|---|
| **One-to-Many** (אחד לרבים) | משתמש ← הרבה הזמנות | Foreign Key בצד ה"רבים": `orders.user_id` |
| **Many-to-Many** (רבים לרבים) | הזמנה ← הרבה מוצרים; מוצר ← בהרבה הזמנות | **Junction Table** (טבלת קישור): `order_items(order_id, product_id, quantity)` |
| **One-to-One** | משתמש ← פרופיל | Foreign Key עם `UNIQUE` |

**Junction Table** היא טבלה שכל שורה בה היא "קשר" אחד – ויכולה להכיל מידע על הקשר עצמו: כמות, המחיר **בזמן הקנייה** וכו'.

## 4. JOIN – חיבור טבלאות בשאילתה

```sql
-- INNER JOIN: רק משתמשים שיש להם הזמנות
SELECT u.name, o.id, o.total
FROM users u
JOIN orders o ON o.user_id = u.id;

-- LEFT JOIN: כל המשתמשים, גם בלי הזמנות (העמודות של orders יהיו NULL)
SELECT u.name, COUNT(o.id) AS orders_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;
```

| JOIN | מה מחזיר | מתי |
|---|---|---|
| **INNER JOIN** | רק שורות שיש להן התאמה בשני הצדדים | "הזמנות עם פרטי הלקוח" |
| **LEFT JOIN** | **כל** השורות מהטבלה השמאלית, גם בלי התאמה | "כל המשתמשים וכמה הזמנות יש לכל אחד (גם 0)" |

> [!tip] טריק נפוץ: "משתמשים **שאין** להם הזמנות" = `LEFT JOIN` + `WHERE o.id IS NULL`.

## 5. Normalization – כל עובדה במקום אחד

**Normalization** (נרמול) בשפה פשוטה: **לא לשכפל מידע**. אם שם הלקוח שמור גם ב-`users` וגם בכל שורה ב-`orders`, ברגע שהוא ישתנה – חלק מהמקומות יתעדכנו וחלק לא, ויהיו לך "שתי אמיתות".

- **לנרמל** = לשמור את השם רק ב-`users`, וב-`orders` רק `user_id`.
- **חריגה מכוונת**: לפעמים **רוצים** עותק – למשל המחיר ב-`order_items` הוא המחיר **ביום הקנייה**, ולא צריך להשתנות כשמחיר המוצר משתנה. זה לא שכפול – זו עובדה היסטורית אחרת.

## 6. JSONB – כשהמבנה גמיש

**JSONB** הוא סוג עמודה ששומר מסמך JSON (בפורמט בינארי מהיר), ואפשר לחפש בתוכו:

```sql
-- מוצרים עם מאפיינים שונים: לחולצה יש מידה, למחשב יש זיכרון
SELECT name FROM products WHERE attributes->>'color' = 'red';
SELECT name FROM products WHERE attributes @> '{"size": "M"}';
```

| מתאים ל-JSONB ✓ | לא מתאים ✗ |
|---|---|
| מאפיינים שמשתנים מסוג לסוג | שדות שכל שורה צריכה (מחיר, סטטוס) |
| Payload גולמי מ-Webhook / API חיצוני | נתונים שעושים עליהם JOIN |
| הגדרות משתמש (Preferences) | ערכים שצריך עליהם Foreign Key או Constraint |

> [!warn] JSONB הוא לא תירוץ לוותר על תכנון. אם אתה מוצא את עצמך מחפש כל הזמן לפי שדה בתוך JSONB – הוא כנראה צריך להיות עמודה רגילה.

## 7. מ-Node.js ל-Postgres: ספריית `pg` ו-Parameterized Queries

```typescript ❌ לעולם לא – SQL Injection
db.query(`SELECT * FROM users WHERE email = '${email}'`);
// אם email = "' OR '1'='1" ← השאילתה מחזירה את כל המשתמשים!
```

```typescript ✅ Parameterized Query
db.query('SELECT * FROM users WHERE email = $1', [email]);
```

ב-**Parameterized Query**, ה-SQL והערכים נשלחים למסד **בנפרד**. `$1` הוא "מקום שמור", והמסד מתייחס לערך **תמיד כנתון, לעולם לא כקוד**. זה מנטרל SQL Injection לחלוטין.

> [!danger] **SQL Injection** היא עדיין אחת הפרצות הנפוצות בעולם. הכלל פשוט: **אף פעם** לא מחברים קלט של משתמש לתוך מחרוזת SQL. תמיד `$1`, `$2`...

## 8. ORMs ו-Query Builders

| כלי | מה זה | יתרונות |
|---|---|---|
| **`pg`** (SQL ישיר) | כותבים SQL בעצמך | שליטה מלאה, אין "קסמים" |

## הסבר – ה-Schema

- **`email text NOT NULL UNIQUE`** – המסד מבטיח שאין שני משתמשים עם אותו אימייל, גם אם שתי הרשמות מגיעות באותה שנייה. בדיקה בקוד לבד לא מספיקה לזה.

- **`PRIMARY KEY (order_id, product_id)`** – **Composite Key**: הצירוף ייחודי. אי אפשר שאותו מוצר יופיע פעמיים באותה הזמנה (מגדילים `quantity` במקום).

- **`new Pool(...)`** – פותחים חיבור למסד דרך כתובת שמגיעה ממשתנה סביבה (`postgres://user:pass@host:5432/db`) – סוד, לא בקוד.

## חלק א׳: Indexes

### 1. מה זה Index?

**Index** הוא מבנה נתונים נוסף שהמסד שומר ליד הטבלה, ממוין לפי עמודה מסוימת, עם "מצביע" לכל שורה. ב-Postgres ברירת המחדל היא **B-tree** – עץ מאוזן שבו כל חיפוש לוקח כמה צעדים בודדים, גם במיליארד שורות (כמו לחפש במילון: פותחים באמצע, מחליטים לאיזה צד, וחוזר חלילה).

B-tree מתאים ל: `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, ו-`LIKE 'abc%'` (התחלה בלבד).

```sql
CREATE INDEX idx_orders_user_id ON orders (user_id);
```

> [!note] Postgres יוצר Index אוטומטית על כל `PRIMARY KEY` ו-`UNIQUE`. אבל **לא** על Foreign Keys! `orders.user_id` – צריך ליצור בעצמך. זו אחת הסיבות הנפוצות לשאילתות איטיות.

### 2. Composite Index – כמה עמודות

```sql
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);
```

מושלם לשאילתה "ההזמנות של משתמש X, מהחדשה לישנה". **הסדר חשוב** – כמו ספר טלפונים שממוין לפי שם משפחה ואז שם פרטי: מצוין לחיפוש "כהן", או "כהן דנה", אבל לא עוזר לחיפוש "כל מי ששמו דנה".

### 3. Partial Index – רק חלק מהשורות

```sql
CREATE INDEX idx_orders_pending ON orders (created_at) WHERE status = 'pending';
```

אם רק 1% מההזמנות ממתינות ותמיד מחפשים רק אותן – Index קטן פי 100, מהיר יותר וזול יותר לעדכון.

### 4. EXPLAIN ANALYZE – לראות מה המסד עושה

`EXPLAIN ANALYZE` לפני שאילתה **מריץ אותה** ומראה את ה-**Query Plan**: איך המסד בחר לבצע אותה וכמה זמן כל שלב לקח.

| מה רואים | מה זה אומר |
|---|---|
| `Seq Scan on orders` | סורק את **כל** הטבלה. בטבלה גדולה עם WHERE סלקטיבי ← חשוד, חסר Index |
| `Index Scan using idx_...` | משתמש ב-Index וקופץ לשורות הנכונות ✓ |
| `Index Only Scan` | כל המידע נמצא ב-Index, לא צריך לגשת לטבלה בכלל ✓✓ |
| `rows=... (actual rows=...)` | הערכה מול מציאות. פער גדול ← הסטטיסטיקות לא מעודכנות (`ANALYZE`) |
| `actual time=0.04..812.3` | זמן ההתחלה והסיום של השלב במילישניות |

> [!tip] Seq Scan **לא תמיד רע**: בטבלה קטנה, או כשמחזירים חלק גדול מהשורות, סריקה מלאה מהירה יותר מקפיצות ב-Index. המסד יודע את זה – והוא בוחר לבד.

### 5. המחיר של Indexes

כל Index: תופס מקום בדיסק, **מאט כל INSERT/UPDATE/DELETE** (צריך לעדכן גם אותו), וצריך להיכנס לזיכרון כדי להיות מהיר. לכן לא שמים Index "על כל עמודה ליתר ביטחון" – יוצרים לפי השאילתות האמיתיות ובודקים עם `EXPLAIN ANALYZE`.

## חלק ב׳: Transactions ומקביליות

### 6. Transaction ו-ACID

**Transaction** = קבוצת פעולות שמתבצעות **כיחידה אחת**: או שכולן מצליחות, או שאף אחת. הדוגמה הקלאסית – העברת כסף: מורידים מחשבון A **ו**מוסיפים לחשבון B. אם השרת קורס באמצע, אסור שהכסף "ייעלם".

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- שומר הכל. במקרה של בעיה: ROLLBACK – מבטל הכל
```

| ACID | משמעות פשוטה |
|---|---|
| **Atomicity** | הכל או כלום |
| **Consistency** | הנתונים תמיד עומדים בכללים (Constraints) |
| **Isolation** | Transactions מקבילות לא "רואות" חצאי עבודה של אחרות |
| **Durability** | אחרי COMMIT – הנתונים שמורים גם אם החשמל נופל |

### 7. Race Condition – המקום האחרון

```text שני משתמשים, אותו מקום, אותו רגע
משתמש א׳: SELECT available FROM seats WHERE id=7  → true
משתמש ב׳: SELECT available FROM seats WHERE id=7  → true
משתמש א׳: UPDATE seats SET available=false ...; INSERT booking ...
משתמש ב׳: UPDATE seats SET available=false ...; INSERT booking ...   ← הזמנה כפולה!
```

הבעיה: **"בדוק ואז פעל"** (Check-then-Act) הן שתי פעולות נפרדות, ובין שתיהן מישהו אחר יכול להיכנס. Transaction לבד **לא** פותר את זה ברמת הבידוד ברירת המחדל (`READ COMMITTED`).

### 8. שלושה פתרונות

**א. Unique Constraint – תן למסד לאכוף**
```sql
CREATE UNIQUE INDEX one_booking_per_seat ON bookings (event_id, seat_id);
```
השני שינסה להכניס הזמנה לאותו מקום יקבל שגיאה (`23505 unique_violation`) ← מחזירים `409`. הפתרון הפשוט והחזק ביותר, כשאפשר לנסח את הכלל כ"ייחודיות".

**ב. `SELECT ... FOR UPDATE` – נעילה פסימית (Pessimistic Locking)**
"אני נועל את השורה הזו עד סוף ה-Transaction". מי שינסה לנעול אותה שורה **יחכה** עד שהראשון יסיים – ואז יראה את הערך המעודכן. מתאים כשיש הרבה התנגשויות על אותה שורה (מלאי, יתרה).

**ג. Optimistic Locking עם עמודת `version`**
לא נועלים. קוראים את השורה עם ה-`version` שלה, ובעדכון בודקים שהיא לא השתנתה:
```sql
UPDATE products SET stock = stock - 1, version = version + 1
WHERE id = 5 AND version = 3;   -- 0 שורות עודכנו? מישהו הקדים אותך ← נסה שוב / 409
```
מתאים כשהתנגשויות נדירות – למשל שני עורכים של אותו מסמך.

> [!tip] לעיתים קרובות הכי פשוט הוא **עדכון אטומי אחד** עם תנאי: `UPDATE products SET stock = stock - 1 WHERE id = 5 AND stock > 0` – אם חזרו 0 שורות, אזל המלאי. בלי SELECT לפני, בלי Race.

## חלק ג׳: טיפים של Senior

> [!tip] **Connection Pooling** – כל חיבור ל-Postgres הוא תהליך שלם בשרת המסד (כמה MB זיכרון). 50 שרתי Node × 20 חיבורים = 1,000 חיבורים, והמסד נחנק. `Pool` בתוך Node משתמש מחדש בחיבורים, ו-**PgBouncer** הוא "מאגר חיבורים" חיצוני שמאפשר לאלפי לקוחות לחלוק כמה עשרות חיבורים אמיתיים. וכלל ברזל: **לא** מחזיקים Transaction פתוח בזמן קריאה ל-API חיצוני – זה תופס חיבור ונעילות.

> [!tip] **Partitioning** – כשטבלה מגיעה למאות מיליוני שורות (לוגים, אירועים, הודעות צ'אט), מחלקים אותה ל"תת-טבלאות" לפי טווח – למשל Partition לכל חודש. שאילתות על החודש האחרון סורקות רק Partition אחד, ומחיקת נתונים ישנים היא `DROP` של Partition שלם במקום `DELETE` של מיליונים.

export async function bookSeat(eventId: number, seatId: number, userId: number) {
  const client = await db.connect(); // Transaction חייב לרוץ על חיבור אחד
  try {
    await client.query('BEGIN');

    // נועלים את השורה: Transaction מקבילה על אותו מקום תחכה כאן

    }

    await client.query('UPDATE seats SET available = false WHERE event_id = $1 AND id = $2', [eventId, seatId]);
    await client.query('INSERT INTO bookings (event_id, seat_id, user_id) VALUES ($1, $2, $3)', [eventId, seatId, userId]);

    await client.query('COMMIT'); // רק עכשיו השינויים נראים לאחרים והנעילה משתחררת
    return { ok: true as const };
  } catch (err) {
    await client.query('ROLLBACK'); // כל שגיאה – מבטלים הכל
    throw err;
  } finally {
    client.release(); // מחזירים את החיבור ל-Pool – תמיד!
  }
}

## הסבר – Indexes

- **`EXPLAIN ANALYZE`** – מריץ את השאילתה באמת ומחזיר את התוכנית. לפני ה-Index: `Seq Scan` על כל הטבלה – 850ms. אחרי: `Index Scan` – פחות ממילישנייה.
- **`(user_id, created_at DESC)`** – קודם העמודה שמסננים לפיה ב-`=`, אחר כך העמודה שממיינים לפיה. המסד קופץ ל"user 42" ב-Index ופשוט קורא את 20 הרשומות הראשונות, שכבר ממוינות. אין צורך למיין בכלל.
- **`CONCURRENTLY`** – `CREATE INDEX` רגיל נועל את הטבלה לכתיבה עד שהבנייה נגמרת (יכול לקחת דקות!). ב-Production תמיד `CONCURRENTLY`.
- **Partial Index** – `WHERE status = 'pending'` גורם ל-Index להכיל רק את השורות האלה.

## הסבר – Transaction

- **`db.connect()`** – לוקחים חיבור **אחד** מה-Pool. חשוב: אם נריץ `BEGIN` עם `db.query` ואת ה-`UPDATE` עם `db.query` נוסף, הם עלולים לרוץ על **חיבורים שונים** – וה-Transaction לא באמת עוטף אותם.
- **`FOR UPDATE`** – נועל את שורת המקום. בקשה שנייה לאותו מקום **נעצרת** בשורה הזו עד ש-COMMIT או ROLLBACK של הראשונה. כשהיא ממשיכה – היא רואה `available = false`.
- **`ROLLBACK` ב-catch** – כל שגיאה (גם באג בקוד) מבטלת את כל השינויים: אין מצב של "המקום סומן תפוס אבל ההזמנה לא נוצרה".
- **`finally { client.release() }`** – אם שוכחים, החיבור "דולף". אחרי 10 דליפות ה-Pool ריק וכל השרת נתקע בהמתנה לחיבור.

> [!note] שכבת הגנה נוספת וזולה: Unique Index על `bookings (event_id, seat_id)`. גם אם יום אחד מישהו יכתוב קוד שעוקף את הפונקציה הזו – המסד עדיין לא ירשה הזמנה כפולה. **Defense in Depth**.

**2. הורדת מלאי בלי מכירה כפולה – Optimistic Locking:**

```typescript src/stock.ts
export async function buyProduct(productId: number, maxAttempts = 3) {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    const { rows } = await db.query('SELECT stock, version FROM products WHERE id = $1', [productId]);
    if (rows.length === 0) return { ok: false, reason: 'NOT_FOUND' };
    if (rows[0].stock <= 0) return { ok: false, reason: 'OUT_OF_STOCK' };

    const result = await db.query(
      `UPDATE products SET stock = stock - 1, version = version + 1
       WHERE id = $1 AND version = $2`,
      [productId, rows[0].version],
    );
    if (result.rowCount === 1) return { ok: true };   // הצלחנו – אף אחד לא הקדים אותנו
    // rowCount === 0 ← מישהו עדכן בינתיים; מנסים שוב עם הנתונים החדשים
  }
  return { ok: false, reason: 'CONFLICT' };            // ← 409 ללקוח
}
```

**3. החלופה הפשוטה ביותר – עדכון אטומי עם תנאי:**

```sql
UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock > 0 RETURNING stock;
-- 0 שורות ← אזל המלאי. אין SELECT לפני, אין חלון ל-Race Condition.
```

**מתי מה?** עדכון אטומי – כשכל ההחלטה נכנסת ב-WHERE אחד. Optimistic – כשההתנגשויות נדירות והלוגיקה מורכבת. `FOR UPDATE` – כשההתנגשויות תכופות ואין טעם "לנסות שוב" בלולאה.
