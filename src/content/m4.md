## מה זה בכלל "Server"?

במודול 1 ראינו שהדפדפן שולח **Request** ומקבל **Response**. עכשיו נעבור לצד השני של הקו: נכתוב בעצמנו את התוכנה שמקבלת את הבקשות. תוכנה כזו נקראת **Server** (שרת).

**Server** הוא פשוט תוכנה שרצה כל הזמן, "מאזינה" על **Port** מסוים (למשל 3000), ומחכה לבקשות. כשבקשה מגיעה, השרת מחליט מה לעשות איתה, ומחזיר תשובה. כשהבקשות האלה מחזירות נתונים (בדרך כלל JSON) ולא דפים, קוראים לזה **API**.

### אנלוגיה: מוקד שירות לקוחות

- **המוקד** פתוח כל הזמן ומחכה לשיחות ← זה ה-**Server** שמאזין על Port.
- **התפריט הקולי** ("לחשבונות הקש 1, לתמיכה הקש 2") ← אלה ה-**Routes** – כל כתובת מגיעה לנציג אחר.
- **המאבטח בכניסה** שבודק תעודה, ו**המקליט** ש"השיחה מוקלטת לצורך שיפור השירות" ← אלה ה-**Middleware** – שלבים שכל שיחה עוברת לפני שהיא מגיעה לנציג.
- **הנציג** שעונה בפועל ← זה ה-**Handler** – הפונקציה שמטפלת בבקשה ומחזירה תשובה.

> [!tip] כמעט כל Backend בעולם – של חנות, אפליקציית צ'אט או מערכת תשלומים – בנוי מאותם שלושה רעיונות: **Routes**, **Middleware** ו-**Handlers**. ברגע שתבין אותם ב-Node.js, תזהה אותם גם ב-Python, Go או Java.

### למה Node.js?

**Node.js** מאפשר להריץ JavaScript (ו-TypeScript) **מחוץ לדפדפן** – על שרת. היתרון הענק: אותה שפה ב-Frontend וב-Backend, אותם כלים, ואפילו אותם Types משותפים. בשיעור הזה נבנה API קטן לניהול משימות עם הספרייה הפופולרית **Express**.

## בונים שרת ראשון, צעד אחר צעד

### 1. מה הספרייה עושה בשבילנו?

אפשר לכתוב שרת עם המודול המובנה `node:http`, אבל זה מסורבל: צריך לפרק בעצמך כתובות, לקרוא את הגוף בחתיכות ולהמיר JSON. **Express** (או **Fastify** – מודרני ומהיר יותר) עושה את כל זה בשבילך ונותן ממשק פשוט:

```typescript הרעיון במשפט אחד
app.get('/api/tasks', (req, res) => res.json(tasks));
// "כשמגיע GET לנתיב הזה – תריץ את הפונקציה הזו"
```

### 2. Routes – "לאן הבקשה הולכת"

**Route** = שילוב של **HTTP Method** + **Path**. אותו נתיב עם מתודה אחרת הוא Route אחר:

| Route | מה הוא עושה |
|---|---|
| `GET /api/tasks` | מחזיר רשימת משימות |
| `GET /api/tasks/:id` | מחזיר משימה אחת |
| `POST /api/tasks` | יוצר משימה חדשה |
| `DELETE /api/tasks/:id` | מוחק משימה |

### 3. req ו-res – הבקשה והתשובה

כל Handler מקבל שני אובייקטים:

- **`req`** (Request) – כל מה שהלקוח שלח: מתודה, נתיב, Headers, גוף.
- **`res`** (Response) – הכלי שלך לענות: `res.status(201)`, `res.json({...})`, `res.send()`.

### 4. שלוש דרכים לקבל מידע מהלקוח

| מקור | דוגמה | איך קוראים בקוד | מתי משתמשים |
|---|---|---|---|
| **Route Params** | `/api/tasks/42` | `req.params.id` ← `'42'` | לזהות **משאב מסוים** |
| **Query String** | `/api/tasks?done=true&limit=10` | `req.query.done` ← `'true'` | **סינון, מיון, עמודים** |
| **JSON Body** | `{"title":"לקנות חלב"}` | `req.body.title` | **נתונים ליצירה או עדכון** (POST/PATCH) |

> [!warn] כל מה שמגיע מ-params ומ-query הוא **טקסט** (string), גם אם נראה כמו מספר. `req.params.id` הוא `'42'` ולא `42`. צריך להמיר עם `Number(...)` – ולבדוק שהתוצאה תקינה.

> [!note] כדי ש-`req.body` יהיה אובייקט ולא `undefined`, צריך להפעיל את ה-Middleware `express.json()` שקורא את הגוף ומפרש את ה-JSON. זו הטעות הראשונה שכמעט כל מתחיל עושה.

### 5. Middleware – פס ייצור

**Middleware** היא פונקציה שרצה **לפני** ה-Handler. היא מקבלת `(req, res, next)` ויכולה:

1. **להסתכל** על הבקשה (למשל לרשום ללוג) ואז לקרוא ל-`next()` כדי להעביר הלאה.
2. **להוסיף** מידע לבקשה (למשל `req.user` אחרי בדיקת זהות).
3. **לעצור** את הבקשה ולענות בעצמה (למשל `401` אם אין הרשאה) – בלי לקרוא ל-`next()`.

תחשוב על זה כמו **פס ייצור** במפעל: כל תחנה עושה דבר אחד ומעבירה הלאה. הסדר חשוב! Middleware שנרשם ראשון רץ ראשון.

```text צינור של בקשה אחת
Request → [logger] → [express.json] → [auth] → Handler → Response
```

> [!example] בחנות אונליין: `logger` רושם כל בקשה, `express.json` מפרש את גוף ההזמנה, `requireAuth` מוודא שהמשתמש מחובר, ורק אז ה-Handler יוצר את ההזמנה.

### 6. מבנה פרויקט שגדל איתך

כשיש 3 Routes, הכל יכול לשבת בקובץ אחד. כשיש 50 – לא. מבנה נפוץ ופשוט:

```text מבנה תיקיות
src/
  server.ts            ← יוצר את app, רושם Middleware ו-Routes, מאזין ל-Port
  routes/tasks.ts      ← רק HTTP: קורא params/body, קורא ל-service, מחזיר תשובה
  services/tasks.ts    ← הלוגיקה העסקית: "איך יוצרים משימה", בלי לדעת על HTTP
  middleware/auth.ts   ← Middleware לשימוש חוזר
```

החלוקה הזו נקראת **Separation of Concerns**: קובץ ה-Route מדבר HTTP, קובץ ה-Service מדבר "עסקים". כך אפשר לבדוק את ה-Service בלי שרת, ולהחליף את Express בלי לגעת בלוגיקה.

import express, { type Request, type Response, type NextFunction } from 'express';

type Task = { id: number; title: string; done: boolean };
const tasks: Task[] = [{ id: 1, title: 'ללמוד Express', done: false }]; // "מסד נתונים" בזיכרון
let nextId = 2;

const app = express();

// Middleware 1: מפרש גוף JSON ושם אותו ב-req.body
app.use(express.json());

// Middleware 2: לוג לכל בקשה – כמה זמן לקחה ואיזה קוד חזר
app.use((req: Request, res: Response, next: NextFunction) => {
  const start = Date.now();
  res.on('finish', () => console.log(`${req.method} ${req.path} → ${res.statusCode} (${Date.now() - start}ms)`));
  next(); // חובה! אחרת הבקשה "נתקעת" כאן
});

// GET /api/tasks?done=true  – רשימה עם סינון אופציונלי מה-Query String
app.get('/api/tasks', (req: Request, res: Response) => {
  const { done } = req.query;
  const result = done === undefined ? tasks : tasks.filter((t) => String(t.done) === done);
  res.json(result);
});

// GET /api/tasks/:id  – משימה אחת לפי Route Param
app.get('/api/tasks/:id', (req: Request, res: Response) => {
  const id = Number(req.params.id); // params הם תמיד string
  const task = tasks.find((t) => t.id === id);
  if (!task) return res.status(404).json({ error: 'המשימה לא נמצאה' });
  res.json(task);
});

// POST /api/tasks  – יצירה מגוף JSON
app.post('/api/tasks', (req: Request, res: Response) => {
  const title = req.body?.title;
  if (typeof title !== 'string' || title.trim() === '') {
    return res.status(400).json({ error: 'חסר title' });
  }
  const task: Task = { id: nextId++, title: title.trim(), done: false };
  tasks.push(task);
  res.status(201).json(task); // 201 = נוצר
});

const PORT = Number(process.env.PORT ?? 3000);
app.listen(PORT, () => console.log(`Server listening on http://localhost:${PORT}`));

## מה קורה בקוד?

- **`const app = express()`** – יוצר את אפליקציית השרת. עדיין לא מאזין לכלום – זה קורה רק ב-`app.listen` בסוף.
- **`app.use(express.json())`** – Middleware שרץ על **כל** בקשה: קורא את הגוף, ואם ה-`Content-Type` הוא JSON – ממיר לאובייקט ב-`req.body`.
- **ה-Middleware של הלוג** – מודד זמן ומדפיס שורה כשהתשובה נשלחה (`res.on('finish')`). שים לב ל-`next()`: בלעדיו הבקשה לעולם לא תגיע ל-Handler והלקוח יחכה לנצח.
- **`req.query`** – הכל טקסט, לכן משווים `String(t.done) === done`.
- **`Number(req.params.id)`** – המרה ממחרוזת למספר. אם מישהו ישלח `/api/tasks/abc` נקבל `NaN`, שלא יימצא – ונחזיר 404.
- **`return res.status(404).json(...)`** – ה-`return` חשוב: הוא עוצר את הפונקציה כדי שלא ננסה לשלוח תשובה פעמיים (שגיאה נפוצה: "Cannot set headers after they are sent").
- **`res.status(201)`** – קוד הסטטוס הנכון ליצירה, כמו שלמדנו במודול 1.
- **`process.env.PORT`** – קוראים את הפורט מ-**Environment Variable**, עם ברירת מחדל 3000. ככה אותו קוד רץ גם במחשב שלך וגם בשרת אמיתי.

> [!note] המערך `tasks` חי בזיכרון – כשהשרת עולה מחדש, הכל נמחק. במודול 5 נחליף אותו ב-PostgreSQL אמיתי.

## פתרון לדוגמה

```typescript src/middleware/requireApiKey.ts
import type { Request, Response, NextFunction } from 'express';

export function requireApiKey(req: Request, res: Response, next: NextFunction) {
  if (req.header('x-api-key') !== process.env.API_KEY) {
    return res.status(401).json({ error: 'מפתח API חסר או שגוי' }); // עוצרים – בלי next()
  }
  next();
}
```

```typescript src/routes/tasks.ts
import { Router } from 'express';
import { requireApiKey } from '../middleware/requireApiKey';
import * as taskService from '../services/tasks';

export const tasksRouter = Router();

tasksRouter.patch('/:id', requireApiKey, (req, res) => {
  const task = taskService.markDone(Number(req.params.id));
  if (!task) return res.status(404).json({ error: 'המשימה לא נמצאה' });
  res.json(task);
});

tasksRouter.delete('/:id', requireApiKey, (req, res) => {
  const deleted = taskService.remove(Number(req.params.id));
  if (!deleted) return res.status(404).json({ error: 'המשימה לא נמצאה' });
  res.status(204).send(); // 204 = הצליח, אין תוכן
});
```

```typescript src/services/tasks.ts
const tasks: { id: number; title: string; done: boolean }[] = [];

export function markDone(id: number) {
  const task = tasks.find((t) => t.id === id);
  if (task) task.done = true;
  return task;
}

export function remove(id: number) {
  const index = tasks.findIndex((t) => t.id === id);
  if (index === -1) return false;
  tasks.splice(index, 1);
  return true;
}
```

וב-`server.ts`: `app.use('/api/tasks', tasksRouter);`

**מה למדנו:** Middleware אפשר להפעיל על **Route ספציפי** (ולא רק גלובלית), ה-Route לא יודע **איך** מוחקים – רק קורא ל-Service, והסוד (`API_KEY`) מגיע ממשתנה סביבה ולא כתוב בקוד.

## מ"עובד אצלי" ל-API שאפשר לסמוך עליו

השרת מהשיעור הקודם עובד – כל עוד כולם מתנהגים יפה. אבל בעולם האמיתי לקוחות שולחים נתונים חסרים, משתמשים מנסים לגשת למידע של אחרים, ובוטים מנסים לנחש סיסמאות אלף פעם בדקה. **API מקצועי** הוא API שמתנהג בצורה צפויה גם כשמשהו משתבש.

### אנלוגיה: סניף בנק

- **הפקידה בודקת שהטופס מלא נכון** לפני שהיא מתחילה לעבוד ← **Validation** (בדיקת קלט).
- **כשמשהו לא בסדר, מקבלים הודעה ברורה ואחידה** ("חסרה חתימה בשדה 4") ← **Error Handling** עקבי.
- **מציגים תעודת זהות** בכניסה ← **Authentication** (מי אתה?).
- **גם עם תעודה, אי אפשר למשוך מחשבון של מישהו אחר** ← **Authorization** (מה מותר לך?).
- **הבנק לא שומר את הקוד הסודי שלך** – רק דרך לבדוק אותו ← **Password Hashing**.
- **הכספת נפתחת רק עם מפתח שלא כתוב על הדלת** ← **Environment Variables** לסודות.

> [!tip] בראיונות עבודה, שאלה כמו "איך היית בונה Endpoint להרשמה?" בודקת בדיוק את הנושאים של השיעור הזה. התשובה הטובה לא מתחילה בקוד – היא מתחילה ב"קודם בודקים קלט, שומרים Hash ולא סיסמה, ומחזירים שגיאות אחידות".

## 1. Validation – לעולם אל תסמוך על הלקוח

כל מה שמגיע מבחוץ – Body, Query, Params, Headers – יכול להיות **כל דבר**: חסר, מהסוג הלא נכון, ארוך מדי, או זדוני. גם אם ה-Frontend שלך בודק, מישהו יכול לשלוח בקשה ישירות עם `curl`.

**Zod** היא ספרייה שבה מגדירים **Schema** (תבנית) של הנתונים, והיא גם בודקת בזמן ריצה וגם נותנת לך **Type** של TypeScript בחינם:

```typescript Schema אחד – גם בדיקה וגם Type
const CreateTask = z.object({
  title: z.string().trim().min(1).max(200),
  dueDate: z.coerce.date().optional(),
});
type CreateTask = z.infer<typeof CreateTask>; // { title: string; dueDate?: Date }
```

`CreateTask.safeParse(req.body)` מחזיר `{ success: true, data }` או `{ success: false, error }` – בלי לזרוק שגיאה.

> [!note] TypeScript בודק Types רק בזמן **כתיבה**. ברגע שהקוד רץ, ה-JSON מהרשת יכול להיות כל דבר. לכן צריך Validation **בזמן ריצה** – ו-Zod מחבר בין השניים.

## 2. Error Handling – תשובות שגיאה אחידות

API מקצועי מחזיר שגיאות **באותו מבנה** תמיד, כדי שה-Frontend יוכל לטפל בהן בקוד אחד:

```json מבנה שגיאה אחיד
{ "error": { "code": "VALIDATION_FAILED", "message": "הנתונים לא תקינים", "details": [...] } }
```

| מצב | Status Code |
|---|---|
| קלט לא תקין | `400` (או `422`) |
| לא מחובר / Token לא תקף | `401` |
| מחובר אבל אין הרשאה | `403` |
| לא נמצא | `404` |
| כבר קיים (אימייל תפוס) | `409` |
| יותר מדי בקשות | `429` |
| באג אצלנו | `500` – **בלי** לחשוף פרטים פנימיים |

### Error Middleware מרכזי

במקום `try/catch` בכל Route, זורקים שגיאה עם מחלקה משלך (`AppError`), ו-**Error Middleware** אחד – פונקציה עם **4** פרמטרים `(err, req, res, next)` שנרשמת **אחרונה** – הופך כל שגיאה לתשובה אחידה. שגיאה לא צפויה ← רושמים ללוג את כל הפרטים, ומחזירים ללקוח רק `500` כללי.

> [!warn] לעולם אל תחזיר ללקוח `err.stack` או הודעות של מסד הנתונים. זה מגלה לתוקף מבנה טבלאות, גרסאות ספריות ונתיבי קבצים.

## 3. Authentication מול Authorization

- **Authentication (AuthN)** – **מי אתה?** בודקים סיסמה, Token או Cookie. נכשל ← `401`.
- **Authorization (AuthZ)** – **מה מותר לך?** האם המשימה הזו שייכת לך? האם אתה Admin? נכשל ← `403`.

> [!danger] הבאג הנפוץ ביותר באבטחת API (נקרא **IDOR / BOLA**): בודקים שהמשתמש מחובר, אבל לא בודקים שהמשאב **שייך לו**. משתמש 7 משנה את ה-URL ל-`/api/orders/8` – ורואה הזמנה של מישהו אחר. תמיד: `WHERE id = $1 AND user_id = $2`.

## 4. סיסמאות – Hash, לעולם לא טקסט רגיל

**Hash** היא פונקציה חד-כיוונית: מסיסמה קל לחשב Hash, אבל מה-Hash אי אפשר לשחזר את הסיסמה. בהתחברות מחשבים Hash למה שהמשתמש הקליד ומשווים.

- משתמשים ב-**bcrypt** או **argon2** – אלגוריתמים **איטיים בכוונה** ועם **Salt** (ערך אקראי לכל משתמש), כדי שניחוש מיליוני סיסמאות יהיה יקר מאוד.
- **לא** `md5`/`sha256` לבד – הם מהירים מדי, וזה בדיוק מה שתוקף רוצה.

## 5. Sessions/Cookies מול JWT

| | **Session + Cookie** | **JWT** (JSON Web Token) |
|---|---|---|
| מה הלקוח מחזיק | מזהה אקראי (`sid=abc123`) | Token חתום שמכיל את המידע (`userId`, תפקיד, תפוגה) |

| ניתוק מיידי (Logout) | קל – מוחקים את ה-Session | קשה – ה-Token תקף עד שפג תוקפו |

## 6. סודות ב-Environment Variables

סיסמת ה-DB, המפתח לחתימת JWT ומפתחות API לא נכתבים בקוד ולא נכנסים ל-Git. הם נקראים מ-`process.env`, ובפיתוח – מקובץ `.env` שנמצא ב-`.gitignore`. מומלץ לבדוק אותם עם Zod בעליית השרת: אם חסר משתנה – השרת לא עולה בכלל (עדיף מאשר לקרוס באמצע הלילה).

  }
}

- **`z.object({...}).parse(process.env)`** – בודקים את משתני הסביבה **בעליית השרת**. אם `JWT_SECRET` חסר או קצר מדי – השרת נופל מיד עם הודעה ברורה, במקום לחתום Tokens עם `undefined`.

- **`Credentials.parse(req.body)`** – אם הקלט לא תקין, Zod זורק `ZodError`. אנחנו **לא** תופסים אותו כאן – ה-Error Middleware יטפל. שים לב גם ל-`.toLowerCase()`: `Uri@x.com` ו-`uri@x.com` הם אותו משתמש.
- **`bcrypt.hash(password, 12)`** – 12 הוא ה-**Cost**: כמה "עבודה" לעשות. כל +1 מכפיל את הזמן. ה-Salt נוצר אוטומטית ונשמר בתוך ה-Hash.
- **`bcrypt.compare`** – מחשב Hash לסיסמה שהוקלדה ומשווה. אנחנו אף פעם לא "מפענחים".

- **`requireAuth`** – מוציא את ה-Token מה-Header `Authorization: Bearer ...`, מאמת את החתימה ושם את `userId` ב-`res.locals` לשימוש ה-Handler. נכשל ← `next(error)`, שמעביר ישר ל-Error Middleware.

## למה שרת "עובד" אבל קורס בעומס?

שרת יכול לעבור את כל הבדיקות במחשב שלך ועדיין להתמוטט ביום מבצע בחנות. הסיבה כמעט אף פעם לא "הקוד לא נכון" – אלא **מה קורה כשהרבה דברים קורים בבת אחת, וחלק מהם איטיים או נכשלים**.

### אנלוגיה: מלצר אחד במסעדה עמוסה

ב-Node.js יש **Thread** ראשי אחד שמריץ את הקוד שלך – כמו **מלצר אחד** שמשרת את כל המסעדה.

- מלצר טוב **לוקח הזמנה, מעביר למטבח, וממשיך לשולחן הבא** בזמן שהאוכל מתבשל. זה **Async I/O** – מחכים ל-DB או לרשת בלי לעמוד במקום.
- אבל אם המלצר **עומד ומקלף בעצמו 100 תפוחי אדמה** – כל המסעדה מחכה. זו **עבודת CPU כבדה שחוסמת את ה-Event Loop**.
- אם המטבח לא עונה, מלצר חכם לא מחכה לנצח: אחרי זמן מסוים הוא חוזר ללקוח ("המנה תתעכב") ← **Timeout**.
- אם לקוח קרא "עוד קולה!" פעמיים כי לא שמע תשובה – מלצר טוב לא מביא שתיים ← **Idempotency**.
- ואם המסעדה מלאה, עדיף להגיד בכניסה "יש המתנה של 20 דקות" מאשר להושיב עוד אנשים שלא יקבלו אוכל ← **Load Shedding**.

> [!tip] השיעור הזה הוא מה שמבדיל בין מפתח שבונה API למפתח שבונה API **שמחזיק ב-Production**. אלה בדיוק השאלות שנשאלות בראיונות Senior: "מה קורה אם השירות החיצוני איטי?", "מה אם הלקוח שולח את אותה בקשה פעמיים?".

## 1. ה-Event Loop והשרת שלך

ה-**Event Loop** הוא הלולאה שמריצה את הקוד שלך ב-Node.js. הכלל: **רק דבר אחד רץ בכל רגע**. כשקוד מחכה ל-I/O (DB, רשת, קובץ) עם `await`, ה-Loop חופשי לטפל בבקשות אחרות. לכן שרת Node אחד יכול להחזיק אלפי חיבורים במקביל.

אבל קוד **סינכרוני** וכבד – לולאה על מיליון איברים, `JSON.parse` על קובץ של 50MB, Hash של סיסמה עם `bcrypt.hashSync`, Regex גרוע – **חוסם את כולם**. אם בקשה אחת לוקחת 2 שניות CPU, כל הבקשות האחרות מחכות 2 שניות.

| סוג עבודה | דוגמה | השפעה על השרת |
|---|---|---|
| **I/O** (המתנה) | שאילתה ל-DB, קריאה ל-API | בסדר – ה-Loop משרת אחרים בזמן ההמתנה |
| **CPU** (חישוב) | עיבוד תמונה, הצפנה סינכרונית, לולאה ענקית | חוסם – כל השרת "קופא" |

**פתרונות לעבודת CPU:** פונקציות async (`bcrypt.hash` ולא `hashSync`), **Worker Threads**, או להעביר את העבודה ל-**Queue** ולעבד ברקע (מודול 8).

## 2. Timeouts – לא מחכים לנצח

כל קריאה החוצה (API חיצוני, DB) יכולה להיתקע. בלי Timeout, הבקשות נערמות, החיבורים נגמרים והשרת שלך נופל **בגלל שירות אחר**. ב-Node משתמשים ב-**AbortController** / `AbortSignal.timeout(ms)` כדי לבטל `fetch` שלוקח יותר מדי.

## 3. Retries עם Exponential Backoff + Jitter

חלק מהכשלונות זמניים (`503`, ניתוק רשת). אז מנסים שוב – **אבל בחוכמה**:

- **רק על שגיאות זמניות** – `5xx`, `429`, Timeout. לא על `400`/`404` – הם ייכשלו שוב.
- **Exponential Backoff** – מחכים יותר בכל ניסיון: 200ms, 400ms, 800ms...
- **Jitter** – מוסיפים אקראיות לזמן ההמתנה. אחרת, אם 10,000 לקוחות נכשלו באותה שנייה, כולם ינסו שוב **באותה שנייה בדיוק** ויפילו את השרת מחדש (נקרא **Thundering Herd**).
- **מספר ניסיונות מוגבל** – 3 בדרך כלל, ואז מוותרים.

> [!warn] Retry הופך כל בעיה קטנה לגדולה אם השירות כבר עמוס: 3 ניסיונות = פי 3 עומס. ואם כמה שכבות מנסות שוב (Frontend ← API ← שירות), זה מתכפל: 3×3×3 = 27 בקשות לכל לחיצה.

## 4. Idempotency – למה נוצרות הזמנות כפולות?

**Idempotent** = פעולה שאם מבצעים אותה פעמיים, התוצאה זהה לביצוע אחד. `GET`, `PUT` ו-`DELETE` הם Idempotent מטבעם. **`POST` לא**: שני `POST /orders` = שתי הזמנות.

איך זה קורה בפועל? הלקוח שלח `POST /payments`, השרת **ביצע את החיוב**, אבל התשובה אבדה ברשת (Timeout). מבחינת הלקוח – "נכשל", אז הוא שולח שוב. **התוצאה: חיוב כפול.**

**הפתרון: Idempotency Key.** הלקוח מייצר מזהה ייחודי (UUID) **לכל פעולה** ושולח אותו ב-Header `Idempotency-Key`. ב-Retry הוא שולח **אותו מפתח**. השרת:

1. מנסה "לתפוס" את המפתח – **INSERT לטבלה עם Unique Constraint** על המפתח. זו פעולה **אטומית**: גם אם שתי בקשות זהות מגיעות באותה מילישנייה, רק אחת תצליח.
2. מי שהצליח לתפוס – מבצע את הפעולה ושומר את התשובה ליד המפתח.
3. מי שנכשל (המפתח כבר קיים) – מחזיר את **התשובה השמורה**, או `409` אם הבקשה הראשונה עדיין בעבודה.

> [!danger] הגרסה הנאיבית – "קודם `SELECT` לבדוק אם המפתח קיים, ואם לא – לבצע" – **לא עובדת**. שתי בקשות מקבילות בודקות שתיהן, שתיהן רואות "לא קיים", ושתיהן מבצעות. רק פעולה אטומית (Unique Constraint) פותרת את זה. נעמיק בזה במודול 5.

## 5. Rate Limiting ו-Graceful Degradation

- **Rate Limiting** – מגביל כמה בקשות לקוח יכול לשלוח בחלון זמן (למשל **Token Bucket**: לכל לקוח "דלי" של 100 אסימונים שמתמלא בקצב קבוע). חורג ← `429` + Header `Retry-After`. כשיש כמה שרתים, המונה נשמר במקום משותף כמו **Redis**.
- **Graceful Degradation** – כשתלות לא חיונית נופלת, המערכת ממשיכה **בגרסה מצומצמת**. שירות ההמלצות בחנות לא עונה? מציגים "מוצרים פופולריים" מ-Cache במקום להחזיר שגיאה לכל הדף.

## 6. טיפים של Senior

> [!tip] **Deadline Propagation** – במקום ש"כל שכבה עם Timeout של 30 שניות משלה", מגדירים **תקציב זמן כולל** לבקשה (למשל 2 שניות) ומעבירים אותו הלאה. אם נשארו 300ms, אין טעם לקרוא לשירות שבדרך כלל לוקח 500ms – עדיף להיכשל מהר. ב-Node מעבירים את אותו `AbortSignal` לכל הקריאות בתוך הבקשה.

> [!tip] **Load Shedding** – כשהשרת עמוס (יותר מדי בקשות בטיפול, Event Loop Lag גבוה), הוא **דוחה בקשות חדשות מיד** עם `503 Service Unavailable` + `Retry-After`, במקום לקבל הכל ולהיות איטי לכולם. עדיף ש-10% מהמשתמשים יקבלו "נסה שוב בעוד רגע" מאשר ש-100% יחכו 30 שניות.

> [!note] **Circuit Breaker** – אם שירות חיצוני נכשל שוב ושוב, "מנתקים את המעגל" לזמן קצר ולא שולחים אליו בכלל (נכשלים מיד), ואז בודקים בזהירות אם חזר. זה מגן גם עליך וגם עליו.

// קריאה לשירות חיצוני: Timeout לכל ניסיון + Exponential Backoff עם Jitter
export async function fetchWithRetry(url: string, init: RequestInit, attempts = 3): Promise<Response> {
  for (let attempt = 1; ; attempt++) {
    try {
      const res = await fetch(url, { ...init, signal: AbortSignal.timeout(2000) }); // מקסימום 2 שניות
      if (!isRetryable(res.status) || attempt === attempts) return res; // 4xx לא מנסים שוב
    } catch (err) {
      if (attempt === attempts) throw err; // Timeout או ניתוק רשת – ניסיון אחרון
    }
    const backoff = 200 * 2 ** (attempt - 1);       // 200, 400, 800...
    await sleep(backoff / 2 + Math.random() * backoff / 2); // Jitter: מפזר את הניסיונות
  }
}

// Endpoint עם Idempotency Key – "תפיסה" אטומית בעזרת Unique Constraint ב-DB
app.post('/api/payments', requireAuth, async (req, res) => {

## מה קורה בקוד?

### `fetchWithRetry`
- **`AbortSignal.timeout(2000)`** – יוצר Signal שמבטל את ה-`fetch` אחרי 2 שניות. בלי זה, קריאה תקועה יכולה להחזיק את הבקשה (ואת החיבור) לדקות.
- **`isRetryable`** – מנסים שוב רק על `429` ו-`5xx`. על `400` או `404` אין טעם – הבקשה עצמה שגויה.
- **`catch`** – תופס Timeout ושגיאות רשת. בניסיון האחרון זורקים הלאה כדי שהקורא ידע שנכשלנו.
- **Backoff** – `200 * 2 ** (attempt - 1)` נותן 200, 400, 800 מילישניות.
- **Jitter** – במקום לחכות בדיוק 400ms, מחכים מספר אקראי בין 200 ל-400. כך אלפי לקוחות לא חוזרים באותו רגע.

### Endpoint התשלום
- **`idempotency-key`** – מזהה שהלקוח ייצר. בלעדיו מחזירים `400` – לפעולה רגישה כמו תשלום זה חובה.
- **`INSERT ... ON CONFLICT (key) DO NOTHING RETURNING key`** – הלב של הפתרון. ה-DB מבטיח שרק בקשה אחת תכניס את המפתח. מי שהכניס מקבל שורה בחזרה (`rowCount === 1`); כל השאר מקבלים 0.
- **`status = 'processing'`** – אם בקשה שנייה מגיעה בזמן שהראשונה עוד רצה, היא מקבלת `409` ולא מבצעת שוב.
- **החזרת `response` השמורה** – ב-Retry הלקוח מקבל **בדיוק** את מה שהיה מקבל בפעם הראשונה, כאילו התשובה לא אבדה.
- **`$1`, `$2`** – **Parameterized Queries**, שמגינים מ-SQL Injection (נלמד במודול 5).

> [!warn] מה חסר כאן כדי להיות מושלם: אם השרת קרס **אחרי** החיוב ולפני ה-`UPDATE`, המפתח יישאר `processing` לנצח. בפועל מוסיפים `created_at` ומאפשרים "לתפוס מחדש" מפתח ישן, ומעבירים את מפתח ה-Idempotency גם לספק התשלומים עצמו.

```typescript src/middleware/rateLimit.ts
type Bucket = { tokens: number; updatedAt: number };
const buckets = new Map<string, Bucket>();
const CAPACITY = 10;         // עד 10 בקשות "ברצף"
const REFILL_PER_SEC = 1;    // ואז אסימון אחד לשנייה

export function rateLimit(req: Request, res: Response, next: NextFunction) {
  const id = String(res.locals.userId ?? req.ip);
  const now = Date.now();
  const b = buckets.get(id) ?? { tokens: CAPACITY, updatedAt: now };
  b.tokens = Math.min(CAPACITY, b.tokens + ((now - b.updatedAt) / 1000) * REFILL_PER_SEC); // מילוי לפי הזמן שעבר
  b.updatedAt = now;
  if (b.tokens < 1) {
    buckets.set(id, b);
    res.setHeader('Retry-After', String(Math.ceil((1 - b.tokens) / REFILL_PER_SEC)));
    return res.status(429).json({ error: 'יותר מדי בקשות' });
  }
  b.tokens -= 1;
  buckets.set(id, b);
  next();
}
```
