## למה בכלל צריך React?

במודול 1 בנינו דף עם JavaScript "ידני": מצאנו אלמנט עם `getElementById`, שינינו לו `textContent`, ודאגנו בעצמנו לעדכן כל פיסה במסך. בדף עם כפתור אחד זה עובד. אבל באפליקציה אמיתית – חנות עם עגלה, מסננים, הודעות ומשתמש מחובר – זה הופך מהר מאוד לבלגן: שוכחים לעדכן מקום אחד, והמסך "משקר".

**React** היא ספרייה שמשנה את צורת החשיבה: במקום לתת לדפדפן **הוראות** ("מצא את הכפתור, שנה לו את הטקסט"), אתה **מתאר איך המסך צריך להיראות** לפי המידע שיש לך עכשיו. כשהמידע משתנה, React מחשב מה השתנה ומעדכן את ה-DOM בעצמו.

### אנלוגיה: קוביות LEGO

- כל **Component** (רכיב) הוא **קוביית LEGO**: כפתור, כרטיס מוצר, תפריט.
- מקוביות קטנות בונים קוביות גדולות: `ProductCard` בתוך `ProductList` בתוך `ShopPage`.
- **Props** הם **ההוראות שמדביקים על הקובייה**: "את תהיי כרטיס של מקלדת, במחיר 249". אותה קובייה, נתונים שונים.
- **JSX** הוא **השרטוט** – הדרך לכתוב איך הקובייה נראית, בתחביר שנראה כמו HTML.

> [!tip] React היא הספרייה הנפוצה ביותר לבניית Frontend. כמעט כל משרת Full Stack מבקשת אותה – ואחרי שתבין Components ו-Props, תוכל לקרוא את רוב הקוד של צוותי Frontend.

### מה נלמד בשיעור הזה

איך כותבים Component, מה הכללים של JSX, איך מעבירים מידע עם Props, איך מציגים רשימות ותנאים, ואיך מרכיבים מסך שלם מחלקים קטנים – עם **TypeScript** שמוודא שלא שלחנו נתונים שגויים.

## Component – פונקציה שמחזירה מסך

ב-React מודרני, **Component** הוא פשוט **Function** שמחזירה JSX. שם ה-Component תמיד מתחיל באות גדולה (`ProductCard`, לא `productCard`) – כך React יודע להבדיל בינו לבין תגית HTML רגילה.

```tsx ה-Component הכי פשוט
function Hello() {
  return <h1>שלום, אורי!</h1>;
}
```

ומשתמשים בו כמו בתגית: `<Hello />`.

### JSX – נראה כמו HTML, אבל זה JavaScript

**JSX** הוא תחביר שמאפשר לכתוב "HTML" בתוך קוד TypeScript. מאחורי הקלעים הוא הופך לקריאות פונקציה. בגלל זה יש כמה כללים שונים מ-HTML:

| כלל | ב-HTML | ב-JSX | למה |
|---|---|---|---|
| מחלקת CSS | `class="card"` | `className="card"` | `class` היא מילה שמורה ב-JavaScript |
| הורה אחד | כמה תגיות ברצף | חייבים לעטוף ב-`<div>` או ב-`<>...</>` (**Fragment**) | פונקציה מחזירה ערך אחד |
| ביטויים | אין | `{price * 2}` בתוך סוגריים מסולסלים | כל מה שבתוך `{}` הוא JavaScript |
| תגיות ריקות | `<img>` | `<img />` – חובה לסגור | JSX קפדני יותר |
| אירועים | `onclick="..."` | `onClick={handleClick}` | camelCase ומעבירים **פונקציה**, לא טקסט |

> [!note] בתוך `{}` מותר לשים **ביטוי** (Expression) – משהו שמחזיר ערך: משתנה, חישוב, קריאה לפונקציה, תנאי מקוצר. אסור לשים **פקודה** כמו `if` או `for` ישירות – לשם כך יש טכניקות שנראה מיד.

### Props – מידע שזורם מלמעלה למטה

**Props** (קיצור של Properties) הם הפרמטרים של ה-Component. ה"הורה" מעביר אותם, וה"ילד" מקבל אותם כאובייקט:

```tsx העברת Props
<ProductCard name="מקלדת" price={249} />
```

כללי הזהב:
1. **המידע זורם בכיוון אחד – מלמעלה למטה** (מהורה לילד). זה נקרא **One-Way Data Flow**.
2. **Props הם לקריאה בלבד.** ילד לא משנה את ה-Props שלו – בדיוק כמו שפונקציה לא אמורה לשנות את הפרמטרים שקיבלה.
3. עם TypeScript מגדירים `type` ל-Props, וכך העורך צועק עליך אם שכחת שדה או שלחת טקסט במקום מספר.

### הצגת רשימות עם map ו-key

כדי להציג רשימה, הופכים **Array** של נתונים ל-Array של JSX בעזרת `map`:

```tsx רשימה עם key
{products.map((p) => (
  <ProductCard key={p.id} name={p.name} price={p.price} />
))}
```

ה-**key** הוא "תעודת זהות" לכל פריט ברשימה. כשהרשימה משתנה (מוסיפים, מוחקים, ממיינים), React משתמש ב-key כדי לדעת **איזה פריט הוא איזה**, ולא לבנות הכל מחדש.

> [!warn] אל תשתמש באינדקס (`key={index}`) ברשימה שאפשר למיין או למחוק ממנה. אם פריט 0 נמחק, כל האינדקסים זזים – ו-React עלול "להדביק" את המצב של פריט אחד (למשל טקסט שהוקלד בשדה) לפריט אחר. השתמש במזהה יציב מהנתונים, כמו `id`.

### Conditional Rendering – הצגה לפי תנאי

שלוש דרכים נפוצות:

- **`&&`** – "הצג רק אם": `{inStock && <span>במלאי</span>}`
- **Ternary** (`? :`) – "זה או זה": `{inStock ? 'במלאי' : 'אזל'}`
- **Early return** – בתחילת ה-Component: `if (products.length === 0) return <p>אין מוצרים</p>;`

> [!danger] מלכודת קלאסית: `{items.length && <List />}`. אם האורך הוא `0`, React **מציג את הספרה 0** על המסך. כתוב `{items.length > 0 && <List />}`.

### Composition – הרכבה

הכוח האמיתי הוא **הרכבה**: Components קטנים, כל אחד עם תפקיד אחד, שמורכבים יחד. Prop מיוחד בשם **children** מאפשר להעביר "תוכן פנימי" – כך בונים מעטפות כמו `<Card>...</Card>` או `<Layout>...</Layout>`.

### React מול DOM ידני

| DOM ידני (מודול 1) | React |
|---|---|
| "מצא את האלמנט ושנה אותו" | "כך המסך נראה עבור הנתונים האלה" |
| אתה אחראי לעדכן כל מקום | React מחשב מה השתנה ומעדכן |
| קל לשכוח עדכון | המסך תמיד נגזר מהנתונים |

> [!tip] מה Senior יודע: Component טוב הוא כמו פונקציה טובה – **קטן, עם תפקיד אחד, ו"טהור"** (אותם Props ← אותו JSX). Senior מתכנן קודם את **עץ ה-Components** ואת **זרימת הנתונים** (מי מחזיק מה, מי מקבל מה), ורק אז כותב קוד. הוא גם יודע ש-React משווה את העץ החדש לישן (**Reconciliation**) – ושה-key הוא מה שמאפשר להשוואה הזו להיות נכונה ומהירה.

@@ m6-l1 code tsx | ProductCard ו-ProductList עם Props מוקלדים
// הגדרת הצורה של מוצר – TypeScript ישמור עלינו
type Product = {
  id: number;
  name: string;
  price: number;
  inStock: boolean;
};

// ה-Props של כרטיס אחד
type ProductCardProps = {
  product: Product;
  onAdd: (id: number) => void; // פונקציה שההורה מעביר
};

function ProductCard({ product, onAdd }: ProductCardProps) {
  return (
    <div className="rounded-lg border p-4">
      <h3 className="font-bold">{product.name}</h3>
      <p>₪{product.price.toFixed(2)}</p>
      {product.inStock ? (
        <button onClick={() => onAdd(product.id)}>הוסף לעגלה</button>
      ) : (
        <span className="text-rose-600">אזל מהמלאי</span>
      )}
    </div>
  );
}

type ProductListProps = {
  products: Product[];
  onAdd: (id: number) => void;
};

export function ProductList({ products, onAdd }: ProductListProps) {
  // Early return: אין מה להציג
  if (products.length === 0) {
    return <p>אין מוצרים להצגה</p>;
  }

  return (
    <>
      <h2>{products.length} מוצרים</h2>
      <div className="grid gap-4">
        {products.map((p) => (
          // key יציב מהנתונים – לא האינדקס
          <ProductCard key={p.id} product={p} onAdd={onAdd} />
        ))}
      </div>
    </>
  );
}

## מה קורה בקוד?

- **`type Product`** – מתארים פעם אחת איך נראה מוצר. מעכשיו TypeScript יתריע אם מישהו ינסה להעביר מוצר בלי `price`, או `price` מסוג טקסט.
- **`type ProductCardProps`** – ה-Props של הכרטיס: מוצר אחד ופונקציה `onAdd`. שים לב שהילד **לא יודע** מה קורה כשמוסיפים לעגלה – הוא רק "מודיע" להורה. כך המידע זורם למטה (Props) והאירועים עולים למעלה (Callbacks).
- **`function ProductCard({ product, onAdd })`** – פירוק (Destructuring) של אובייקט ה-Props ישירות בפרמטר. קריא ונוח.
- **`className`** – ולא `class`, כי זה JSX.
- **`{product.price.toFixed(2)}`** – ביטוי JavaScript בתוך `{}`. התוצאה נכנסת לטקסט.
- **Ternary** – אם במלאי מציגים כפתור, אחרת הודעה אדומה.
- **`onClick={() => onAdd(product.id)}`** – מעבירים **פונקציה**. אם היינו כותבים `onClick={onAdd(product.id)}` היא הייתה רצה מיד בזמן הציור, ולא בלחיצה!
- **Early return** ב-`ProductList` – מטפלים במקרה הריק לפני הכל.
- **`<>...</>`** – Fragment: עוטף את הכותרת והרשת בלי להוסיף `div` מיותר ל-DOM.
- **`key={p.id}`** – מזהה יציב לכל פריט, כדי ש-React ידע לעקוב אחריו גם אחרי מיון או מחיקה.

> [!tip] נסה: צור פרויקט עם `npm create vite@latest my-shop -- --template react-ts`, הדבק את הקוד, והעבר ל-`ProductList` מערך של שלושה מוצרים. אחר כך נסה להעביר `price: '249'` (טקסט) – ותראה את TypeScript עוצר אותך עוד לפני שהקוד רץ.

## פתרון לדוגמה

```tsx TaskList.tsx
type Task = { id: string; title: string; done: boolean; priority: 'low' | 'high' };

function Badge({ children }: { children: React.ReactNode }) {
  return <span className="rounded bg-rose-100 px-2 text-rose-700">{children}</span>;
}

function TaskItem({ task }: { task: Task }) {
  return (
    <li className={task.done ? 'line-through text-slate-400' : ''}>
      {task.title} {task.priority === 'high' && <Badge>דחוף</Badge>}
    </li>
  );
}

export function TaskList({ tasks }: { tasks: Task[] }) {
  if (tasks.length === 0) return <p>אין משימות – כל הכבוד! 🎉</p>;

  const doneCount = tasks.filter((t) => t.done).length;

  return (
    <section>
      <h2>
        בוצעו {doneCount} מתוך {tasks.length}
      </h2>
      <ul>
        {tasks.map((t) => (
          <TaskItem key={t.id} task={t} />
        ))}
      </ul>
    </section>
  );
}
```

**מה חשוב כאן:**
- כל Component קטן ועם תפקיד אחד: `Badge` (תווית), `TaskItem` (שורה), `TaskList` (הרשימה).
- `priority: 'low' | 'high'` – TypeScript מונע ערך כמו `'urgent'` בטעות.
- `key={t.id}` ולא אינדקס.
- `task.priority === 'high' && ...` – התנאי מחזיר `true`/`false` ולכן לא תופיע ספרה מוזרה על המסך.
- `Badge` מקבל `children` – דוגמה ל-Composition.

## State – הזיכרון של ה-Component

בשיעור הקודם ה-Components שלנו היו "טיפשים": קיבלו Props והציגו אותם. אבל אפליקציה אמיתית **משתנה**: לוחצים על כפתור, מקלידים בשדה, פותחים תפריט. בשביל זה יש **State** (מצב) – מידע שה-Component **זוכר** ושיכול להשתנות לאורך זמן.

### אנלוגיה: לוח מחיק במטבח

- **Props** הם **מתכון שקיבלת מאמא** – אתה קורא אותו, לא משנה אותו.
- **State** הוא **הלוח המחיק על המקרר** – "נשארו 3 ביצים". כשמשהו משתנה, אתה **מוחק וכותב מחדש**, וכל מי שמסתכל על הלוח רואה את המספר החדש.
- ב-React, כשה-State משתנה, ה-Component **מצויר מחדש** (Re-render) – והמסך מתעדכן אוטומטית.

ובמודול 1, בתרגיל המונה, כתבנו משתנה `count` ופונקציה `render()` שקראנו לה ידנית. **React עושה בדיוק את זה – אבל אוטומטית.**

### Hooks

**Hooks** הם פונקציות מיוחדות שמתחילות ב-`use` ונותנות ל-Component "כוחות": `useState` נותן זיכרון, `useEffect` נותן חיבור לעולם החיצון, ואפשר לכתוב Hooks משלך.

> [!tip] כמעט כל באג ב-React מתחיל בשאלה "איפה ה-State הזה צריך לגור, ומי משנה אותו?". מי ששולט בתשובה לשאלה הזו כותב קוד React יציב.

## useState – צעד אחר צעד

```tsx מונה עם useState
const [count, setCount] = useState(0);
```

- `useState(0)` – "תן לי תא זיכרון שמתחיל ב-0".
- מקבלים **זוג**: הערך הנוכחי (`count`) ופונקציה לשינוי (`setCount`).
- קוראים ל-`setCount(5)` ← React שומר את הערך החדש ← מצייר את ה-Component מחדש ← `count` הוא עכשיו 5.

> [!warn] אל תשנה State ישירות (`count = 5`). React לא ידע שמשהו השתנה ולא יצייר מחדש. **רק דרך פונקציית ה-set.**

### Props מול State

| | Props | State |
|---|---|---|
| מי קובע | ההורה | ה-Component עצמו |
| אפשר לשנות? | לא (קריאה בלבד) | כן, דרך `setX` |
| דוגמה | שם המוצר | האם התפריט פתוח, מה הוקלד בשדה |

### Events ו-Controlled Inputs

אירועים ב-React: `onClick`, `onChange`, `onSubmit`. שדה טופס שבו React הוא "מקור האמת" נקרא **Controlled Input**:

```tsx שדה נשלט
const [email, setEmail] = useState('');
<input value={email} onChange={(e) => setEmail(e.target.value)} />
```

כל הקלדה ← `onChange` ← עדכון State ← ציור מחדש עם הערך החדש. היתרון: הערך תמיד זמין ב-State לבדיקות (למשל "הכפתור פעיל רק אם יש `@`").

### Immutability – לא משנים, מחליפים

React בודק אם State השתנה **בהשוואת הפניה** (Reference): "זה אותו אובייקט או אובייקט חדש?". אם תשנה מערך קיים (`items.push(x)`) ותעביר אותו שוב, React יראה **אותו מערך** – ולא יצייר מחדש.

| ❌ שינוי במקום (Mutation) | ✅ החלפה (Immutable update) |
|---|---|
| `items.push(newItem)` | `setItems([...items, newItem])` |
| `item.done = true` | `setItems(items.map(i => i.id === id ? { ...i, done: true } : i))` |
| `items.splice(idx, 1)` | `setItems(items.filter(i => i.id !== id))` |

> [!tip] כשהערך החדש תלוי בקודם, השתמש בצורת הפונקציה: `setCount(c => c + 1)`. כך אתה תמיד מקבל את הערך העדכני ביותר, גם אם יש כמה עדכונים ברצף.

### Lifting State Up – להרים את ה-State

אם שני Components צריכים את אותו מידע (למשל רשימת מוצרים ומונה העגלה בכותרת), ה-State צריך לגור **בהורה המשותף הקרוב ביותר**. ההורה מעביר את הערך למטה ב-Props, ופונקציות שינוי (Callbacks) כדי שהילדים "יבקשו" שינוי. זה נקרא **Lifting State Up**.

### useEffect – סנכרון עם העולם החיצון

`useEffect` מיועד לדברים **מחוץ ל-React**: טיימר, חיבור WebSocket, שינוי כותרת הלשונית, האזנה לגודל החלון, `localStorage`.

```tsx מבנה של useEffect
useEffect(() => {
  // 1) הפעולה – רצה אחרי שהמסך צויר
  const id = setInterval(tick, 1000);
  // 2) Cleanup – רץ לפני ההפעלה הבאה ובעת הסרת ה-Component
  return () => clearInterval(id);
}, [/* 3) Dependency Array */]);
```

**ה-Dependency Array** קובע מתי ה-Effect רץ:

| מערך | מתי רץ |
|---|---|
| בלי מערך | אחרי **כל** ציור (כמעט אף פעם לא מה שרוצים) |
| `[]` | פעם אחת, כשה-Component מופיע (Mount) |
| `[userId]` | בהופעה, ושוב בכל פעם ש-`userId` משתנה |

**Cleanup Function** – אם פתחת משהו (טיימר, חיבור, מאזין), תסגור אותו. אחרת תקבל **Memory Leak** ומאזינים כפולים.

> [!note] ב-Development, React (במצב StrictMode) מריץ כל Effect **פעמיים** בכוונה – כדי לחשוף Effects בלי Cleanup. אם משהו נשבר בגלל זה, הבאג אמיתי.

### מלכודות נפוצות

- **Infinite loop** – Effect שמעדכן State שנמצא ב-Dependencies שלו (או בלי מערך בכלל): עדכון ← ציור ← Effect ← עדכון...
- **Stale Closure** – פונקציה "זוכרת" ערך ישן של State, כי היא נוצרה בציור קודם. למשל `setInterval(() => setCount(count + 1), 1000)` עם `[]` – `count` תמיד 0. פתרון: `setCount(c => c + 1)`.
- **Effect מיותר** – אם אפשר לחשב ערך מ-State/Props קיימים (כמו `total` מתוך `items`), **פשוט תחשב אותו בזמן הציור**. לא צריך State נוסף ולא Effect.

### Custom Hooks

כשאותה לוגיקה חוזרת בכמה Components, מוציאים אותה ל-**Custom Hook** – פונקציה שמתחילה ב-`use` ומשתמשת ב-Hooks אחרים. בקוד למטה נבנה `useLocalStorage` – כמו `useState`, אבל הערך שורד רענון.

> [!tip] מה Senior יודע: **מינימום State**. כל מה שאפשר לחשב – מחשבים. כל State גר כמה שיותר **נמוך** בעץ (קרוב למי שמשתמש בו), ומורם רק כשצריך לשתף. ו-`useEffect` הוא "פתח מילוט" לעולם החיצון, לא כלי לניהול לוגיקה – Senior שואל לפני כל Effect: "האם יש כאן מערכת חיצונית שצריך לסנכרן איתה?". אם לא – כנראה לא צריך Effect.

import { useEffect, useState } from 'react';

// Custom Hook: כמו useState, אבל נשמר ב-localStorage
export function useLocalStorage<T>(key: string, initial: T) {
  // Lazy initializer: קוראים מ-localStorage רק בציור הראשון
  const [value, setValue] = useState<T>(() => {
    const saved = localStorage.getItem(key);
    return saved !== null ? (JSON.parse(saved) as T) : initial;
  });

  // סנכרון עם העולם החיצון: בכל שינוי – שומרים
  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue] as const;
}

type Todo = { id: string; title: string; done: boolean };

export function TodoApp() {
  const [todos, setTodos] = useLocalStorage<Todo[]>('todos', []);
  const [title, setTitle] = useState(''); // Controlled Input

  function addTodo(e: React.FormEvent) {
    e.preventDefault(); // לא לרענן את הדף
    if (!title.trim()) return;
    // Immutable: מערך חדש, לא push
    setTodos((prev) => [...prev, { id: crypto.randomUUID(), title, done: false }]);
    setTitle('');
  }

  function toggle(id: string) {
    setTodos((prev) => prev.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
  }

  const left = todos.filter((t) => !t.done).length; // ערך מחושב – לא State

  return (
    <form onSubmit={addTodo}>
      <input value={title} onChange={(e) => setTitle(e.target.value)} />
      <button disabled={!title.trim()}>הוסף</button>
      <p>נשארו {left} משימות</p>
      <ul>
        {todos.map((t) => (
          <li key={t.id} onClick={() => toggle(t.id)}>
            {t.done ? '✅' : '⬜'} {t.title}
          </li>
        ))}
      </ul>
    </form>
  );
}

  return <span>🛒 {count}</span>;
}

function CartRow({ item, onChangeQty }: { item: CartItem; onChangeQty: (id: number, delta: number) => void }) {
  return (
    <li>
      {item.name} – {item.qty}
      <button onClick={() => onChangeQty(item.id, +1)}>+</button>
      <button onClick={() => onChangeQty(item.id, -1)}>-</button>
    </li>
  );

export function CartPage() {
  // ה-State "הורם" להורה המשותף של הכותרת ושל הרשימה
  const [items, setItems] = useState<CartItem[]>([
    { id: 1, name: 'מקלדת', price: 249, qty: 1 },
    { id: 2, name: 'עכבר', price: 99, qty: 2 },
  ]);

  function changeQty(id: number, delta: number) {
    setItems((prev) =>
      prev
        .map((i) => (i.id === id ? { ...i, qty: i.qty + delta } : i))
        .filter((i) => i.qty > 0), // כמות 0 = הסרה
    );
  }

  const count = items.reduce((sum, i) => sum + i.qty, 0);
  const total = items.reduce((sum, i) => sum + i.qty * i.price, 0);

  // Effect אמיתי: סנכרון עם העולם החיצון (כותרת הלשונית)
  useEffect(() => {
    document.title = `עגלה (${count})`;

      <CartBadge count={count} />
      <ul>
        {items.map((i) => (

        ))}
      </ul>

    </div>
  );
}

## איך מביאים נתונים מהשרת לתוך React?

עד עכשיו הנתונים שלנו היו "מומצאים" בקוד. באפליקציה אמיתית הם מגיעים מה-**API** שבנינו במודול 4 ומה-**Database** ממודול 5. נשמע פשוט: "תעשה `fetch` ותשים ב-State". בפועל, זה אחד המקומות שבהם הכי הרבה קוד React נשבר.

### אנלוגיה: מקרר משותף במשרד

נתונים מהשרת הם כמו **אוכל במקרר משותף**:
- זה **לא שלך** – מישהו אחר יכול לקחת או להוסיף בכל רגע (משתמש אחר עדכן את ההזמנה).
- מה שראית לפני חמש דקות אולי כבר **לא מעודכן** (Stale).
- לא כדאי לרוץ למקרר בכל פעם שמישהו שואל "יש חלב?" – זוכרים מה ראית (**Cache**), ובודקים שוב מדי פעם.
- כשאתה מוסיף משהו, אתה יכול **לרשום על הלוח מיד** "הבאתי חלב" ולא לחכות שמישהו יאשר (**Optimistic Update**) – אבל אם התברר שהחלב נשפך בדרך, צריך למחוק את מה שרשמת (**Rollback**).

### TanStack Query – המושגים

- **`useQuery`** – קריאת נתונים. מקבל **queryKey** ו-**queryFn**, ומחזיר `data`, `isPending`, `isError`, `error` ועוד.
- **queryKey** – "שם המגירה" ב-Cache, למשל `['orders', { status: 'open' }]`. מפתח שונה = מגירה שונה. כל משתנה שהבקשה תלויה בו **חייב** להיות במפתח.
- **Cache** – התוצאה נשמרת לפי ה-Key. Component אחר שמבקש את אותו Key מקבל אותה מיד, ובקשות זהות מאוחדות לבקשה אחת (**Deduplication**).
- **staleTime** – כמה זמן הנתונים נחשבים "טריים". ברירת המחדל היא `0`: מציגים מיד מה-Cache, ומביאים גרסה טרייה ברקע (**stale-while-revalidate**). עם `staleTime: 30_000` לא תהיה בקשה חוזרת במשך 30 שניות.
- **Refetch אוטומטי** – כשחוזרים ללשונית (`refetchOnWindowFocus`) או כשהרשת חוזרת.
- **`useMutation`** – פעולות כתיבה (POST/PATCH/DELETE). מחזיר `mutate`, `isPending` וכו׳.
- **Invalidation** – אחרי כתיבה מוצלחת אומרים `queryClient.invalidateQueries({ queryKey: ['orders'] })` = "המגירה הזו כבר לא מעודכנת, תביא מחדש".

### Optimistic Updates – לעדכן לפני שהשרת ענה

רגיל: לוחצים "סמן כבוצע" ← מחכים 300ms לשרת ← המסך מתעדכן. **אופטימי**: המסך מתעדכן **מיד**, והבקשה נשלחת ברקע. אם היא נכשלת – **Rollback**.

השלבים עם `useMutation`:
1. **`onMutate`** – מבטלים Queries פעילים (`cancelQueries`) כדי שתשובה ישנה לא תדרוס, שומרים **Snapshot** של המצב הקודם, ומעדכנים את ה-Cache ידנית (`setQueryData`).
2. **`onError`** – מחזירים את ה-Snapshot ומציגים הודעה.
3. **`onSettled`** – בכל מקרה, `invalidateQueries` כדי להסתנכרן עם האמת של השרת.

> [!danger] **מתי לא להשתמש ב-Optimistic Update:** פעולות שיש להן משמעות כספית או בלתי הפיכה – תשלום, העברת כסף, אישור הזמנה, חסימת עסקה חשודה. להציג "התשלום בוצע ✓" ואז לגלות שנכשל זו חוויה גרועה ולפעמים בעיה משפטית. שם מציגים מצב "מעבד..." ומחכים לתשובה אמיתית. Optimistic מתאים לפעולות קטנות והפיכות: לייק, סימון משימה, שינוי סדר.

### ביצועים: Re-renders בקצרה

כל עדכון State מצייר מחדש את ה-Component **ואת כל הילדים שלו**. בדרך כלל זה מהיר מספיק. כשזה לא:

1. **מודדים קודם** – **React DevTools ← Profiler**: מקליטים פעולה ורואים אילו Components צוירו, כמה פעמים ולמה. אל תנחש.
2. **State נמוך** – אם רק שדה החיפוש צריך את הטקסט, שים את ה-State בתוך Component החיפוש, לא בראש הדף. כך הקלדה מציירת מחדש רק אותו.
3. **`memo`** – עוטפים Component ב-`memo(...)` כדי לדלג על ציור אם ה-Props לא השתנו. עובד רק אם ה-Props יציבים – פונקציות ואובייקטים שנוצרים מחדש בכל ציור "שוברים" אותו (לשם כך יש `useCallback`/`useMemo`).
4. **Virtualization** – רשימה של 10,000 שורות? מציגים רק את ה-30 שעל המסך, עם ספרייה כמו **TanStack Virtual**. ה-DOM נשאר קטן והגלילה חלקה.

> [!tip] מה Senior יודע: הוא **מפריד** Server State מ-UI State ולא מערבב אותם. הוא מתכנן **queryKey** כמו שמתכננים API – היררכי ועקבי (`['orders']`, `['orders', id]`) כדי ש-Invalidation של `['orders']` יתפוס את כולם. הוא בוחר Optimistic רק כשהפעולה הפיכה וזולה, ומודד עם Profiler **לפני** שהוא מפזר `memo` בכל מקום.

import { useMutation, useQuery, useQueryClient } from '@tanstack/react-query';

type Task = { id: string; title: string; done: boolean };

async function fetchTasks(): Promise<Task[]> {
  const res = await fetch('/api/tasks');
  if (!res.ok) throw new Error(`שגיאה ${res.status}`); // חשוב: לזרוק כדי ש-isError יעבוד
  return res.json();
}

async function toggleTask(task: Task): Promise<Task> {
  const res = await fetch(`/api/tasks/${task.id}`, {
    method: 'PATCH',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ done: !task.done }),
  });
  if (!res.ok) throw new Error('העדכון נכשל');
  return res.json();
}

export function TaskBoard() {
  const queryClient = useQueryClient();

  const { data: tasks, isPending, isError } = useQuery({
    queryKey: ['tasks'],
    queryFn: fetchTasks,
    staleTime: 30_000, // 30 שניות הנתונים נחשבים טריים
  });

  const toggle = useMutation({
    mutationFn: toggleTask,
    onMutate: async (task) => {
      await queryClient.cancelQueries({ queryKey: ['tasks'] }); // שתשובה ישנה לא תדרוס
      const previous = queryClient.getQueryData<Task[]>(['tasks']); // Snapshot
      queryClient.setQueryData<Task[]>(['tasks'], (old = []) =>
        old.map((t) => (t.id === task.id ? { ...t, done: !t.done } : t)),
      );
      return { previous }; // יגיע ל-onError כ-context
    },
    onError: (_err, _task, context) => {
      queryClient.setQueryData(['tasks'], context?.previous); // Rollback
      alert('לא הצלחנו לשמור – החזרנו את המצב הקודם');
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: ['tasks'] }), // סנכרון עם השרת
  });

  if (isPending) return <p>טוען...</p>;
  if (isError) return <p>משהו השתבש</p>;

  return (
    <ul>
      {tasks.map((t) => (
        <li key={t.id} onClick={() => toggle.mutate(t)}>
          {t.done ? '✅' : '⬜'} {t.title}
        </li>
      ))}
    </ul>
  );
}

- **`onError`** – הבקשה נכשלה: מחזירים את ה-Snapshot (**Rollback**) ומודיעים למשתמש.
- **`onSettled`** – רץ בהצלחה **וגם** בכישלון: `invalidateQueries` מביא את האמת מהשרת, למקרה שמשהו נוסף השתנה.
- **`isPending` / `isError`** – אין צורך ב-`useState` משלנו ל-loading ו-error. הספרייה מנהלת את זה.

> [!note] במשימה זה מתאים: סימון משימה הוא פעולה קטנה והפיכה. בכפתור "שלם עכשיו" היינו משתמשים ב-`toggle.isPending` כדי להציג "מעבד..." ולנטרל את הכפתור – **בלי** עדכון אופטימי.

## פתרון לדוגמה

```tsx Orders.tsx
import { useMutation, useQuery, useQueryClient } from '@tanstack/react-query';
import { useState } from 'react';

type Order = { id: string; customer: string; status: 'open' | 'shipped' };

async function getJson<T>(url: string, init?: RequestInit): Promise<T> {
  const res = await fetch(url, init);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

export function OrdersPage() {
  // UI State – רק של הדפדפן
  const [status, setStatus] = useState<'open' | 'shipped'>('open');
  const queryClient = useQueryClient();

  // Server State – המסנן חלק מה-queryKey!
  const orders = useQuery({
    queryKey: ['orders', { status }],
    queryFn: () => getJson<Order[]>(`/api/orders?status=${status}`),
    staleTime: 10_000,
  });

  // פעולה כספית/תפעולית – בלי Optimistic, מחכים לאישור
  const ship = useMutation({
    mutationFn: (id: string) => getJson<Order>(`/api/orders/${id}/ship`, { method: 'POST' }),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['orders'] }), // תופס את כל המסננים
  });

  return (
    <div>
      <select value={status} onChange={(e) => setStatus(e.target.value as 'open' | 'shipped')}>
        <option value="open">פתוחות</option>
        <option value="shipped">נשלחו</option>
      </select>

      {orders.isPending && <p>טוען...</p>}
      {orders.isError && <p>שגיאה בטעינה</p>}
      <ul>
        {orders.data?.map((o) => (
          <li key={o.id}>
            {o.customer}
            {o.status === 'open' && (
              <button disabled={ship.isPending} onClick={() => ship.mutate(o.id)}>
                {ship.isPending ? 'שולח...' : 'סמן כנשלח'}
              </button>
            )}
          </li>
        ))}
      </ul>
    </div>
  );
}
```

**מה חשוב כאן:**
- `status` הוא **UI State** (`useState`); ההזמנות הן **Server State** (`useQuery`).
- `status` נמצא בתוך ה-`queryKey` – כל מסנן מקבל מגירה משלו ב-Cache, ואין Race Condition: TanStack Query תמיד מציג את התוצאה של ה-Key הנוכחי.
- `invalidateQueries({ queryKey: ['orders'] })` מתאים לכל המפתחות שמתחילים ב-`orders` – גם `open` וגם `shipped`.
- "סמן כנשלח" היא פעולה עם השלכות בעולם האמיתי – לכן בלי Optimistic Update: הכפתור מנוטרל ומציג "שולח..." עד שהשרת מאשר.
