## למה צריך Queue בכלל?

עד עכשיו כל מה שבנינו עבד **Synchronous** (סינכרוני): ה-Client שולח Request, השרת עושה **את כל העבודה**, ורק אז מחזיר Response. זה מצוין כשהעבודה קצרה. אבל מה קורה כשמשתמש נרשם לאתר, ואנחנו צריכים לשלוח לו מייל ברוכים הבאים, ליצור לו תמונת פרופיל, לעדכן מערכת שיווק ולחשב המלצות? אם נעשה את כל זה לפני שנחזיר תשובה – המשתמש יחכה 8 שניות מול מסך טעינה, ואם שירות המיילים נפל, כל ההרשמה תיכשל.

### אנלוגיה: פתק ההזמנה במסעדה

- **המלצר** לוקח ממך הזמנה, כותב **פתק** ותולה אותו על המסילה שמעל המטבח ← זה ה-**Producer** (יצרן ההודעה).
- **המסילה עם הפתקים** ← זה ה-**Queue** (תור).
- **הטבחים** מורידים פתק אחד בכל פעם ומכינים את המנה ← אלה ה-**Consumers** (צרכנים), שנקראים גם **Workers**.

המלצר **לא עומד ליד הכיריים** ומחכה שהסטייק יהיה מוכן. הוא אומר לך "ההזמנה התקבלה" וממשיך לשולחן הבא. אם יש עומס – הפתקים מצטברים על המסילה, ואף הזמנה לא הולכת לאיבוד. אם צריך לעבוד מהר יותר – מוסיפים טבח. זו בדיוק עבודה **Asynchronous** (אסינכרונית): "קיבלתי, אטפל בזה בקרוב".

> [!tip] השאלה שמפתחים מנוסים שואלים על כל פעולה: "האם המשתמש **חייב** לחכות לתוצאה הזו כדי להמשיך?" אם לא – זו מועמדת מצוינת ל-Queue.

### למה זה חשוב לך?

מערכות אמיתיות – תשלומים, התראות, זיהוי עסקאות חשודות – בנויות סביב **Events** ו-**Queues**. זה מה שמאפשר להן לעמוד בעומסים, לשרוד נפילה של שירות אחד, ולהוסיף יכולות חדשות בלי לגעת בקוד הקיים. בשיעור הזה נבין את אבני הבניין, נכיר את Kafka, RabbitMQ ו-BullMQ, ונכתוב Producer ו-Worker אמיתיים.

## אבני הבניין

| מונח | מה זה בשפה פשוטה |
|---|---|
| **Message** (הודעה) | חבילת מידע קטנה, בדרך כלל JSON: "משתמש 42 נרשם" |
| **Producer** | הקוד ששולח הודעות (למשל ה-API שלך אחרי הרשמה) |
| **Queue** | "מסילת הפתקים" – שומרת הודעות עד שמישהו מטפל בהן. כל הודעה הולכת ל-Consumer **אחד** |
| **Topic** | "ערוץ" של אירועים מסוג מסוים (`user.registered`). **כמה** קבוצות Consumers יכולות לקרוא את אותו אירוע |
| **Consumer / Worker** | הקוד שמקבל הודעות ומבצע את העבודה |
| **Broker** | השרת שמנהל את התורים: Kafka, RabbitMQ, Redis |

### Sync מול Async – צעד אחר צעד

**בלי Queue:** `POST /signup` ← שמירה ב-DB ← שליחת מייל (2 שניות) ← יצירת תמונה (3 שניות) ← Response. המשתמש מחכה 5+ שניות, ונפילה של שירות המייל מפילה את ההרשמה.

**עם Queue:** `POST /signup` ← שמירה ב-DB ← שליחת הודעה ל-Queue (5 מילישניות) ← Response `201`. ברקע, Worker לוקח את ההודעה ושולח את המייל. אם שירות המייל נפל, ה-Worker ינסה שוב בעוד דקה – וההרשמה כבר הצליחה.

### Event מול Command

זו הבחנה שמראיינים אוהבים:

- **Command** (פקודה) – "תעשה משהו": `SendWelcomeEmail`. יש לה **נמען אחד** שאחראי לבצע. שם בציווי.
- **Event** (אירוע) – "משהו כבר קרה": `UserRegistered`. השולח **לא יודע ולא אכפת לו** מי מאזין. שם בזמן עבר.

> [!example] בחנות אונליין: השירות שמטפל בהזמנות מפרסם Event בשם `OrderPlaced`. שירות המלאי מוריד כמויות, שירות ההתראות שולח SMS, ושירות זיהוי ההונאות בודק את העסקה. מחר מוסיפים שירות נקודות נאמנות – **בלי לשנות שורה** בשירות ההזמנות. זה נקרא **Fan-out**: אירוע אחד, הרבה צרכנים.

### Kafka – היסודות

**Kafka** הוא לא "תור" רגיל אלא **Log** (יומן) שאליו רק מוסיפים בסוף. הודעות לא נמחקות כשקוראים אותן.

1. **Topic** – יומן בשם מסוים, למשל `payments`.
2. **Partition** – כל Topic מחולק לכמה "מסילות" מקבילות. כך אפשר לעבד במקביל.
3. **Key** – לכל הודעה אפשר לתת מפתח (למשל `userId`). הודעות עם **אותו Key** תמיד נוחתות **באותו Partition**, ולכן נשמר ביניהן **סדר**. בין Partitions שונים אין הבטחת סדר.
4. **Offset** – המספר הסידורי של הודעה בתוך Partition. כל Consumer זוכר "עד איפה קראתי".
5. **Consumer Group** – קבוצת Workers שמתחלקים בעבודה: כל Partition שייך ל-Worker אחד בקבוצה. שתי קבוצות שונות (למשל `emails` ו-`fraud`) מקבלות **כל אחת** את כל ההודעות – זה ה-Fan-out.
6. **Retention** – Kafka שומר הודעות לזמן מוגדר (למשל 7 ימים) גם אחרי שנקראו. לכן אפשר לעשות **Replay**: להחזיר את ה-Offset אחורה ולעבד מחדש, למשל אחרי תיקון באג.

> [!note] מספר ה-Workers האפקטיבי בקבוצה מוגבל למספר ה-Partitions. Topic עם 6 Partitions ו-10 Workers – ארבעה Workers יישבו בטלים.

### Kafka מול RabbitMQ מול BullMQ

| | **Kafka** | **RabbitMQ** | **BullMQ** (על Redis) |
|---|---|---|---|
| מודל | Log מתמשך עם Replay | Message Broker קלאסי עם Routing | תור Jobs ל-Node.js |
| אחרי קריאה | ההודעה נשארת (Retention) | ההודעה נמחקת אחרי Ack | ה-Job מסומן כהושלם |
| חוזקה | נפחים עצומים, סדר לפי Key, הרבה צרכנים | ניתוב גמיש, תורים לכל מטרה | פשוט, Retries, Delays, Cron מובנים |
| מתאים ל | Event Streaming בין שירותים | משימות ותקשורת בין שירותים | Background Jobs באפליקציה אחת |
| מורכבות תפעול | גבוהה | בינונית | נמוכה (רק Redis) |

### מתי **לא** להשתמש ב-Queue

- כשהמשתמש **חייב** את התשובה עכשיו (למשל "האם הסיסמה נכונה?").
- כשהעבודה לוקחת 20 מילישניות – Queue רק מוסיף מורכבות.
- כשאין לך עדיין דרך לנטר תורים: תור שמתמלא בשקט הוא באג שמתגלה אחרי שבוע.

> [!tip] מה Senior יודע: Queue לא "מעלים" עבודה – הוא **דוחה** אותה. צריך לנטר את **Queue Lag** (כמה הודעות מחכות וכמה זמן), להגביל קצב, ולתכנן מה קורה כשהעבודה נכשלת. על זה בדיוק השיעור הבא.

@@ m8-l1 code typescript | producer.ts – ה-API מכניס Job לתור
import { Queue } from 'bullmq';

// חיבור ל-Redis – BullMQ שומר שם את התורים
const connection = { host: process.env.REDIS_HOST ?? 'localhost', port: 6379 };

// התור שלנו – "מסילת הפתקים" של המיילים
export const emailQueue = new Queue('emails', { connection });

interface WelcomeEmailJob {
  userId: string;
  email: string;
  name: string;
}

// נקרא מתוך POST /signup, אחרי שהמשתמש נשמר ב-DB
export async function enqueueWelcomeEmail(data: WelcomeEmailJob) {
  await emailQueue.add('send-welcome-email', data, {
    jobId: `welcome-${data.userId}`, // אותו userId = אותו Job, גם אם נקרא פעמיים
    attempts: 5, // עד 5 ניסיונות
    backoff: { type: 'exponential', delay: 2000 }, // 2s, 4s, 8s, 16s...
    removeOnComplete: 1000, // לא לנפח את Redis
    removeOnFail: 5000, // שומרים כישלונות לחקירה
  });
}

@@ m8-l1 code typescript | worker.ts – תהליך נפרד שמבצע את העבודה
import { Worker, Job } from 'bullmq';
import { sendEmail } from './email-provider';

const connection = { host: process.env.REDIS_HOST ?? 'localhost', port: 6379 };

const worker = new Worker(
  'emails',
  async (job: Job) => {
    if (job.name !== 'send-welcome-email') return;
    const { email, name } = job.data;

    // אם זה זורק שגיאה – BullMQ ינסה שוב לפי attempts/backoff
    await sendEmail({
      to: email,
      subject: 'ברוך הבא!',
      text: `שלום ${name}, שמחים שהצטרפת.`,
    });
  },
  { connection, concurrency: 5 }, // עד 5 מיילים במקביל ב-Worker הזה
);

worker.on('completed', (job) => console.log(`✓ job ${job.id} done`));
worker.on('failed', (job, err) => {
  console.error(`✗ job ${job?.id} attempt ${job?.attemptsMade} failed: ${err.message}`);
});

// כיבוי מסודר: מסיימים את ה-Jobs הנוכחיים לפני יציאה
process.on('SIGTERM', async () => {
  await worker.close();
  process.exit(0);
});

## הסבר הקוד

**producer.ts** – רץ בתוך שרת ה-API:

- **`new Queue('emails', { connection })`** – יוצר (או מתחבר ל-) תור בשם `emails` שנשמר ב-Redis. ה-Producer וה-Worker צריכים להסכים על השם.
- **`emailQueue.add(name, data, options)`** – מוסיף **Job** לתור. `data` חייב להיות JSON פשוט (בלי Functions או Class instances).
- **`jobId`** – מזהה ייחודי שאנחנו קובעים. אם בטעות נקרא לפונקציה פעמיים לאותו משתמש, BullMQ יתעלם מהכפילות. זו הצצה ראשונה ל-**Idempotency**.
- **`attempts` + `backoff`** – אם ה-Worker נכשל, BullMQ ינסה שוב, וכל פעם יחכה פי שניים. כך לא "מפציצים" שירות שכבר מתקשה.

**worker.ts** – תהליך **נפרד** (מריצים אותו עם `node worker.js` בנוסף לשרת):

- **`new Worker('emails', handler)`** – מאזין לתור. לכל Job מריץ את ה-handler. אם ה-handler מסתיים בהצלחה – ה-Job מסומן `completed`; אם הוא זורק – `failed` וינוסה שוב.
- **`concurrency: 5`** – כמה Jobs במקביל. רוצים יותר? מריצים עוד עותקים של ה-Worker – בדיוק כמו להוסיף טבח.
- **`SIGTERM`** – כשמכבים את התהליך (למשל ב-Deploy), `worker.close()` מחכה שה-Jobs הנוכחיים יסתיימו. בלי זה, מייל יכול להישלח באמצע ולהישלח שוב.

> [!note] שים לב שה-API לא מחכה למייל בכלל: הוא מחזיר תשובה מיד אחרי `add`, שלוקח כמה מילישניות.

## פתרון לדוגמה

**1. מה נכנס ל-Queue ומה לא:**

| פעולה | Sync או Async? | למה |
|---|---|---|
| בדיקת מלאי ושמירת ההזמנה | **Sync** | המשתמש חייב לדעת שההזמנה נקלטה |
| חיוב כרטיס אשראי | **Sync** (בדרך כלל) | צריך להגיד למשתמש אם התשלום עבר |
| מייל אישור הזמנה | **Async** | אפשר שיגיע תוך דקה |
| הפקת חשבונית PDF | **Async** | איטי, ולא חוסם את המשתמש |
| עדכון מערכת המלצות | **Async** | לא קריטי בכלל לזמן אמת |

**2. Event ולא Command:** אחרי שמירת ההזמנה מפרסמים Event אחד, `OrderPlaced`, עם `orderId`, `userId`, `total`, `items`. שלושה Consumers עצמאיים מאזינים לו: `emails`, `invoices`, `recommendations`. שירות ההזמנות לא מכיר אף אחד מהם.

**3. איזה כלי:** אם זו אפליקציית Node.js אחת – **BullMQ** מספיק בהחלט: שלושה תורים או Worker אחד שמפרסם לשלושה תורים. אם יש כמה שירותים נפרדים, צוותים שונים, ורצון לעשות Replay – **Kafka** עם Topic `orders` ו-Key = `orderId`, ושלוש Consumer Groups.

## מה קורה כשמשהו נכשל באמצע?

בשיעור הקודם ה-Worker שלח מייל. עכשיו נשאל את השאלה שמבדילה בין קוד דמו לקוד Production: **מה קורה כשמשהו נכשל?** ה-Worker קרס באמצע. שירות המייל החזיר שגיאה. הרשת נותקה בדיוק אחרי שהמייל נשלח, אבל לפני שסימנו "בוצע". במערכות אסינכרוניות זה לא "אם" – זה "מתי".

### אנלוגיה: שליח חבילות

שליח מגיע לדלת שלך עם חבילה. הוא צריך את החתימה שלך כדי לסמן "נמסר".

- אם הוא **לא** מקבל חתימה (לא היית בבית, או שהמכשיר שלו נכבה) – הוא **יבוא שוב מחר**. זה **Retry**.
- אבל מה אם השארת לו פתק "תשאיר ליד הדלת", הוא השאיר, והמכשיר נכבה לפני שסימן? הוא יבוא שוב מחר עם **אותה חבילה**. אתה צריך להיות חכם מספיק לומר "את זו כבר קיבלתי" – זה **Idempotency**.
- ואם הכתובת פשוט לא קיימת? אחרי חמישה ניסיונות הוא לא ינסה לנצח – החבילה עוברת ל**מחסן חבילות בעייתיות** שבו בן אדם בודק מה קרה. זה ה-**Dead Letter Queue**.

### למה זה חשוב לך?

במערכת תשלומים, "שלחנו פעמיים" אומר **חיוב כפול** ללקוח, ו"פספסנו פעם" אומר **עסקה חשודה שלא נבדקה**. הכללים בשיעור הזה – At-Least-Once, Idempotent Consumer, Retries עם Backoff ו-DLQ – הם מהדברים הראשונים שבודקים בראיון למשרת Backend בכירה.

## שלוש הבטחות מסירה

כל מערכת הודעות נותנת אחת משלוש הבטחות. ההבדל הוא **מתי מסמנים "טיפלתי"** (Ack / Commit):

| הבטחה | מתי מסמנים | מה יכול לקרות | מתי מתאים |
|---|---|---|---|
| **At-Most-Once** | **לפני** העיבוד | Crash באמצע ← ההודעה **אבדה** | מדדים לא חשובים, לוגים |
| **At-Least-Once** | **אחרי** העיבוד | Crash אחרי העיבוד ולפני הסימון ← ההודעה **תגיע שוב** | ברירת המחדל הנכונה כמעט תמיד |
| **Exactly-Once** | "בדיוק פעם אחת" | קיים רק בתוך גבולות המערכת | ראה בהמשך |

> [!warn] "Exactly-Once" הוא מונח מטעה. Kafka יכול להבטיח זאת **בתוך Kafka** (קריאה מ-Topic וכתיבה ל-Topic אחר בטרנזקציה). אבל ברגע שהעיבוד שלך נוגע במערכת חיצונית – שולח מייל, מחייב כרטיס, כותב ל-PostgreSQL – אין Broker שיכול להבטיח את זה. הדרך היחידה היא **At-Least-Once + Idempotent Consumer** = "**Effectively-Once**".

## Commit אחרי העיבוד

ב-Kafka ה-Consumer שומר **Offset** – "עד איפה קראתי". ברירת המחדל של הרבה ספריות היא Auto-Commit כל כמה שניות, וזה מסוכן: ה-Offset עלול להישמר לפני שסיימת לעבד. הכלל:

1. קרא הודעה.
2. עבד אותה **עד הסוף** (כולל כתיבה ל-DB).
3. רק אז **Commit** ל-Offset הבא (`offset + 1`).

## Idempotent Consumer

**Idempotent** = לבצע פעולה פעמיים נותן את אותה תוצאה כמו לבצע פעם אחת. הדרך הנפוצה: לכל Event יש `eventId` ייחודי, ושומרים טבלה של אירועים שכבר עובדו:

```sql טבלת אירועים שעובדו
CREATE TABLE processed_events (
  consumer   TEXT        NOT NULL,
  event_id   UUID        NOT NULL,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer, event_id)
);
```

בתוך **אותה Transaction** של העבודה עצמה:

1. `INSERT INTO processed_events ... ON CONFLICT DO NOTHING`.
2. אם לא נוספה שורה – כבר טיפלנו. מדלגים.
3. אם נוספה – מבצעים את העבודה ועושים `COMMIT`.

כך העבודה והסימון "בוצע" נשמרים יחד – או ששניהם קרו, או ששניהם לא.

> [!tip] לפעולות מול שירות חיצוני (למשל ספק תשלומים) שולחים **Idempotency Key** – בדרך כלל ה-`eventId`. רוב ספקי התשלומים תומכים בזה בדיוק בשביל המקרה הזה.

## Retries עם Exponential Backoff

כשלים מתחלקים לשני סוגים:

- **Transient** (זמני) – Timeout, `503`, נעילה ב-DB. **שווה לנסות שוב.**
- **Permanent** (קבוע) – JSON שבור, שדה חובה חסר, משתמש שנמחק. **לנסות שוב זה בזבוז.**

לכשלים זמניים מנסים שוב עם **Exponential Backoff**: 1 שנייה, 2, 4, 8... ומוסיפים **Jitter** (רעש אקראי קטן), כדי שאלף Workers לא ינסו שוב באותה מילישנייה בדיוק. ותמיד מגבילים את מספר הניסיונות.

## Poison Message ו-Dead Letter Queue

**Poison Message** (הודעה מורעלת) היא הודעה שתמיד תיכשל. ב-Kafka, אם לא מטפלים בה, ה-Consumer ינסה אותה לנצח וכל ה-Partition **ייתקע** מאחוריה – אלפי הודעות תקינות מחכות.

הפתרון: אחרי N ניסיונות, מעבירים את ההודעה ל-**DLQ** (Dead Letter Queue) – Topic או תור נפרד – ועושים Commit כדי להמשיך.

**מה שומרים ב-DLQ:**
- את ההודעה המקורית, בלי שינוי.
- מאיפה הגיעה: Topic, Partition, Offset.
- הודעת השגיאה, מספר הניסיונות והזמן.

**ומה עושים איתו:**
- **Alerting** – התראה כשה-DLQ לא ריק. DLQ שאף אחד לא מסתכל עליו הוא פח זבל.
- **Redrive** – אחרי שתיקנו את הבאג, מחזירים את ההודעות מה-DLQ ל-Topic המקורי לעיבוד מחדש. זה בטוח רק כי ה-Consumer **Idempotent**.

> [!tip] מה Senior יודע: מודדים **Consumer Lag** (כמה הודעות מחכות) ו-**DLQ size**, מגדירים להם התראות, וכותבים Runbook קצר: "DLQ התמלא ← בודקים שגיאה ← מתקנים ← Redrive". זה ההבדל בין מערכת שנראית עובדת למערכת שבאמת אמינה.

          });

## איך מחלקים מערכת גדולה לחלקים?

כשמערכת גדלה, הצוות גדל איתה. פתאום 30 מפתחים עובדים על אותו קוד, כל Deploy מפחיד, ושינוי קטן במודול התשלומים שובר את מסך ההתראות. כאן נכנסת המילה שכולם אוהבים להגיד: **Microservices**.

### אנלוגיה: מסעדה קטנה מול רשת מסעדות

**Monolith** (מונוליט) הוא מסעדה אחת עם מטבח אחד. כולם רואים את כולם, קל לתאם, ושינוי בתפריט קורה תוך שעה. **Microservices** הם רשת שבה לכל מטבח – מאפייה, קצביה, קונדיטוריה – יש צוות משלו, ספק משלו ושעות פתיחה משלו. כל אחד יכול לגדול לבד, אבל עכשיו צריך **חוזים** ("כל יום ב-6 בבוקר מגיעות 200 לחמניות בקרטון הזה") ו**לוגיסטיקה** בין הסניפים. אם הקונדיטוריה משנה בלי להודיע את גודל הקרטון – המשאית לא נסגרת.

### מה נלמד?

- מתי Microservices שווים את המחיר, ולמה כמעט תמיד מתחילים מ-**Modular Monolith**.
- איך מגדירים **Contracts** (חוזים) ל-Events כך ששינוי בשירות אחד לא שובר אחר.
- **Dual-Write Problem** – הבאג השקט שמחכה לכל מי ששומר ב-DB ושולח ל-Kafka באותה פונקציה – והפתרון: **Transactional Outbox**.
- **Choreography** מול **Orchestration** לתהליכים שעוברים בין כמה שירותים.

> [!tip] בראיונות לתפקידים בכירים, "למה **לא** הייתי מפצל לשירותים" היא תשובה חזקה בדיוק כמו "איך הייתי מפצל". מראיינים מחפשים שיקול דעת, לא באזוורדס.

### כללי Versioning ו-Backward Compatibility

- ✅ **מותר:** להוסיף שדה **אופציונלי** חדש. Consumers ישנים פשוט מתעלמים ממנו.

## The Dual-Write Problem

```typescript הבאג השקט
await db.query('INSERT INTO payments ...'); // 1. נשמר
await kafka.send({ topic: 'payments', ... }); // 2. השרת קרס כאן? ה-Event לא נשלח לעולם
```

כתיבה לשתי מערכות שונות (DB ו-Broker) **אינה אטומית**. אם התהליך קורס בין שתי השורות – התשלום קיים, אבל שירות זיהוי ההונאות לא שמע עליו מעולם. להפוך את הסדר לא עוזר: אז ה-Event נשלח על תשלום שאולי לא נשמר.

## הפתרון: Transactional Outbox

1. באותה **DB Transaction** שבה שומרים את התשלום, מכניסים שורה לטבלת `outbox` עם ה-Event.
2. Transaction אחת = או ששניהם נשמרו או אף אחד.
3. תהליך נפרד – **Relay** – קורא שורות שעוד לא פורסמו, שולח אותן ל-Kafka, ומסמן `published_at`.
4. אם ה-Relay קורס אחרי השליחה ולפני הסימון – ה-Event יישלח שוב. זה **At-Least-Once**, ולכן ה-Consumers חייבים להיות **Idempotent** (שיעור קודם). הכל מתחבר.

> [!note] במקום Relay שעושה Polling, אפשר להשתמש ב-**CDC** (Change Data Capture, למשל Debezium) שקורא את ה-WAL של PostgreSQL ומפרסם שינויים. אותו רעיון, פחות עומס על ה-DB.

## Choreography מול Orchestration (Saga)

תהליך כמו "הזמנה ← תשלום ← מלאי ← משלוח" עובר בין שירותים, ואין Transaction אחת שעוטפת הכל. לכן משתמשים ב-**Saga**: רצף צעדים מקומיים, ולכל צעד יש **Compensation** (פעולה מתקנת – למשל "החזר כספי") אם צעד מאוחר יותר נכשל.

- **Choreography** – אין מנהל. כל שירות מאזין ל-Events ומפרסם Events משלו. פשוט ומנותק, אבל קשה לראות את התהליך המלא.
- **Orchestration** – שירות **Orchestrator** אחד שולח Commands לכל שירות ועוקב אחרי מצב התהליך. ברור יותר ונוח לניטור, אבל יש רכיב מרכזי.

> [!tip] מה Senior יודע: 2–3 צעדים – Choreography. תהליך ארוך עם הרבה מקרי קצה ו-Compensations – Orchestration (לפעמים עם כלי Workflow ייעודי). ובכל מקרה: Outbox לפרסום, Idempotency בצריכה, ו-Schema מוגדר לכל Event.

import { Kafka } from 'kafkajs';
import { Pool } from 'pg';

const db = new Pool({ connectionString: process.env.DATABASE_URL });
const producer = new Kafka({ clientId: 'outbox-relay', brokers: ['localhost:9092'] }).producer();
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

async function publishBatch(): Promise<number> {
  const client = await db.connect();
  try {
    await client.query('BEGIN');
    // SKIP LOCKED: כמה Relays יכולים לרוץ במקביל בלי לקחת את אותן שורות
    const { rows } = await client.query(
      `SELECT id, event_id, topic, message_key, payload
         FROM outbox
        WHERE published_at IS NULL
        ORDER BY id
        LIMIT 100
        FOR UPDATE SKIP LOCKED`,
    );
    for (const row of rows) {
      await producer.send({
        topic: row.topic,
        messages: [{
          key: row.message_key,
          value: JSON.stringify({ eventId: row.event_id, ...row.payload }),
        }],
      });
      await client.query('UPDATE outbox SET published_at = now() WHERE id = $1', [row.id]);
    }
    await client.query('COMMIT');
    return rows.length;
  } catch (err) {
    await client.query('ROLLBACK'); // השורות יישלחו שוב בסבב הבא (At-Least-Once)
    throw err;
  } finally {
    client.release();
  }
}

await producer.connect();
while (true) {
  try {
    const sent = await publishBatch();
    if (sent === 0) await sleep(500); // אין עבודה – מחכים קצת
  } catch (err) {
    console.error('outbox relay error', err);
    await sleep(2000);
  }
}

## הסבר הקוד

**קובץ ה-SQL:**

- **`outbox`** היא טבלה רגילה ב-PostgreSQL, באותו DB של התשלומים. לכן אפשר לכתוב אליה **באותה Transaction**.
- **`event_id UNIQUE`** – המזהה שה-Consumers ישתמשו בו ל-Idempotency.
- **`message_key`** – יהפוך ל-Key ב-Kafka. כל ה-Events של אותו משתמש ינחתו באותו Partition, בסדר הנכון.
- **`published_at`** – `NULL` אומר "עוד לא נשלח". ה-**Partial Index** מכיל רק שורות כאלה, כך שהחיפוש נשאר מהיר גם כשהטבלה ענקית.
- **`BEGIN ... COMMIT`** – הלב של הדפוס: התשלום וה-Event נשמרים יחד או לא נשמרים בכלל. אין יותר מצב ביניים.

**ה-Relay:**

- **`FOR UPDATE SKIP LOCKED`** – נועל את השורות שנבחרו ומדלג על שורות שתהליך אחר כבר נעל. כך אפשר להריץ שני Relays לזמינות גבוהה בלי שליחה כפולה רגילה.
- **`ORDER BY id`** – שולחים בסדר שבו ה-Events נוצרו.
- **שליחה ואז `UPDATE`** – אם `producer.send` הצליח אבל ה-`COMMIT` נכשל, השורה תישלח שוב. זה At-Least-Once מכוון – ה-Consumers מטפלים בכפילויות לפי `eventId`.
- **הלולאה** – כשאין עבודה ישנים חצי שנייה; כשיש שגיאה ישנים יותר. בנוסף כדאי למחוק או לארכב שורות ישנות שכבר פורסמו (למשל כל לילה).
