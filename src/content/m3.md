## הכלים שכל מפתח משתמש בהם כל יום

עד עכשיו כתבנו קוד ב-Console של הדפדפן. אבל פרויקט אמיתי חי **על המחשב שלך**: תיקיות, קבצים, ספריות קוד של אחרים, ופקודות שמריצות הכל. הכלי המרכזי לזה הוא ה-**Terminal**.

### אנלוגיה: מטבח של מסעדה

- **Terminal** (מסוף) = **לדבר ישירות עם השף** במקום להצביע על תמונות בתפריט. במקום ללחוץ על אייקונים, אתה **כותב פקודה** – וזה הרבה יותר מהיר ומדויק.
- **Node.js** = **המטבח עצמו** – המקום שבו מתכוני JavaScript מבושלים מחוץ לדפדפן.
- **npm** = **הספק** שמביא מצרכים מוכנים (**Packages**): לא טוחנים קמח לבד – קונים שק מוכן.
- **package.json** = **רשימת הקניות והמתכונים** של הפרויקט: אילו מצרכים צריך, ואיך מבשלים (`npm run dev`).
- **`.env`** = **הכספת של המסעדה** – קוד האזעקה והסיסמאות. לא תולים אותה על הקיר בכניסה.

> [!tip] בהתחלה ה-Terminal נראה מפחיד – מסך שחור עם סמן מהבהב. אחרי שבוע תרגיש בו כמו בבית, ואחרי חודש לא תבין איך עבדת בלעדיו. כל מפתח Senior חי בתוכו.

### למה זה חשוב לך?

כל פרויקט מתחיל ב-`npm install` ו-`npm run dev`. כל שרת בענן (מודול 10) הוא בעצם Terminal בלי מסך. ומה שהכי חשוב: הבנה של `package.json`, גרסאות ומשתני סביבה מונעת את רוב הבעיות מסוג "אצלי זה עובד".

## 1. Terminal ו-Shell

ה-**Terminal** הוא החלון. ה-**Shell** הוא התוכנה שבתוכו שמבינה את הפקודות. ב-Mac וב-Linux זה בדרך כלל **bash** או **zsh**. ב-Windows יש **PowerShell** (וגם אפשר להתקין Git Bash או WSL שמדמים Linux). ב-VS Code פותחים Terminal מובנה מהתפריט **Terminal ← New Terminal** (או בקיצור Ctrl + המקש שמעל Tab).

### פקודות בסיס

| פקודה | מה עושה | ב-PowerShell |
|---|---|---|
| `pwd` | איפה אני עכשיו? (Print Working Directory) | `pwd` / `Get-Location` |
| `ls` | מה יש בתיקייה הזו? | `ls` / `dir` |
| `cd my-app` | כניסה לתיקייה | זהה |
| `cd ..` | חזרה תיקייה אחת למעלה | זהה |
| `mkdir my-app` | יצירת תיקייה | זהה |
| `code .` | פתיחת התיקייה הנוכחית ב-VS Code | זהה |
| `clear` | ניקוי המסך | `cls` / `clear` |

> [!tip] מקש **Tab** משלים שמות של קבצים ותיקיות, וחץ **למעלה** מחזיר את הפקודה הקודמת. שני המקשים האלה לבד חוסכים שעות.

## 2. Node.js – JavaScript מחוץ לדפדפן

**Node.js** הוא תוכנה שמריצה JavaScript **על המחשב או השרת** – בלי דפדפן. זה מה שמאפשר לכתוב Backend ב-JavaScript/TypeScript (מודול 4). בודקים שהוא מותקן עם `node -v`, ומריצים קובץ עם `node app.js`.

## 3. npm – מנהל החבילות

**npm** (Node Package Manager) מגיע עם Node.js ומאפשר להוריד **Packages** – קוד שאנשים אחרים כתבו ופרסמו (יש מעל 2 מיליון!).

| פקודה | מה עושה |
|---|---|
| `npm init -y` | יוצר `package.json` חדש לפרויקט |
| `npm install zod` | מוריד את zod ומוסיף אותו ל-`dependencies` |
| `npm install -D vitest` | מוסיף ל-`devDependencies` (רק לפיתוח) |
| `npm install` | מתקין את **כל** מה שרשום ב-`package.json` |
| `npm run dev` | מריץ את הסקריפט `dev` מתוך `package.json` |
| `npx tsc --init` | מריץ כלי בלי להתקין אותו גלובלית |

### package.json – הלב של הפרויקט

- **`dependencies`** – מה שהאפליקציה צריכה **כדי לרוץ** בפרודקשן (react, zod, express).
- **`devDependencies`** – מה שצריך **רק בזמן פיתוח** (typescript, vitest, eslint).
- **`scripts`** – קיצורי דרך לפקודות: `"dev": "vite"` ← מריצים `npm run dev`.

### node_modules ו-Lockfile

- **`node_modules/`** – התיקייה שבה כל ה-Packages מותקנים בפועל. היא **ענקית**, **לא** נכנסת ל-Git, ואפשר תמיד למחוק אותה ולהריץ `npm install` מחדש.
- **`package-lock.json`** – ה-**Lockfile**: רושם את **הגרסה המדויקת** של כל Package (כולל ה-Packages של ה-Packages). **כן** נכנס ל-Git, כדי שכל המפתחים והשרתים יקבלו בדיוק את אותו הדבר.

### Semantic Versioning – מה אומר `^1.2.3`?

גרסה בנויה משלושה מספרים: **MAJOR.MINOR.PATCH**.

| חלק | מתי עולה | דוגמה |
|---|---|---|
| **MAJOR** | שינוי ששובר תאימות – הקוד שלך עלול להישבר | `1.x` ← `2.0.0` |
| **MINOR** | יכולת חדשה, בלי לשבור | `1.2` ← `1.3.0` |
| **PATCH** | תיקון באג | `1.2.3` ← `1.2.4` |

- `^1.2.3` = "כל גרסה `1.x.x` מ-1.2.3 ומעלה" – מקבל MINOR ו-PATCH, אבל לא MAJOR.
- `~1.2.3` = רק PATCH (`1.2.x`).
- `1.2.3` = בדיוק הגרסה הזו.

## 4. Environment Variables ו-`.env`

**Environment Variables** (משתני סביבה) הם הגדרות שמגיעות **מבחוץ** לקוד: כתובת מסד הנתונים, מפתח API, פורט. כך אותו קוד רץ במחשב שלך, בבדיקות ובפרודקשן – עם הגדרות שונות.

```text .env (לא נכנס ל-Git!)
DATABASE_URL=postgres://localhost:5432/shop
PAYMENT_API_KEY=sk_test_abc123
PORT=3000
```

ב-Node.js קוראים אותם עם `process.env.PORT`.

> [!danger] **לעולם** לא מכניסים את `.env` ל-Git. בוטים סורקים את GitHub כל הזמן ומוצאים מפתחות שדלפו תוך דקות. מוסיפים `.env` ל-`.gitignore`, ושומרים בריפו רק קובץ `.env.example` עם שמות המשתנים בלי הערכים.

> [!tip] מה Senior יודע: (1) ב-CI ובשרתים משתמשים ב-`npm ci` במקום `npm install` – הוא מתקין **בדיוק** לפי ה-Lockfile ונכשל אם יש אי-התאמה. (2) כל Dependency הוא קוד של מישהו אחר שרץ אצלך – לפני שמוסיפים ספרייה בודקים שהיא מתוחזקת, ומריצים `npm audit` לחולשות אבטחה. (3) בודקים את משתני הסביבה **בעליית האפליקציה** (למשל עם Zod ממודול 2) – עדיף לקרוס מיד עם הודעה ברורה מאשר לגלות בעוד שעה ש-`DATABASE_URL` חסר.

## מה עשינו כאן?

**בקובץ הפקודות:**
- **`mkdir` + `cd`** – יוצרים תיקייה ונכנסים אליה. כל הפקודות הבאות רצות **בתוך** התיקייה הזו.
- **`node -v` / `npm -v`** – בדיקה ראשונה בכל מחשב חדש: האם הכלים מותקנים ובאיזו גרסה.
- **`npm init -y`** – יוצר `package.json` (ה-`-y` אומר "כן לכל השאלות").
- **`npm install zod`** – מוריד את zod ל-`node_modules` ורושם אותו ב-`dependencies` וב-Lockfile.
- **`npm install -D ...`** – ה-`-D` שם את החבילות ב-`devDependencies`. `tsx` מריץ קבצי TypeScript ישירות, ו-`@types/node` נותן Types לפונקציות של Node.
- **`npx tsc --init`** – `npx` מריץ כלי מתוך `node_modules` (או מוריד אותו זמנית). יוצר `tsconfig.json`.
- **`.gitignore`** – מגן על `node_modules` ועל `.env` מלהיכנס ל-Git (נלמד בשיעור הבא).

**ב-package.json:**
- **`"type": "module"`** – אומר ל-Node להשתמש ב-`import`/`export` המודרניים.
- **`scripts`** – `dev` מריץ את השרת ומרענן בכל שינוי (`watch`), `build` מקמפל ל-JavaScript, `start` מריץ את הגרסה המקומפלת בפרודקשן, `test` מריץ את הבדיקות.
- **`^` בגרסאות** – מאפשר עדכוני MINOR ו-PATCH אוטומטיים בהתקנה חדשה, אבל ה-Lockfile הוא שקובע מה יותקן בפועל.

> [!note] ב-PowerShell הישן (5.1) הפקודה `echo "x" > .env` עלולה לשמור את הקובץ בקידוד UTF-16 שחלק מהכלים לא קוראים. אם משהו מוזר קורה – צור את הקובץ דרך VS Code.

## Git – מכונת זמן לקוד

תאר לעצמך שאתה כותב עבודה גדולה ושומר קבצים בשם `final.docx`, `final2.docx`, `final_REAL.docx`, `final_REAL_fixed.docx`... ואז חבר רוצה לעבוד עליה איתך במקביל. כאוס. **Git** פותר בדיוק את זה.

### אנלוגיה: אלבום תמונות עם מכונת זמן

- **Repository** (ריפו) = **האלבום** – כל ההיסטוריה של הפרויקט.
- **Commit** = **תמונה** של כל הפרויקט ברגע מסוים, עם כיתוב ("הוספתי כפתור התחברות"). אפשר תמיד לחזור לכל תמונה.
- **Staging area** = **השולחן שעליו מסדרים את מה שייכנס לתמונה הבאה** – לא חייבים לצלם הכל.
- **Branch** (ענף) = **ציר זמן מקביל** – "מה אם ננסה עיצוב חדש?" – בלי לגעת בגרסה שעובדת.
- **Merge** = **איחוד** של ציר הזמן המקביל חזרה לראשי.
- **GitHub** = **ענן משותף לאלבומים** – כולם בצוות מעלים ומורידים משם, ושם גם עושים **Code Review**.

> [!note] **Git** הוא הכלי שרץ אצלך במחשב. **GitHub** הוא אתר שמאחסן ריפו של Git ומוסיף שיתוף פעולה (Pull Requests, Issues, CI). אפשר להשתמש ב-Git בלי GitHub, אבל לא להפך.

### למה זה חשוב לך?

בכל צוות פיתוח בעולם, **שום שורת קוד לא מגיעה לפרודקשן בלי לעבור דרך Git ו-Pull Request**. זה הכלי שבו תשתמש עשרות פעמים ביום, והוא הדבר הראשון שבודקים כשמצטרפים לצוות.

## 1. שלושת האזורים

| אזור | מה זה | פקודה שמעבירה הלאה |
|---|---|---|
| **Working Directory** | הקבצים כמו שהם עכשיו בתיקייה | `git add` ← |
| **Staging Area** | השינויים שבחרת להכניס ל-Commit הבא | `git commit` ← |
| **Repository** (`.git`) | ההיסטוריה השמורה – כל ה-Commits | `git push` ← GitHub |

הפקודה הכי חשובה: **`git status`** – תמיד אומרת לך מה מצב כל קובץ. כשמתבלבלים – מריצים אותה.

## 2. Branches – לעבוד בלי לשבור

ה-Branch הראשי נקרא בדרך כלל **`main`** – והוא אמור **תמיד לעבוד**. כל פיצ׳ר או תיקון נעשה ב-Branch משלו:

```bash יצירת Branch ומעבר אליו
git switch -c feature/login-button   # יוצר Branch חדש ועובר אליו
git branch                           # מציג את כל ה-Branches (הנוכחי מסומן ב-*)
git switch main                      # חזרה ל-main
```

## 3. Merge ו-Merge Conflicts

כשמאחדים Branch, Git משלב את השינויים לבד – **כל עוד הם לא נוגעים באותן שורות**. אם שני אנשים שינו את **אותה שורה**, Git לא יכול לנחש מי צודק ומסמן **Merge Conflict**:

```text כך נראה Conflict בתוך הקובץ
<<<<<<< HEAD
const FREE_SHIPPING_FROM = 200;
=======
const FREE_SHIPPING_FROM = 250;
>>>>>>> feature/new-prices
```

**איך פותרים:**
1. פותחים את הקובץ (VS Code מסמן את ה-Conflict בצבעים ונותן כפתורים: Accept Current / Incoming / Both).
2. מחליטים מה הגרסה הנכונה – לפעמים אחת מהן, לפעמים שילוב. **אם לא בטוחים – שואלים את מי שכתב את השינוי השני.**
3. מוחקים את הסימונים `<<<<<<<`, `=======`, `>>>>>>>`.
4. `git add` לקובץ ו-`git commit` לסיום.

> [!tip] Conflicts הם לא תקלה – הם חלק רגיל מעבודת צוות. הדרך לקבל פחות מהם: Branches קצרים (יום-יומיים), ו-`git pull` מ-`main` לעתים קרובות.

## 4. Remote – עבודה מול GitHub

| פקודה | מה עושה |
|---|---|
| `git clone <url>` | מוריד ריפו קיים מ-GitHub למחשב |
| `git push` | מעלה את ה-Commits שלך ל-GitHub |
| `git pull` | מוריד שינויים של אחרים ומשלב אצלך |
| `git fetch` | רק מוריד מידע על שינויים, בלי לשלב |

**origin** הוא השם המקובל לריפו המרוחק ב-GitHub.

## 5. Pull Request ו-Code Review

**Pull Request** (PR) הוא בקשה: "בדקו את השינויים ב-Branch שלי, ואם הם טובים – תמזגו ל-`main`".

1. דוחפים Branch ל-GitHub ופותחים PR עם תיאור: **מה** שיניתי ו**למה**.
2. **CI** מריץ אוטומטית בדיקות ו-Lint (שיעור הבא).
3. חבר צוות עושה **Code Review**: קורא, שואל שאלות, מציע שיפורים.
4. מתקנים לפי ההערות ודוחפים עוד Commits לאותו Branch – ה-PR מתעדכן לבד.
5. אחרי אישור – **Merge** ל-`main` ומוחקים את ה-Branch.

## 7. Commit Messages טובות

| ❌ רע | ✅ טוב |
|---|---|
| `fix` | `fix: prevent double order on fast double-click` |
| `changes` | `feat: add free shipping above 200 ILS` |
| `asdf` | `refactor: extract price calculation to pure function` |

הכלל: **שורה ראשונה קצרה (עד ~70 תווים) בלשון ציווי**, שמתארת **מה** השינוי עושה. הרבה צוותים משתמשים בקידומות **Conventional Commits**: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`.

> [!danger] אם בטעות עשית Commit לסוד (סיסמה, מפתח API) ודחפת – מחיקה ב-Commit הבא **לא מספיקה**, הוא נשאר בהיסטוריה. צריך **לבטל את המפתח מיד** (Rotate) אצל הספק, ורק אחר כך לנקות.

> [!tip] מה Senior יודע: Commits **קטנים וממוקדים** – כל Commit עושה דבר אחד ואפשר להבין אותו לבד. ## מה קורה בתהליך?

- **`git switch main` + `git pull`** – תמיד מתחילים מהגרסה העדכנית ביותר. כך מקטינים את הסיכוי ל-Conflicts.
- **`git switch -c feature/...`** – Branch חדש עם שם שמתאר את העבודה. הקידומת `feature/` (או `fix/`) היא מוסכמה נפוצה.
- **`git status` ו-`git diff`** – לפני כל Commit בודקים **מה בדיוק** השתנה. כך לא מכניסים בטעות `console.log` שנשכח או קובץ זמני.
- **`git add <קבצים>`** – מוסיפים קבצים ספציפיים ל-Staging, במקום `git add .` עיוור. ככה כל Commit ממוקד.
- **שני Commits נפרדים** – פיצ׳ר ותיקון הם שני שינויים לוגיים שונים. אם יתברר שהתיקון שגוי – אפשר לבטל רק אותו (`git revert`).
- **`git push -u origin ...`** – ה-`-u` מקשר את ה-Branch המקומי ל-Branch ב-GitHub, כך שבפעם הבאה מספיק `git push`.
- **`git fetch` + `git merge origin/main`** – מכניסים ל-Branch שלנו את מה שהשתנה ב-`main` בזמן שעבדנו. יש צוותים שמעדיפים `git rebase` – זה מסדר היסטוריה "ישרה", אבל משכתב Commits, ולכן **לא עושים rebase ל-Branch שאחרים עובדים עליו**.
- **`git branch -d`** – מוחק Branch מקומי שכבר מוזג. ריפו נקי = פחות בלבול.
- **`git log --oneline --graph`** – מראה את ההיסטוריה כעץ קטן: מי התפצל ממי ואיפה התאחדו.

## איך יודעים שהקוד עובד – ונשאר עובד?

כתבת פונקציה שמחשבת משלוח, בדקת ידנית – עובד. חודש אחרי, מישהו שינה משהו קטן בפונקציה אחרת, ופתאום כל ההזמנות מקבלות משלוח חינם. אף אחד לא שם לב עד שהגיע הדוח החודשי. **Tests** (בדיקות אוטומטיות) נועדו למנוע בדיוק את זה.

### אנלוגיה: רשימת בדיקות של טייס

לפני כל טיסה, הטייס עובר **Checklist** – גם אם הוא טס 20 שנה. זה לא כי הוא לא סומך על עצמו, אלא כי **בדיקה אוטומטית וקבועה תופסת דברים שבן אדם מפספס**.

- **Test** = **סעיף ב-Checklist**: "כשהסל ריק – המשלוח חייב להיות 0".
- **Test Runner** (כמו **Vitest**) = **הטייס שעובר על כל הרשימה** ומדווח מה עבר ומה נכשל.
- **Debugging** (ניפוי באגים) = **עבודת הבלש** כשמשהו בכל זאת נכשל: לאסוף ראיות, לצמצם חשודים, למצוא את האשם.

### למה זה חשוב לך?

בכל צוות מקצועי, PR בלי Tests לא עובר Review. ומצד שני – רוב הזמן של מפתח הולך לא על כתיבת קוד חדש אלא על **הבנה ותיקון של קוד קיים**. מי שיודע לדבג בשיטתיות פותר בעיות בדקות במקום בימים.

| Matcher | מתי |
|---|---|
| `toBe(5)` | ערכים פשוטים (מספר, טקסט, boolean) |

## 3. Arrange – Act – Assert

כל Test טוב בנוי משלושה חלקים:
1. **Arrange** – הכנה: יוצרים את הנתונים.
2. **Act** – פעולה: קוראים לפונקציה.
3. **Assert** – בדיקה: מוודאים שהתוצאה נכונה.

## 4. Edge Cases – איפה הבאגים מתחבאים

לא מספיק לבדוק את "המסלול השמח". בודקים את **הקצוות**: רשימה ריקה, 0, מספר שלילי, בדיוק על הגבול (199.99 / 200 / 200.01), `null`, טקסט ענק, עברית ואימוג׳י.

## 5. Mocking – לבודד תלויות

**Mock** (דמה) הוא תחליף מזויף לחלק שאנחנו לא רוצים להפעיל באמת בבדיקה – למשל `fetch` לשרת חיצוני. למה? כי שרת אמיתי איטי, עולה כסף, ולפעמים לא זמין – והבדיקה צריכה להיות **מהירה ודטרמיניסטית** (אותה תוצאה בכל הרצה).

## 6. TDD – Test-Driven Development

**TDD** הוא סדר עבודה: **Red** (כותבים Test שנכשל) ← **Green** (כותבים מינימום קוד שיעבור) ← **Refactor** (משפרים את הקוד, והבדיקה מוודאת ששום דבר לא נשבר). לא חייבים לעבוד ככה תמיד, אבל זה מצוין לתיקון באגים: קודם Test שמשחזר את הבאג, ואז התיקון.

export const FREE_SHIPPING_FROM = 200;
export const SHIPPING_PRICE = 30;

export interface CartItem {
  price: number;
  quantity: number;
}

// Pure function – קל מאוד לבדוק
export function shippingCost(subtotal: number): number {
  if (subtotal < 0) throw new Error('סכום לא יכול להיות שלילי');
  if (subtotal === 0 || subtotal >= FREE_SHIPPING_FROM) return 0;
  return SHIPPING_PRICE;
}

export function cartTotal(items: CartItem[]): number {
  const subtotal = items.reduce((sum, i) => sum + i.price * i.quantity, 0);
  return subtotal + shippingCost(subtotal);
}

// פונקציה עם תלות חיצונית (רשת) – בבדיקה נחליף את fetch ב-Mock
export async function fetchCoupon(code: string): Promise<number> {
  const res = await fetch(`/api/coupons/${code}`);
  if (!res.ok) throw new Error(`קופון לא תקין: ${code}`);
  const data: { discount: number } = await res.json();
  return data.discount;
}

export function applyDiscount(price: number, percent: number): number {
  if (price < 0) throw new Error('מחיר לא יכול להיות שלילי');
  if (percent < 0 || percent > 100) throw new Error('אחוז הנחה חייב להיות בין 0 ל-100');
  const result = price * (1 - percent / 100);
  return Math.round(result * 100) / 100; // עיגול לאגורות
}
