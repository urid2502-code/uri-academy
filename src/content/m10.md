## "אצלי זה עובד!" – הבעיה ש-Docker פותר

כל מפתח שמע (או אמר) את המשפט הזה: **"אצלי במחשב זה עובד"**. הקוד רץ מצוין אצלך, אבל בשרת הוא קורס. למה? כי אצלך מותקן Node.js 22 ובשרת Node.js 18, אצלך יש ספרייה מסוימת ובשרת לא, אצלך Windows ובשרת Linux. הקוד זהה – **הסביבה** שונה.

**Docker** פותר את זה: במקום לשלוח רק את הקוד, אורזים את הקוד **יחד עם כל מה שהוא צריך כדי לרוץ** – מערכת ההפעלה הבסיסית, גרסת Node.js, הספריות וההגדרות – לחבילה אחת שרצה בדיוק אותו דבר בכל מקום.

### אנלוגיה: מכולת שילוח

לפני שהמציאו את **מכולת השילוח** הסטנדרטית, כל נמל העמיס סחורה אחרת: שקים, חביות, ארגזים בכל גודל. כל משלוח היה פרויקט. אז המציאו מכולה בגודל קבוע: **לא משנה מה בפנים** – רהיטים, בננות או מחשבים – כל אוניה, כל משאית וכל עגורן בעולם יודעים להרים אותה.

- **המכולה** ← זה ה-**Container**: הקוד שלך + כל התלויות, ארוז ומבודד.
- **התוכנית לבניית המכולה ותכולתה** ← זה ה-**Dockerfile**.
- **העגורן והאוניה** ← זה המחשב או השרת שמריץ Docker. לא משנה לו מה בפנים.

> [!tip] כמעט כל חברה מודרנית מריצה את ה-Backend שלה ב-Containers. גם Kubernetes (השיעור הבא) לא מריץ "קוד" – הוא מריץ Containers. לכן Docker הוא הצעד הראשון בדרך ל-Cloud.

### למה זה חשוב לך?

כמפתח Full Stack תכתוב Dockerfile לכל שירות, תריץ מקומית PostgreSQL ו-Redis בפקודה אחת, ותבין למה ה-Deploy נכשל. זה כלי יומיומי, לא "עניין של DevOps".

## Image מול Container – ההבדל הכי חשוב

| מושג | מה זה בשפה פשוטה | אנלוגיה |
|---|---|---|
| **Image** (תמונה) | חבילה **קפואה וקבועה** של מערכת קבצים + הוראת הפעלה. לא רצה, רק קיימת | מתכון מודפס, או Class בקוד |
| **Container** | **מופע רץ** של Image – תהליך חי עם זיכרון, רשת ולוגים | העוגה שאפית לפי המתכון, או Object שנוצר מה-Class |
| **Registry** | "מחסן" שבו שומרים Images ומורידים אותם (Docker Hub, ECR, GHCR) | ספריית מתכונים משותפת |

מ-Image אחד אפשר להריץ **עשרה Containers** במקביל. כשמוחקים Container – ה-Image נשאר. ואם שינית משהו בתוך Container רץ – השינוי נעלם כשהוא נמחק. Container הוא **זמני** (Ephemeral) מטבעו.

## Dockerfile – המתכון

**Dockerfile** הוא קובץ טקסט עם הוראות, שורה אחרי שורה. כל הוראה יוצרת **Layer** (שכבה). Docker שומר כל שכבה ב-**Cache**: אם שורה וכל מה שלפניה לא השתנו – הוא לא בונה אותה מחדש. לכן הסדר חשוב מאוד.

| הוראה | מה היא עושה |
|---|---|
| `FROM` | מאיזה Image מתחילים (למשל `node:22-alpine`) |
| `WORKDIR` | התיקייה שבה נעבוד בתוך ה-Image |
| `COPY` | העתקת קבצים מהמחשב שלך לתוך ה-Image |
| `RUN` | הרצת פקודה בזמן **הבנייה** (התקנת חבילות, קומפילציה) |
| `ENV` | משתנה סביבה קבוע |
| `USER` | איזה משתמש מריץ את התהליך |
| `EXPOSE` | תיעוד: על איזה Port האפליקציה מאזינה |
| `CMD` | הפקודה שרצה כש-Container **עולה** |

### ארבעה הרגלים של Dockerfile מקצועי

1. **Multi-stage Build.** שלב ראשון ("build") מתקין את כל הכלים – TypeScript, devDependencies – ומקמפל. שלב שני ("runtime") מעתיק **רק** את ה-JavaScript המקומפל ואת התלויות של Production. התוצאה: Image קטן פי כמה, ופחות כלים שתוקף יכול לנצל.
2. **`npm ci` ולא `npm install`.** `npm ci` מתקין **בדיוק** את מה שכתוב ב-`package-lock.json`, ונכשל אם יש אי-התאמה. ככה כל Build זהה.
3. **Non-root User.** כברירת מחדל תהליך ב-Container רץ כ-`root`. אם מישהו פורץ לאפליקציה – הוא root. משתמשים ב-`USER node` (משתמש מוכן ב-Images של Node).
4. **Exec-form CMD.** כותבים `CMD ["node", "dist/server.js"]` (מערך) ולא `CMD node dist/server.js` (מחרוזת). בצורת המחרוזת Docker מריץ את Node **דרך Shell**, וה-Shell לא מעביר את אות העצירה **SIGTERM** ל-Node. התוצאה: האפליקציה לא יודעת שמבקשים ממנה לסגור, וכעבור 10 שניות היא "נהרגת" באמצע בקשות.

> [!warn] אל תריץ `npm start` ב-CMD. גם npm הוא תהליך ביניים שלא תמיד מעביר את SIGTERM. הרץ את `node` ישירות.

## הפקודות שתשתמש בהן כל יום

```bash פקודות Docker בסיסיות
docker build -t orders-api:1.0 .          # בניית Image מה-Dockerfile בתיקייה הנוכחית
docker images                             # רשימת ה-Images שיש לך
docker run -d -p 8080:3000 --name api orders-api:1.0   # הרצת Container ברקע
docker ps                                 # אילו Containers רצים עכשיו
docker logs -f api                        # צפייה בלוגים בזמן אמת
docker exec -it api sh                    # "להיכנס" ל-Container ולהריץ פקודות
docker stop api && docker rm api          # עצירה (SIGTERM) ומחיקה
```

### Port Mapping

ל-Container יש רשת משלו. גם אם האפליקציה מאזינה בתוכו על Port 3000, מבחוץ אי אפשר להגיע אליה – עד שממפים. `-p 8080:3000` אומר: **"Port 8080 במחשב שלי ← Port 3000 בתוך ה-Container"**. הסדר הוא תמיד **מבחוץ:בפנים**.

> [!note] בתוך Container האפליקציה צריכה להאזין על `0.0.0.0` ולא על `localhost`. `localhost` בתוך Container זה ה-Container עצמו, ולכן חיבורים מבחוץ לא יגיעו.

### Environment Variables

אותו Image צריך לרוץ ב-Development, ב-Staging וב-Production – רק עם הגדרות שונות. לכן הגדרות (כתובת מסד נתונים, רמת לוגים) מגיעות מ-**Environment Variables** בזמן הריצה: `docker run -e LOG_LEVEL=debug ...` או `--env-file .env`.

> [!danger] לעולם אל תכתוב סיסמאות או מפתחות API בתוך ה-Dockerfile (`ENV DB_PASSWORD=...`) ואל תעתיק את `.env` לתוך ה-Image. כל מי שמוריד את ה-Image יכול לקרוא את השכבות שלו.

## .dockerignore

כמו `.gitignore`, אבל ל-`COPY`. בלעדיו `COPY . .` מעתיק גם את `node_modules` של Windows שלך (שלא יעבוד ב-Linux), את `.git` ואת `.env` עם הסודות.

## Docker Compose – כמה Containers ביחד

אפליקציה אמיתית צריכה גם **PostgreSQL** וגם **Redis**. במקום שלוש פקודות `docker run` ארוכות, כותבים קובץ `compose.yaml` אחד ומריצים `docker compose up`. Compose יוצר רשת משותפת שבה כל שירות נגיש **לפי השם שלו** – האפליקציה מתחברת ל-`postgres:5432`, לא ל-`localhost`.

> [!tip] מה Senior יודע: מצמידים גרסה מדויקת ל-Base Image (`node:22.11-alpine`, לא `latest`); מתייגים כל Image לפי ה-Git Commit SHA כדי לדעת בדיוק מה רץ ב-Production; סורקים Images לחולשות אבטחה (`docker scout`, Trivy); ומריצים **תהליך אחד** בכל Container. Compose מעולה לפיתוח מקומי – ב-Production משתמשים ב-Kubernetes.

## Dockerfile – מה קורה בכל שלב

- **`FROM node:22-alpine AS build`** – מתחילים מ-Image רשמי של Node.js על Alpine Linux (הפצה זעירה). `AS build` נותן לשלב שם כדי שנוכל להעתיק ממנו אחר כך.
- **`COPY package*.json` ואז `RUN npm ci`** – זה הטריק הכי חשוב ל-Cache. אם שינית רק קובץ ב-`src` – קבצי החבילות לא השתנו, ו-Docker מדלג על `npm ci` (שלוקח דקות). אם היינו מעתיקים את כל הקוד קודם, כל שינוי קטן היה מתקין הכל מחדש.
- **`npm run build`** – מריץ `tsc` ומייצר תיקיית `dist` עם JavaScript.
- **`npm prune --omit=dev`** – משאיר ב-`node_modules` רק תלויות של Production.
- **`FROM node:22-alpine AS runtime`** – מתחילים **Image חדש ונקי**. כל מה שהיה בשלב הקודם (קוד TypeScript, כלי Build) לא נכנס, חוץ ממה שנעתיק במפורש עם `--from=build`.
- **`--chown=node:node` ו-`USER node`** – הקבצים שייכים למשתמש רגיל, והתהליך רץ בלי הרשאות root.
- **`CMD ["node", "dist/server.js"]`** – צורת מערך. Node.js הוא התהליך הראשי (PID 1), ולכן כש-Docker או Kubernetes שולחים SIGTERM – הוא מגיע ישר לקוד שלך.

## compose.yaml

- **`services`** – כל שירות הופך ל-Container. השם (`postgres`, `redis`) הוא גם **שם המחשב** ברשת הפנימית – לכן ב-`DATABASE_URL` כתוב `@postgres:5432`.
- **`depends_on` עם `service_healthy`** – בלי זה, האפליקציה עלולה לעלות לפני ש-PostgreSQL מוכן לקבל חיבורים ולקרוס.
- **`healthcheck`** – Compose מריץ `pg_isready` כל 5 שניות כדי לדעת מתי ה-DB באמת מוכן.
- **`volumes: pgdata`** – בלי Volume, הנתונים יושבים בתוך ה-Container ונמחקים איתו. Volume שומר אותם בנפרד.

> [!tip] נסה: `docker compose up --build`, ואז `docker compose ps` ו-`docker compose logs -f api`. לסגירה: `docker compose down` (הוסף `-v` כדי למחוק גם את הנתונים).

## למה צריך Kubernetes?

ב-Docker למדנו להריץ Container אחד. אבל ב-Production יש לך אולי 15 שירותים, מכל אחד 3–20 עותקים, על עשרות שרתים. מי מחליט איזה Container ירוץ על איזה שרת? מה קורה כששרת נופל באמצע הלילה? איך מעדכנים גרסה בלי להפיל את האתר? איך מוסיפים עותקים כשיש עומס?

**Kubernetes** (בקיצור **K8s**) הוא מערכת **Orchestration** (תזמור) שעונה על כל השאלות האלה. אתה אומר לו **מה אתה רוצה** ("3 עותקים של orders-api, גרסה 1.4") – והוא דואג שזה יקרה, וממשיך לדאוג **כל הזמן**. נפל Container? הוא מעלה חדש. נפל שרת שלם? הוא מעביר את ה-Containers לשרת אחר. זה נקרא **Self-healing**.

### אנלוגיה: מנהל רשת מסעדות

- **Cluster** ← כל הרשת.
- **Node** ← סניף (שרת פיזי או וירטואלי) עם מטבח, כוח אדם ומקום מוגבל.
- **Pod** ← עמדת עבודה של טבח אחד במטבח (בדרך כלל Container אחד).
- **Deployment** ← ההוראה של המנהל: "בכל רגע חייבים להיות 3 טבחי פיצה". טבח הלך הביתה? המנהל מגייס מחליף מיד.
- **Service** ← מספר טלפון מרכזי להזמנות. הלקוח לא צריך לדעת איזה טבח פנוי – המוקד מפנה.
- **Ingress** ← הכניסה הראשית והמארחת בדלת, שמפנה כל אורח לאזור הנכון.

> [!note] המנהל לא מבשל בעצמו. הוא רק משווה כל הזמן בין **מה שצריך להיות** (Desired State) למה **שיש בפועל** (Actual State), ומתקן את הפער. זה כל הקסם של Kubernetes.

## אבני הבניין

| מושג | מה זה בשפה פשוטה |
|---|---|
| **Cluster** | קבוצת שרתים ש-Kubernetes מנהל כיחידה אחת |
| **Node** | שרת אחד ב-Cluster שמריץ Pods |
| **Pod** | היחידה הקטנה ביותר: Container אחד (לפעמים כמה) עם כתובת IP משלו. **Pods הם חד-פעמיים** – הם מתים ונולדים עם IP חדש |
| **Deployment** | מגדיר איזה Image להריץ, כמה עותקים (**Replicas**), ואיך לעדכן גרסה |
| **Service** | כתובת **קבועה** ומאזן עומסים פנימי מול קבוצת Pods משתנה |
| **Ingress** | הכניסה מהאינטרנט: מפנה `shop.example.com/api` ל-Service הנכון |
| **ConfigMap / Secret** | הגדרות וסודות שמוזרקים ל-Pods כ-Environment Variables |

הכל מוגדר בקבצי **YAML** ונשלח ל-Cluster עם `kubectl apply -f deployment.yaml`. פקודות שימושיות: `kubectl get pods`, `kubectl logs <pod>`, `kubectl describe pod <pod>` (למה הוא לא עולה?), `kubectl rollout status deployment/orders-api`.

## Probes – איך Kubernetes יודע שהאפליקציה בסדר?

Kubernetes רואה שהתהליך רץ – אבל "רץ" זה לא "תקין". לכן הוא שואל את האפליקציה שלוש שאלות שונות, דרך **Probes** (בדיקות):

| Probe | השאלה | מה קורה כשנכשל |
|---|---|---|
| **Startup** | "סיימת לעלות?" | מחכים. שתי הבדיקות האחרות לא מתחילות עד שזו מצליחה. מתאים לאפליקציה שעולה לאט |
| **Readiness** | "אתה מוכן לקבל תנועה **עכשיו**?" | ה-Pod **מוצא מה-Service** – לא שולחים אליו בקשות. **לא** מפעילים אותו מחדש |
| **Liveness** | "אתה תקוע לגמרי?" | Kubernetes **הורג ומפעיל מחדש** את ה-Container |

> [!danger] **לעולם אל תבדוק את מסד הנתונים ב-Liveness Probe.** אם ה-DB איטי לכמה שניות, **כל** ה-Pods נכשלים ב-Liveness בבת אחת, Kubernetes מפעיל את כולם מחדש, וכולם מנסים להתחבר ל-DB בבת אחת – והופכים תקלה קטנה להשבתה מלאה. Liveness בודק רק "התהליך שלי חי ולא תקוע" (`/livez` שמחזיר 200). תלויות חיצוניות – אם בכלל – רק ב-Readiness.

## Resources: Requests ו-Limits

- **Requests** – כמה CPU וזיכרון ה-Pod **מבטיח לעצמו**. לפי זה Kubernetes מחליט על איזה Node יש מקום (כמו להזמין שולחן).
- **Limits** – התקרה. חרגת מ-CPU? מאטים אותך (**Throttling**). חרגת מזיכרון? ה-Container נהרג (**OOMKilled**).

> [!warn] Pod בלי Requests עלול לשבת על Node עמוס מדי. Pod עם Limit זיכרון נמוך מדי יקרוס שוב ושוב עם `OOMKilled` – ותראה `CrashLoopBackOff` ב-`kubectl get pods`.

## Rolling Update – עדכון גרסה בלי השבתה

כשמשנים את ה-Image ב-Deployment, Kubernetes לא מכבה הכל. הוא מעלה Pod חדש, מחכה שיעבור **Readiness**, ורק אז מוריד Pod ישן – וחוזר חלילה. `maxSurge` קובע כמה Pods **נוספים** מותר להעלות, ו-`maxUnavailable` כמה מותר שיחסרו. אם הגרסה החדשה לא עוברת Readiness – העדכון נעצר והישנים ממשיכים לשרת. חזרה אחורה: `kubectl rollout undo`.

## Graceful Shutdown – לסגור בלי לשבור בקשות

בכל Rolling Update, Scale-down או העברת Pod – Kubernetes סוגר Pods. כך זה עובד:

1. Kubernetes שולח **SIGTERM** ל-Container (בגלל זה ה-Exec form ב-Dockerfile כל כך חשוב!).
2. **במקביל** הוא מתחיל להוציא את ה-Pod מה-Service – אבל זה לוקח כמה שניות להתפשט, ובינתיים עוד מגיעות בקשות.
3. יש לך `terminationGracePeriodSeconds` (ברירת מחדל 30) לסיים. אחרי זה – **SIGKILL**, בלי רחמים.

לכן האפליקציה צריכה: (א) להתחיל להחזיר 503 ב-Readiness, (ב) לחכות כמה שניות שהתנועה תפסיק להגיע, (ג) לסיים בקשות פתוחות, (ד) לסגור חיבורים ל-DB ול-Queue, (ה) לצאת.

## Autoscaling: HPA מול KEDA

- **HPA** (Horizontal Pod Autoscaler) – מוסיף או מוריד Pods לפי **CPU** (או זיכרון). מצוין ל-API: יותר בקשות ← יותר CPU ← יותר Pods.
- **KEDA** – מרחיב את ה-Autoscaling לפי **אירועים חיצוניים**, למשל **אורך התור** ב-Queue (מודול 8). Worker שמחכה להודעות כמעט לא צורך CPU, אבל אם יש 50,000 הודעות בתור – צריך עוד Workers עכשיו. KEDA גם יודע להוריד ל-**אפס** Pods כשהתור ריק.

> [!tip] מה Senior יודע: Readiness ו-Liveness הם Endpoints **שונים** עם לוגיקה שונה; Requests מוגדרים לפי מדידה אמיתית ולא ניחוש; מגדירים **PodDisruptionBudget** כדי שתחזוקת Nodes לא תוריד את כל העותקים בבת אחת; ומפזרים Replicas על Nodes ו-Zones שונים. וזוכרים ש-Pods הם "בקר ולא חיות מחמד" – אסור לשמור בהם מצב חשוב בזיכרון או בדיסק המקומי.

import http from 'node:http';
import { app } from './app';
import { db } from './db';
import { queueConsumer } from './queue';

let shuttingDown = false;
const server = http.createServer(app);

// Liveness: רק "התהליך חי". לא נוגעים ב-DB
app.get('/livez', (_req, res) => res.status(200).send('ok'));

// Readiness: מוכן לקבל תנועה? בזמן כיבוי – לא
app.get('/readyz', (_req, res) => {
  res.status(shuttingDown ? 503 : 200).send(shuttingDown ? 'draining' : 'ready');
});

server.listen(3000, '0.0.0.0');

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

async function shutdown(signal: string) {
  if (shuttingDown) return;
  shuttingDown = true;
  console.log(`${signal} received – starting graceful shutdown`);

  // רשת ביטחון: אם משהו נתקע – יוצאים לפני ש-Kubernetes שולח SIGKILL
  setTimeout(() => process.exit(1), 25_000).unref();

  // 1) נכשלים ב-Readiness ומחכים שה-Service יפסיק לשלוח אלינו
  await sleep(5_000);

  // 2) מפסיקים לקבל חיבורים חדשים ומחכים לבקשות הפתוחות
  await new Promise<void>((resolve) => server.close(() => resolve()));

  // 3) מפסיקים לצרוך הודעות ומשחררים משאבים
  await queueConsumer.stop();
  await db.end();

  console.log('shutdown complete');
  process.exit(0);
}

process.on('SIGTERM', () => void shutdown('SIGTERM'));
process.on('SIGINT', () => void shutdown('SIGINT'));

## "אי אפשר לתקן את מה שלא רואים"

עד עכשיו כשמשהו נשבר, הרצת את הקוד אצלך, הוספת `console.log` ומצאת את הבאג. ב-Production זה לא עובד: יש 30 Pods, 10 שירותים שמדברים ביניהם ו-Queues באמצע. משתמש כותב "התשלום נתקע" – ואין לך דרך "להריץ אצלך" את מה שקרה לו.

**Observability** (נראוּת) היא היכולת **להבין מה קורה בתוך המערכת רק מהמידע שהיא מוציאה החוצה** – בלי להוסיף קוד ובלי לעשות Deploy חדש. היא נשענת על שלושה "עמודים": **Logs**, **Metrics** ו-**Traces**.

### אנלוגיה: רופא במחלקה

- **Metrics** ← המוניטור ליד המיטה: דופק, לחץ דם, חום – **מספרים** לאורך זמן. במבט אחד רואים שמשהו לא בסדר ("הדופק קפץ ב-14:05").
- **Logs** ← יומן האחות: **רשומות מפורטות** על אירועים ("14:03 – קיבל תרופה X, התלונן על סחרחורת"). כאן מבינים **מה** קרה.
- **Traces** ← חומר ניגוד בצילום: עוקבים אחרי **מסלול** אחד דרך כל הגוף ורואים בדיוק **איפה** החסימה.

הרופא לא מחכה שהמטופל יתעלף – **התראה** (Alert) מצפצפת כשהדופק חוצה סף.

> [!tip] בראיונות ל-Senior שואלים כמעט תמיד: "איך היית יודע שמשהו נשבר ב-Production, ואיך היית מוצא איפה?". התשובה היא השיעור הזה.

## עמוד 1: Structured Logs

לוג של מתחילים: `console.log('order failed ' + id)`. אי אפשר לחפש בזה ברצינות. **Structured Log** הוא **JSON** עם שדות קבועים, כך שמערכת לוגים (Loki, Elasticsearch, CloudWatch) יכולה לסנן: "כל השגיאות של `orders-api` עבור `orderId=1543` בשעה האחרונה".

```json לוג מובנה אחד
{"level":"error","time":"2026-11-16T12:03:11Z","service":"orders-api","requestId":"req-8f2c","traceId":"4bf92f3577b34da6a3ce929d0e0e4736","orderId":1543,"msg":"payment failed","err":{"type":"TimeoutError"}}
```

ב-Node.js הספרייה הסטנדרטית היא **pino** – מהירה מאוד וכותבת JSON כברירת מחדל.

- **Log Levels:** `debug` (פרטים לפיתוח) · `info` (אירועים רגילים) · `warn` (מוזר אבל עובד) · `error` (משהו נכשל). ב-Production בדרך כלל `info` ומעלה.
- **Correlation ID** (מזהה קישור): מזהה ייחודי לכל בקשה (`requestId`), שמוצמד **לכל** שורת לוג שלה – וגם עובר לשירותים הבאים. ככה מוצאים את כל הסיפור של בקשה אחת מתוך מיליוני שורות.

> [!danger] **לעולם אל תכתוב ללוג סודות או מידע אישי (PII):** סיסמאות, Tokens, כותרת `Authorization`, מספרי כרטיס אשראי, תעודות זהות. לוגים נשמרים זמן רב, מועתקים למערכות רבות, והרבה אנשים יכולים לקרוא אותם. ב-pino משתמשים ב-`redact` כדי למחוק שדות כאלה אוטומטית.

## עמוד 2: Metrics

**Metric** הוא **מספר שנמדד לאורך זמן**. זול לשמור, מהיר לשאול – מושלם לגרפים ולהתראות. שלושה סוגים:

| סוג | מה הוא | דוגמה |
|---|---|---|
| **Counter** | מספר שרק **עולה** | סה"כ בקשות, סה"כ שגיאות, הזמנות שנוצרו |
| **Gauge** | ערך שעולה ויורד, "מצב עכשיו" | אורך תור, חיבורים פתוחים, זיכרון |
| **Histogram** | **התפלגות** של ערכים | זמני תגובה – כמה בקשות לקחו פחות מ-100ms, 500ms, 1s |

### RED – שלושת המספרים לכל שירות

- **R**ate – כמה בקשות בשנייה.
- **E**rrors – כמה מהן נכשלו (באחוזים).
- **D**uration – כמה זמן הן לוקחות.

אם יש לך רק דשבורד אחד לשירות – שים עליו את שלושת אלה.

### Percentiles: p50, p95, p99 בשפה פשוטה

**ממוצע משקר.** אם 99 בקשות לוקחות 10ms ואחת לוקחת 10 שניות – הממוצע הוא כ-110ms, ונראה "בסדר". אבל משתמש אחד מכל מאה מחכה 10 שניות!

סדר את 100 הבקשות האחרונות מהמהירה לאיטית:
- **p50** (החציון) – הבקשה ה-50: חצי מהמשתמשים חוו זמן כזה או מהיר יותר. "החוויה הטיפוסית".
- **p95** – הבקשה ה-95: רק 5% חוו גרוע מזה.
- **p99** – הבקשה ה-99: "הזנב". המשתמש הכי פעיל שלך, שעושה 100 בקשות ביום, **פוגש את זה כל יום**.

> [!tip] מגדירים יעדים והתראות על **p95/p99**, לא על ממוצע. וזו בדיוק הסיבה שמודדים זמנים עם **Histogram** ולא עם Gauge.

## עמוד 3: Distributed Tracing

בקשה אחת של "בצע הזמנה" עוברת: API Gateway ← orders-api ← PostgreSQL ← payments-api ← Queue ← notifications-worker. היא לקחה 4 שניות. **איפה?**

- **Trace** – המסע המלא של בקשה אחת, עם `traceId` ייחודי.
- **Span** – שלב אחד במסע (קריאת HTTP, Query ל-DB, טיפול בהודעה), עם זמן התחלה, משך, ו-**Parent** – מי קרא לו. ביחד הם יוצרים "עץ" שמוצג כמו תרשים גאנט.

**OpenTelemetry** (בקיצור **OTel**) הוא הסטנדרט הפתוח לאיסוף Traces, Metrics ו-Logs. כותבים את הקוד פעם אחת, ושולחים לכל מערכת (Jaeger, Grafana Tempo, Datadog...). הספרייה גם עושה **Auto-instrumentation**: Spans ל-HTTP, Express, PostgreSQL ו-Redis נוצרים אוטומטית.

### Propagation – איך ה-traceId עובר בין שירותים?

ב-HTTP, OTel מוסיף לכל בקשה יוצאת כותרת סטנדרטית (W3C):

```text כותרת traceparent
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             גרסה-traceId (32 תווים)----------spanId של ההורה--דגלים
```

השירות המקבל קורא את הכותרת וממשיך **את אותו Trace**. ב-**Queues** אין כותרות HTTP – לכן מכניסים את `traceparent` ל-**Headers של ההודעה** (`propagation.inject`) ושולפים אותו ב-Consumer (`propagation.extract`). בלי זה, ה-Trace "נקטע" בתור.

## Dashboards ו-Alerts

- **Dashboard** – גרפים של RED לכל שירות, ועוד: אורך תורים, חיבורי DB, זיכרון Pods.
- **Alert** – התראה אוטומטית (Slack, טלפון). הכלל: מתריעים על **סימפטומים שמשתמשים מרגישים** ("p99 מעל 2 שניות", "5% שגיאות"), לא על כל CPU שקפץ ל-80%. יותר מדי התראות = **Alert Fatigue** – כולם מתחילים להתעלם, ואז מפספסים את האמיתית.

## SLI, SLO ו-Error Budget

- **SLI** (Service Level Indicator) – **מה מודדים**: "אחוז בקשות ה-checkout שהצליחו ותוך פחות משנייה".
- **SLO** (Service Level Objective) – **היעד**: "99.9% מהבקשות בחודש".
- **Error Budget** – **כמה מותר להיכשל**: 0.1%. בחודש של 30 יום זה בערך **43 דקות** של תקלה. נשאר תקציב? אפשר לשחרר פיצ׳רים מהר. התקציב נגמר? עוצרים פיצ׳רים ומשקיעים ביציבות.

> [!tip] מה Senior יודע: מקשרים בין שלושת העמודים – `traceId` בכל לוג, וממטריקה חריגה קופצים ל-Trace לדוגמה ומשם ללוגים שלו. נזהרים מ-**High Cardinality**: לא שמים `userId` או `orderId` כ-Label של Metric (זה ייצור מיליוני סדרות ויפיל את מערכת המטריקות) – מקומם בלוגים וב-Traces. ומשתמשים ב-**Sampling** ל-Traces כשהתנועה גדולה.

@@ m10-l3 code typescript | checkout.ts – Span מותאם, Metric ולוג מובנה
import { trace, metrics, SpanStatusCode } from '@opentelemetry/api';
import pino from 'pino';
import { chargeCard, saveOrder, type Order } from './orders';

const tracer = trace.getTracer('orders-api');
const meter = metrics.getMeter('orders-api');

// Histogram לזמנים (בשביל p95/p99), Counter להזמנות
const checkoutDuration = meter.createHistogram('checkout.duration', { unit: 'ms' });
const ordersCreated = meter.createCounter('orders.created');

// redact: שדות רגישים לא יגיעו ללוג לעולם
const logger = pino({ redact: ['req.headers.authorization', '*.password', '*.cardNumber'] });

export async function checkout(order: Order, requestId: string) {
  return tracer.startActiveSpan('checkout', async (span) => {
    const start = performance.now();
    let outcome = 'success';
    span.setAttribute('order.items_count', order.items.length);

    // כל שורת לוג תכלול requestId ו-traceId – הקישור בין העמודים
    const log = logger.child({ requestId, traceId: span.spanContext().traceId, orderId: order.id });

    try {
      await chargeCard(order); // Span-ים פנימיים (HTTP, pg) נוצרים אוטומטית כילדים
      await saveOrder(order);
      ordersCreated.add(1, { payment_method: order.paymentMethod }); // Label עם מעט ערכים
      log.info('checkout completed');
    } catch (err) {
      outcome = 'error';
      span.recordException(err as Error);
      span.setStatus({ code: SpanStatusCode.ERROR });
      log.error({ err }, 'checkout failed');
      throw err;
    } finally {
      checkoutDuration.record(performance.now() - start, { outcome });
      span.end(); // חובה! Span שלא נסגר לא יישלח
    }
  });
}

## telemetry.ts

- **`NodeSDK`** – נקודת הכניסה של OpenTelemetry ב-Node.js. מאחדת Traces ו-Metrics.
- **`resource`** – "תעודת זהות" של השירות: שם וגרסה. בזכותה אפשר לסנן "כל ה-Traces של orders-api בגרסה 1.4" ולראות אם גרסה חדשה האטה משהו.
- **`OTLPTraceExporter` / `OTLPMetricExporter`** – שולחים בפרוטוקול הסטנדרטי **OTLP** ל-**OpenTelemetry Collector** – שירות שמקבל את הכל ומעביר למערכות האחסון. הקוד שלך לא תלוי בספק.
- **`getNodeAutoInstrumentations()`** – הקסם: בלי לשנות שורת קוד, כל בקשת HTTP נכנסת ויוצאת, כל Query ל-PostgreSQL וכל פקודת Redis הופכים ל-Span, והכותרת `traceparent` נוספת אוטומטית.

> [!warn] את הקובץ הזה צריך לטעון **לפני** כל import אחר (למשל `node --import ./dist/telemetry.js dist/server.js`). אחרת ספריות כמו `pg` ו-`http` כבר נטענו, וה-Auto-instrumentation לא "תופס" אותן.

## checkout.ts

1. **`startActiveSpan('checkout', ...)`** – פותח Span מותאם ומגדיר אותו כ"פעיל". כל Span אוטומטי שייווצר בפנים (הקריאה ל-payments, ה-INSERT) יהיה **ילד** שלו – וב-Trace תראה בדיוק כמה זמן לקח כל שלב.
2. **`span.setAttribute`** – מידע עסקי על ה-Span לחיפוש אחר כך.
3. **`logger.child({...traceId})`** – Logger "ילד" שמוסיף את השדות האלה לכל שורה. מהלוג אפשר לקפוץ ישר ל-Trace.
4. **`ordersCreated.add(1, { payment_method })`** – Counter עם Label שיש לו מעט ערכים אפשריים (card, paypal). **לא** `orderId` – זה High Cardinality.
5. **`recordException` + `setStatus(ERROR)`** – ה-Span יסומן באדום במערכת ה-Tracing.
6. **`finally`** – רץ גם בהצלחה וגם בכישלון: מודדים זמן עם Label `outcome` (כך אפשר לראות p99 של הצלחות בנפרד משגיאות) ו**סוגרים את ה-Span**.

## פתרון לדוגמה

**1. SLI ו-SLO:**
- **SLI:** אחוז בקשות `POST /api/checkout` שהחזירו קוד שאינו 5xx **וגם** הסתיימו תוך פחות מ-1,000ms.

- **Error Budget:** 0.5% – אם יש 2,000,000 בקשות בחודש, מותר שעד 10,000 "ייכשלו".
