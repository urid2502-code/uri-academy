## למה צריך "זמן אמת"?

ב-HTTP הרגיל שלמדנו במודול 1, **ה-Client תמיד מתחיל**: הוא שואל, השרת עונה, והשיחה נגמרת. אבל יש מוצרים שבהם **השרת** יודע משהו חדש ורוצה לספר עליו **עכשיו**:

- **צ׳אט** – הודעה חדשה הגיעה מחבר.
- **Dashboard חי** – מספר ההזמנות מתעדכן בכל שנייה.
- **התראות סיכון** – מערכת זיהתה עסקה חשודה, והנציג צריך לראות אותה מיד, לא בעוד דקה.
- **צ׳אט עם AI** – התשובה של מודל השפה מגיעה מילה אחרי מילה.

### אנלוגיה: איך מחכים לחבילה

- **Polling** – אתה יורד לתיבת הדואר כל 5 דקות לבדוק אם הגיעה חבילה. רוב הפעמים – כלום. מבזבז הליכות.
- **Long Polling** – אתה יורד לתיבה ו**מחכה שם** עד שמשהו מגיע (או עד שנמאס לך), ואז עולה וחוזר מיד לחכות.
- **Server-Sent Events (SSE)** – נרשמת לשירות הודעות: **השליח מתקשר אליך** בכל פעם שיש משהו. אתה רק מקשיב.
- **WebSocket** – **שיחת טלפון פתוחה** כל הזמן: שני הצדדים יכולים לדבר מתי שהם רוצים.

## ארבע הדרכים – צעד אחר צעד

### 1. Polling

ה-Client שולח `GET /api/alerts` כל X שניות. **פשוט**, עובד בכל מקום, אבל: רוב הבקשות מחזירות "אין חדש" (בזבוז), והעיכוב הוא עד X שניות.

### 2. Long Polling

ה-Client שולח בקשה, והשרת **לא עונה מיד** – הוא מחזיק אותה פתוחה עד שיש חדש (או עד Timeout של ~30 שניות). ברגע שהתשובה מגיעה, ה-Client שולח בקשה חדשה. עיכוב נמוך, אבל מסובך לניהול בשרת ועדיין "בקשה לכל הודעה".

### 3. Server-Sent Events (SSE)

בקשת HTTP אחת שנשארת פתוחה, והשרת **כותב אליה אירועים** בפורמט טקסט פשוט (`data: ...`). כיוון **אחד בלבד** – שרת ← לקוח. לדפדפן יש `EventSource` מובנה שאפילו **מתחבר מחדש לבד** ושולח `Last-Event-ID`.

### 4. WebSocket

חיבור **דו-כיווני** וקבוע. אחרי שנפתח, כל צד שולח **Frames** (הודעות) מתי שהוא רוצה, עם תקורה זעירה.

### טבלת השוואה

| | Polling | Long Polling | SSE | WebSocket |
|---|---|---|---|---|
| כיוון | לקוח שואל | לקוח שואל | שרת ← לקוח | דו-כיווני |
| עיכוב (Latency) | עד מרווח הבדיקה | נמוך | נמוך מאוד | נמוך מאוד |
| עומס על השרת | בקשות רבות ריקות | חיבור לכל לקוח + בקשות חוזרות | חיבור פתוח לכל לקוח | חיבור פתוח לכל לקוח |
| מורכבות | הכי פשוט | בינונית | פשוט | הכי מורכב |
| התחברות מחדש | לא רלוונטי | ידני | **מובנה** בדפדפן | ידני (נלמד בשיעור הבא) |
| מתאים ל | נתונים שמשתנים לאט | מערכות ישנות | פידים, התראות, **Streaming של LLM** | צ׳אט, משחקים, שיתוף פעולה |

> [!tip] כלל אצבע: אם השרת רק **מדבר** והלקוח רק **מקשיב** – **SSE**. זה בדיוק המקרה של Streaming טוקנים ממודל שפה (נלמד במודול 9): הלקוח שולח שאלה ב-POST רגיל, והתשובה זורמת חזרה. אם שני הצדדים מדברים הרבה – **WebSocket**.

### איך WebSocket נפתח? – HTTP Upgrade

WebSocket מתחיל כבקשת HTTP רגילה עם "בקשה מיוחדת":

```text Handshake
GET /ws HTTP/1.1
Host: app.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
```

קוד `101 Switching Protocols` אומר: "מעכשיו אנחנו לא מדברים HTTP, אלא WebSocket – על אותו חיבור TCP". הכתובת מתחילה ב-`ws://`, או `wss://` כשמוצפן (כמו https – תמיד בפרודקשן).

### Message Envelope – מעטפה עם type

ב-WebSocket אין "נתיבים" כמו ב-REST. כל ההודעות עוברות באותו צינור, אז צריך להסכים על **מבנה**:

```json מעטפת הודעה
{ "type": "chat.message", "id": "m_812", "payload": { "roomId": "r1", "text": "שלום" } }
```

- **`type`** – מה זה (כמו Method + Path ב-HTTP). ה-Client וה-Server עושים `switch` עליו.
- **`id`** – מזהה ייחודי, כדי לזהות כפילויות ולקשר תשובות.
- **`payload`** – התוכן.

ב-TypeScript מגדירים את זה כ-**Discriminated Union** – והקומפיילר יודע בדיוק אילו שדות יש לכל `type`.

### Auth ל-WebSocket – בלי Token ב-URL

הדפדפן **לא מאפשר** להוסיף Header כמו `Authorization` לחיבור WebSocket. הפיתוי: `wss://app/ws?token=eyJ...`.

> [!danger] **אל תשים Token ארוך-טווח ב-URL.** כתובות נשמרות ב-Logs של שרתים, Proxies ו-Load Balancers, ובהיסטוריה. מי שקורא את ה-Logs – מתחזה למשתמש.

הדרך המקובלת – **Ticket קצר-מועד**:
1. ה-Client שולח `POST /api/ws-ticket` רגיל (מאומת עם Cookie או Token בכותרת).
2. השרת מחזיר Ticket אקראי, **חד-פעמי**, שתקף ל-30 שניות.
3. ה-Client מתחבר עם `wss://app/ws?ticket=...`.
4. השרת בודק את ה-Ticket ב-Upgrade, **מוחק אותו**, ומשייך את החיבור למשתמש.

גם אם ה-Ticket דלף ל-Log – הוא כבר שומש ופג. חלופות: Cookie (אם אותו דומיין, עם הגנה על Origin), או הודעת `auth` ראשונה אחרי החיבור.

> [!warn] בדוק תמיד את כותרת **Origin** ב-Upgrade. אחרת אתר זדוני יכול לפתוח WebSocket לשרת שלך בשם המשתמש (עם ה-Cookies שלו) – מתקפה שנקראת **Cross-Site WebSocket Hijacking**.

> [!tip] מה Senior יודע: הבחירה בין Polling, SSE ו-WebSocket היא **Trade-off**, לא עניין של "מה מגניב". Polling כל 30 שניות לדשבורד של מנהלים זה לגיטימי לגמרי. Senior גם יודע שחיבור קבוע הוא **משאב** – כל אחד תופס זיכרון ו-File Descriptor בשרת – ולכן שואל מראש: כמה חיבורים בו-זמנית? כמה הודעות לשנייה? מה קורה כשהחיבור נופל?

export type ClientMsg =
  | { type: 'chat.send'; id: string; payload: { roomId: string; text: string } }
  | { type: 'ping'; id: string };

export type ServerMsg =
  | { type: 'chat.message'; id: string; payload: { roomId: string; from: string; text: string } }
  | { type: 'error'; id: string; payload: { reason: string } };

// ===== server.ts (Node.js, npm i ws) =====
import { WebSocketServer, WebSocket } from 'ws';

const wss = new WebSocketServer({ port: 8080 });

wss.on('connection', (socket, req) => {
  console.log('חיבור חדש מ-', req.socket.remoteAddress);

  socket.on('message', (raw) => {
    let msg: ClientMsg;
    try {
      msg = JSON.parse(raw.toString()); // אף פעם לא לסמוך על קלט – לעטוף ב-try
    } catch {
      return socket.send(JSON.stringify({ type: 'error', id: 'n/a', payload: { reason: 'bad json' } }));
    }

    switch (msg.type) {
      case 'chat.send': {
        const out: ServerMsg = {
          type: 'chat.message',
          id: crypto.randomUUID(),
          payload: { roomId: msg.payload.roomId, from: 'user', text: msg.payload.text },
        };
        // שידור לכל המחוברים (Broadcast)
        for (const client of wss.clients) {
          if (client.readyState === WebSocket.OPEN) client.send(JSON.stringify(out));
        }
        break;
      }
      case 'ping':
        break; // נטפל ב-Heartbeat בשיעור הבא
    }
  });

  socket.on('close', () => console.log('החיבור נסגר'));
});

const ws = new WebSocket('wss://app.example.com/ws?ticket=abc123');

ws.addEventListener('open', () => {

  ws.send(JSON.stringify(msg));
});

ws.addEventListener('message', (event) => {
  const msg = JSON.parse(event.data) as ServerMsg;
  if (msg.type === 'chat.message') console.log(`${msg.payload.from}: ${msg.payload.text}`);

## מה קורה בקוד?

- **`ClientMsg` / `ServerMsg`** – **Discriminated Unions**: כל הודעה מזוהה לפי `type`. בתוך `case 'chat.send'`, TypeScript **יודע** שיש `msg.payload.roomId`. את הקובץ הזה משתפים בין השרת ללקוח, כך ששניהם מדברים באותה שפה.
- **`new WebSocketServer({ port: 8080 })`** – ספריית `ws` היא הסטנדרט ב-Node.js. היא מטפלת ב-Handshake וב-`101 Switching Protocols` בשבילנו. (בפרודקשן מחברים אותה לשרת HTTP קיים ובודקים Ticket ו-Origin באירוע ה-Upgrade.)
- **`connection`** – רץ פעם אחת לכל לקוח שמתחבר. `socket` הוא הצינור לאותו לקוח ספציפי.
- **`JSON.parse` בתוך `try`** – ההודעה מגיעה כ-Buffer מהרשת. לקוח (או תוקף) יכול לשלוח זבל – אסור שזה יפיל את השרת. בפרודקשן גם מאמתים את המבנה עם **Zod**.
- **`switch (msg.type)`** – ה"Router" של WebSocket: במקום נתיבים, `type`.
- **`wss.clients` + `readyState === OPEN`** – שידור לכולם. בודקים שהחיבור פתוח, כי שליחה לחיבור שנסגר זורקת שגיאה.
- **`new WebSocket('wss://...')`** – ה-API המובנה בדפדפן. `wss` = מוצפן. ה-`ticket` הוא חד-פעמי וקצר-מועד, לא ה-Token האמיתי.
- **`open` / `message`** – אסור לשלוח לפני `open`! לכן השליחה הראשונה נמצאת בתוך המאזין.

> [!note] הקוד הזה עדיין "תמים": אין בו זיהוי חיבורים מתים, אין התחברות מחדש, ואין טיפול בלקוח איטי. את כל זה נוסיף בשיעור הבא – ושם נמצא רוב העבודה האמיתית.

## 1. Half-Open Connections – חיבורים "זומבים"

כשחיבור נסגר **בצורה מסודרת**, שני הצדדים מקבלים אירוע `close`. אבל כשהרשת פשוט **נעלמת** (כבל נשלף, טלפון במעלית), אף אחד לא שולח "להתראות". התוצאה: **Half-Open Connection** – השרת חושב שהלקוח מחובר ושולח לו הודעות לחלל, והלקוח חושב שהוא מחובר ולא מבין למה אין הודעות חדשות.

TCP לבדו יכול לגלות את זה רק אחרי **דקות ארוכות**. לכן צריך מנגנון משלנו.

## 2. Heartbeat – Ping/Pong

- **בצד השרת:** כל 30 שניות שולחים `ping` לכל חיבור. מי שלא ענה `pong` עד הסבב הבא – מת. סוגרים אותו עם `terminate()` ומשחררים משאבים.
- **בצד הלקוח:** אם לא הגיעה **שום** הודעה (כולל Heartbeat) במשך 45 שניות – מניחים שהחיבור מת, סוגרים ומתחברים מחדש.

> [!note] פרוטוקול WebSocket כולל Frames מובנים של Ping/Pong, והדפדפן עונה עליהם אוטומטית – אבל JavaScript בדפדפן **לא רואה** אותם. לכן הרבה מערכות שולחות גם Heartbeat ברמת האפליקציה (`{ "type": "ping" }`) כדי שגם הלקוח יוכל למדוד.

Heartbeat גם שומר על החיבור "חי" מול Load Balancers ו-Proxies שסוגרים חיבורים שקטים (לרוב אחרי 60 שניות).

## 3. Reconnect עם Exponential Backoff + Jitter

הלקוח צריך להתחבר מחדש לבד. הטעות הנאיבית: "ניסיון כל שנייה".

**הבעיה – Thundering Herd (עדר דוהר):** השרת נפל ל-10 שניות. 50,000 לקוחות מנסים להתחבר **באותה שנייה בדיוק**, שוב ושוב. השרת עולה – ומיד קורס שוב מהעומס.

**הפתרון:**
- **Exponential Backoff** – כל ניסיון כושל מכפיל את ההמתנה: 0.5s ← 1s ← 2s ← 4s ← ... עד תקרה (למשל 30s).
- **Jitter** – מוסיפים **אקראיות**: במקום בדיוק 4 שניות, מספר אקראי בין 0 ל-4. כך הלקוחות "מתפזרים" על פני הזמן במקום להגיע כגל אחד.
- **איפוס** – אחרי חיבור מוצלח, מאפסים את המונה.

| ניסיון | Backoff בלי Jitter | עם Full Jitter |
|---|---|---|
| 1 | 0.5s | 0–0.5s |
| 2 | 1s | 0–1s |
| 3 | 2s | 0–2s |
| 4 | 4s | 0–4s |
| 10 | 30s (תקרה) | 0–30s |

## 4. Resume – "איפה עצרנו?"

התחברנו מחדש – אבל מה עם ההודעות שנשלחו בזמן שהיינו מנותקים?

- לכל אירוע השרת נותן **מזהה עולה** (`eventId` או Sequence Number).
- הלקוח זוכר את **`lastEventId`** – המזהה האחרון שקיבל.
- בהתחברות מחדש הוא שולח: `{ "type": "resume", "lastEventId": 1042 }`.
- השרת שולח את כל מה שאחרי 1042 (**Tail**), ואז ממשיך בשידור חי.

ואם הפער גדול מדי (הלקוח היה מנותק שעה והשרת לא שומר כל כך הרבה)? **Snapshot + Tail**: השרת שולח **מצב מלא עדכני** (Snapshot) ואז את האירועים מאותה נקודה. זו גם הדרך הנכונה לטעינה ראשונה: קודם `GET` של המצב המלא, ואז Stream של שינויים.

> [!warn] אחרי Resume ייתכנו **כפילויות** (הודעה שהגיעה רגע לפני הניתוק נשלחת שוב). הלקוח חייב להיות **Idempotent** – לזהות `id` שכבר ראה ולהתעלם.

## 5. Backpressure – כשהלקוח איטי

השרת שולח 200 עדכוני מחירים לשנייה. לקוח אחד על 3G בקושי מעבד 20. מה קורה? ההודעות **נצברות בזיכרון של השרת** בתור השליחה של אותו חיבור. אחרי כמה דקות – השרת נגמר לו הזיכרון וקורס, **לכל הלקוחות**.

**איך מזהים?** בספריית `ws` (וגם בדפדפן) יש **`bufferedAmount`** – כמה בתים ממתינים לשליחה בחיבור הזה. אם הוא עולה ולא יורד – הלקוח לא עומד בקצב.

**אסטרטגיות:**

| אסטרטגיה | מה עושים | מתאים ל |
|---|---|---|
| **Drop** | מדלגים על הודעות לא חשובות | אינדיקציית "מקליד...", מיקום סמן |
| **Coalesce** (איחוד) | שומרים רק את **הערך האחרון** לכל מפתח ושולחים כל 100ms | מחירים, מונים, דשבורדים |
| **Disconnect** | סוגרים את החיבור; הלקוח יתחבר מחדש ויעשה Snapshot | לקוח שחרג מהגבול הקשיח |

> [!danger] אסור לעשות Drop להודעות קריטיות (התראת סיכון, הודעת צ׳אט). עבורן משתמשים ב-Disconnect + Resume, כך שהלקוח יקבל הכל כשיחזור לקצב.

## 6. Application-Level Acks

`socket.send()` הצליח? זה רק אומר שהנתונים **נכנסו ל-Buffer** של מערכת ההפעלה. לא שהלקוח קיבל, ובטח לא שהוא עיבד.

להודעות חשובות מוסיפים **Ack** ברמת האפליקציה:
1. הלקוח שולח `{ "type": "chat.send", "id": "c_77", ... }` ומציג "⏳ שולח".
2. השרת שומר ב-Database ומחזיר `{ "type": "ack", "id": "c_77" }`.
3. הלקוח מסמן "✓ נשלח". אם אין Ack תוך 5 שניות – שולח שוב **עם אותו `id`**, והשרת מזהה כפילות ולא שומר פעמיים (**Idempotency**, כמו שלמדנו במודול 4).

> [!tip] מה Senior יודע: **WebSocket הוא לא מקור אמת – ה-Database הוא.** החיבור הוא רק "צינור מהיר" שיכול להיקטע בכל רגע. לכן Senior מתכנן מראש: כל אירוע עם מזהה, לקוח שיודע לעשות Resume, שרת שיודע לשלוח Snapshot, Heartbeat בשני הצדדים, תקרת Backpressure לכל חיבור, ו-Backoff עם Jitter. והוא **בודק** את זה: מנתק רשת ב-DevTools (Offline), מאט ל-Slow 3G, ועושה Restart לשרת באמצע שיחה.

// ===== server.ts – Heartbeat ו-Backpressure =====
import { WebSocketServer, WebSocket } from 'ws';

const wss = new WebSocketServer({ port: 8080 });
const alive = new WeakMap<WebSocket, boolean>();
const MAX_BUFFER = 1_000_000; // 1MB – מעל זה הלקוח לא עומד בקצב

wss.on('connection', (socket) => {
  alive.set(socket, true);
  socket.on('pong', () => alive.set(socket, true)); // "אני כאן!"
});

setInterval(() => {
  for (const socket of wss.clients) {
    if (!alive.get(socket)) { socket.terminate(); continue; } // לא ענה – חיבור מת
    alive.set(socket, false);
    socket.ping();
  }
}, 30_000);

export function safeSend(socket: WebSocket, data: string) {
  if (socket.bufferedAmount > MAX_BUFFER) {
    socket.close(4008, 'too slow'); // Disconnect – הלקוח יחזור עם Resume
    return;
  }
  socket.send(data);
}

// ===== client.ts – Reconnect עם Exponential Backoff + Jitter =====
let attempt = 0;
let lastEventId = Number(localStorage.getItem('lastEventId') ?? 0);
const seen = new Set<string>();

function connect() {
  const ws = new WebSocket('wss://app.example.com/ws');

  ws.onopen = () => {
    attempt = 0; // הצלחנו – מאפסים
    ws.send(JSON.stringify({ type: 'resume', lastEventId })); // "איפה עצרנו?"
  };

  ws.onmessage = (e) => {
    const msg = JSON.parse(e.data) as { id: string; seq: number; type: string };
    if (seen.has(msg.id)) return; // כפילות אחרי Resume – מתעלמים
    seen.add(msg.id);
    lastEventId = msg.seq;
    localStorage.setItem('lastEventId', String(lastEventId));
    // ... לעדכן את המסך
  };

  ws.onclose = () => {
    const base = Math.min(30_000, 500 * 2 ** attempt); // 0.5s, 1s, 2s ... עד 30s
    const delay = Math.random() * base; // Full Jitter
    attempt++;
    setTimeout(connect, delay);
  };
}

connect();

## הסבר שורה אחרי שורה

**בשרת:**
- **`alive` (WeakMap)** – לכל חיבור דגל "האם ענה מאז ה-Ping האחרון". `WeakMap` לא מונע מה-Garbage Collector לנקות חיבורים שנסגרו.
- **`socket.on('pong', ...)`** – הדפדפן עונה אוטומטית ל-Ping ברמת הפרוטוקול. כשמגיע Pong – מסמנים "חי".
- **ה-`setInterval`** – כל 30 שניות: מי שעדיין `false` (לא ענה לסבב הקודם) – `terminate()` (סגירה מיידית, בלי לחכות ל-Handshake של סגירה). השאר מקבלים `false` ו-Ping חדש.
- **`safeSend`** – לפני כל שליחה בודקים `bufferedAmount`. אם הלקוח צבר יותר ממגה של הודעות שלא נשלחו – סוגרים עם קוד מותאם `4008` (קודים 4000–4999 שמורים לאפליקציה). זו אסטרטגיית **Disconnect**: עדיף לנתק לקוח אחד מאשר להפיל שרת שלם.

**בלקוח:**
- **`attempt`** – מונה ניסיונות כושלים, מתאפס ב-`onopen`.
- **`lastEventId` ב-localStorage** – שורד גם רענון דף, לא רק ניתוק.
- **`resume`** – ההודעה הראשונה אחרי כל התחברות. השרת יחזיר את מה שפספסנו (או Snapshot אם הפער גדול).
- **`seen`** – סט של מזהים שכבר טיפלנו בהם. אחרי Resume ייתכנו כפילויות, ואנחנו מתעלמים מהן (בפרודקשן מגבילים את הגודל שלו).
- **`500 * 2 ** attempt`** – Exponential Backoff, עם `Math.min` כתקרה של 30 שניות.
- **`Math.random() * base`** – **Full Jitter**: מפזר את הלקוחות על פני כל הטווח, כדי שלא יחזרו כולם יחד.

> [!tip] נסה: הרץ את השרת, פתח את הלקוח, ובלשונית Network ב-DevTools בחר **Offline** לכמה שניות. תראה את ה-`onclose`, את הניסיונות המתרחקים, ואת ה-`resume` כשהרשת חוזרת.

```typescript LiveAlertsClient.ts
type Alert = { id: string; seq: number; severity: 'low' | 'high'; text: string };
type Status = 'connecting' | 'live' | 'reconnecting';

export class LiveAlertsClient {
  private ws?: WebSocket;
  private attempt = 0;
  private lastSeq = 0;
  private seen = new Set<string>();
  private watchdog?: ReturnType<typeof setTimeout>;

  constructor(
    private url: string,
    private onAlert: (a: Alert) => void,
    private onStatus: (s: Status) => void,
  ) {}

  start() {
    this.onStatus(this.attempt === 0 ? 'connecting' : 'reconnecting');
    this.ws = new WebSocket(this.url);

    this.ws.onopen = () => {
      this.attempt = 0;
      this.onStatus('live');
      this.ws!.send(JSON.stringify({ type: 'resume', lastEventId: this.lastSeq }));
      this.resetWatchdog();
    };

    this.ws.onmessage = (e) => {
      this.resetWatchdog(); // כל הודעה (כולל heartbeat) = החיבור חי
      const msg = JSON.parse(e.data);
      if (msg.type === 'heartbeat') return;
      if (msg.type === 'alert') {
        const alert = msg.payload as Alert;
        if (this.seen.has(alert.id)) return; // Idempotent
        this.seen.add(alert.id);
        this.lastSeq = Math.max(this.lastSeq, alert.seq);
        this.onAlert(alert);
        this.ws!.send(JSON.stringify({ type: 'ack', id: alert.id })); // Ack ברמת האפליקציה
      }
    };

    this.ws.onclose = () => {
      clearTimeout(this.watchdog);
      const base = Math.min(30_000, 500 * 2 ** this.attempt++);
      setTimeout(() => this.start(), Math.random() * base); // Backoff + Jitter
    };
  }

  // אם 45 שניות אין כלום – החיבור כנראה Half-Open
  private resetWatchdog() {
    clearTimeout(this.watchdog);
    this.watchdog = setTimeout(() => this.ws?.close(), 45_000);
  }
}
```

**מה חשוב כאן:**
- **Watchdog** בצד הלקוח מגלה Half-Open: השרת שולח `heartbeat` כל 20 שניות; 45 שניות של שקט = סוגרים ומתחברים מחדש.
- **Backoff + Jitter** עם תקרה ואיפוס בהצלחה.
- **Resume** לפי `lastSeq`, ו-**Idempotency** עם `seen`.
- **Ack** לכל התראה – השרת יודע מה הנציג באמת קיבל, ויכול לשלוח שוב או להסלים אם אין Ack.
- **סטטוס** (`live`/`reconnecting`) מוצג למשתמש – נציג חייב לדעת אם הוא רואה התראות חיות או שהוא "עיוור" כרגע.

## שרת אחד לא מספיק

עד עכשיו היה לנו **שרת אחד** שמחזיק את כל החיבורים. כשמשתמש שולח הודעה, השרת עובר על `wss.clients` ושולח לכולם. פשוט.

אבל שרת אחד יכול להחזיק אולי עשרות אלפי חיבורים, והוא גם **נקודת כשל יחידה**. אז מוסיפים עוד שרתים מאחורי **Load Balancer**. ופתאום: אורי מחובר לשרת A, דנה מחוברת לשרת B. אורי שולח הודעה ← שרת A שולח לכל **הלקוחות שלו** ← **דנה לא מקבלת כלום**, כי היא בכלל לא אצלו.

### אנלוגיה: רשת סניפים של בית קפה

כל **שרת** הוא **סניף**, וכל לקוח יושב בסניף אחד. כשההנהלה רוצה להודיע "מבצע 1+1!", היא לא יכולה לצעוק בסניף אחד – היא שולחת הודעה ב**קבוצת וואטסאפ של מנהלי הסניפים**, וכל מנהל מכריז בסניף שלו. קבוצת הוואטסאפ הזו היא **Redis Pub/Sub**.

ואם מנהל סניף היה בהפסקה כשההודעה נשלחה? הוא פספס. בשביל זה יש **לוח מודעות** שאפשר לגלול אחורה – זה **Redis Streams**.

> [!tip] כאן Real-Time פוגש ארכיטקטורה מבוזרת. השאלה "איך תגרום לצ׳אט לעבוד על 10 שרתים?" היא שאלת System Design קלאסית בראיונות Senior – ובסוף השיעור תדע לענות עליה, כולל תקציב Latency לכל שלב.

## 1. Fan-out עם Redis Pub/Sub

**Redis** הוא שרת נתונים בזיכרון, מהיר מאוד. יש לו מנגנון **Pub/Sub** (Publish/Subscribe):
- כל שרת WebSocket עושה `SUBSCRIBE` לערוצים (למשל `room:r1`).
- כשהודעה מגיעה לשרת A, הוא **לא** שולח ישירות ללקוחות – הוא עושה `PUBLISH room:r1 <הודעה>`.
- Redis מעביר אותה **לכל השרתים** שרשומים לערוץ (כולל A עצמו).
- כל שרת שולח ללקוחות **המקומיים שלו** שנמצאים בחדר.

זה נקרא **Fan-out** – הודעה אחת "מתפצלת" לכל מי שצריך אותה.

> [!warn] **Pub/Sub הוא Fire-and-Forget.** Redis לא שומר את ההודעה. אם שרת B היה באמצע Restart באותה מילישנייה – ההודעה **אבדה** עבורו ועבור כל הלקוחות שלו. אין היסטוריה, אין אישור קבלה, אין "שלח שוב".

## 2. Redis Streams – כשצריך Replay

**Redis Streams** הוא **Log** – רשימה שמוסיפים לסופה (`XADD`) ושכל רשומה בה מקבלת **ID עולה**. בניגוד ל-Pub/Sub:
- הרשומות **נשמרות** (עם גבול, למשל 10,000 האחרונות בכל חדר: `MAXLEN ~ 10000`).
- אפשר לקרוא **מנקודה מסוימת** (`XREAD ... <lastId>`) – בדיוק מה שצריך ל-**Resume** מהשיעור הקודם!
- ה-ID של Redis הוא ה-`lastEventId` הטבעי שנותנים ללקוח.

| | Pub/Sub | Streams |
|---|---|---|
| שומר הודעות? | לא | כן (עד גבול) |
| Replay מנקודה | לא | כן |
| מהירות | מהיר מאוד | מהיר מאוד |
| מתאים ל | "מקליד...", נוכחות, אירועים שמותר לאבד | הודעות צ׳אט, התראות, כל מה שצריך Resume |

> [!note] Redis Streams הוא לא תחליף ל-Database. ההודעה נשמרת **קודם** ב-PostgreSQL (מקור האמת), ו-Streams משמש כ"חלון זמן" מהיר ל-Replay. ל-Pipelines גדולים עם שמירה ארוכה משתמשים ב-Kafka – נלמד במודול 8.

## 3. Sticky Sessions – Trade-off

**Sticky Session** אומר שה-Load Balancer שולח את אותו לקוח **תמיד לאותו שרת**.
- **למה צריך:** ב-Long Polling או בספריות כמו Socket.IO (שמתחילות ב-Polling ועוברות ל-WebSocket), כמה בקשות HTTP של אותו "חיבור" חייבות להגיע לאותו שרת.
- **המחיר:** חלוקת עומס לא שווה (שרת אחד "נתקע" עם הרבה לקוחות כבדים), ומה קורה כשהשרת הזה נופל? כל הלקוחות שלו מתנתקים יחד.
- **WebSocket טהור** לא צריך Sticky – החיבור עצמו כבר "דבוק" לשרת אחד כל עוד הוא חי. לכן Senior מתכנן כך שכל שרת יוכל לשרת כל לקוח, וה-State המשותף נמצא ב-Redis ו-Database – לא בזיכרון של שרת אחד.

## 4. Graceful Drain ב-Deploy

Deploy = מחליפים שרתים ישנים בחדשים. אם פשוט "הורגים" שרת עם 20,000 חיבורים – 20,000 לקוחות מתחברים מחדש באותה שנייה (**Thundering Herd** שוב!).

**Graceful Drain:**
1. השרת מקבל `SIGTERM` (ב-Kubernetes – נלמד במודול 10).
2. מפסיק לקבל חיבורים חדשים (ה-Readiness Probe נכשל ← ה-Load Balancer מפסיק לשלוח אליו).
3. שולח ללקוחות הודעה `{ "type": "reconnect" }` **בהדרגה** – למשל 1,000 לשנייה, לא כולם יחד.
4. הלקוחות מתחברים מחדש (עם Jitter!) לשרתים אחרים ועושים Resume.
5. אחרי פרק זמן (או כשנשארו 0 חיבורים) – השרת נסגר.

## 5. Live Pipeline ו-Latency Budget

דוגמה: מערכת שמנתחת **שיחת צ׳אט חיה** בין נציג ללקוח, ומתריעה לנציג אם הלקוח מבקש משהו מחשיד (למשל "תעביר את הכסף לחשבון אחר דחוף").

הדרישה: **התראה בסיסית תוך פחות מ-200ms** מרגע שההודעה נשלחה. איך מתכננים? מחלקים את הזמן ל-**Latency Budget** לכל "קפיצה" (Hop):

| Hop | מה קורה | תקציב |
|---|---|---|
| Client ← Server A | הודעה ב-WebSocket | 30ms |
| Server A ← Redis Stream | `XADD` | 5ms |
| Rules Engine | בדיקת כללים מהירה (מילות מפתח, סכומים, רשימות שחורות) | 20ms |
| Redis Pub/Sub ← Server B | Fan-out לשרת של הנציג | 5ms |
| Server B ← הנציג | WebSocket | 30ms |
| **מרווח ביטחון** | עומסים, GC, רשת | ~110ms |
| **סה״כ** | | **< 200ms** |

ומה עם **ניתוח AI** (מודל שפה שמבין הקשר)? הוא לוקח 1–3 **שניות**. אם נשים אותו בנתיב המהיר – שברנו את התקציב. לכן הוא רץ **אסינכרונית**: Consumer נפרד קורא מאותו Stream, שולח למודל, וכשהתשובה מגיעה – מוסיף התראה "מעמיקה" שנייה. הנציג מקבל **מיד** התראה בסיסית, ואחרי שתי שניות – ניתוח מלא.

> [!tip] העיקרון: **הנתיב המהיר (Hot Path) קצר, פשוט ודטרמיניסטי. כל מה שאיטי – בצד, אסינכרוני.** זה בדיוק הרעיון של Event-Driven Architecture שנלמד במודול 8.

### איך מודדים Latency?

- **Timestamps לאורך הדרך** – כל Hop מוסיף לאירוע שדה זמן (`receivedAt`, `rulesDoneAt`, `sentAt`). ההפרש = הזמן שלקח כל שלב.
- **Percentiles, לא ממוצע** – ממוצע של 80ms יכול להסתיר ש-1% מההודעות לוקחות 2 שניות. מודדים **p50, p95, p99**. היעד "<200ms" מוגדר ב-**p99**.
- **Histograms ו-Tracing** – כלים כמו Prometheus ו-OpenTelemetry (מודול 10) מציגים את ההתפלגות ואת "המסלול" של כל אירוע.
- **שעונים לא מסונכרנים** – בין מחשבים שונים השעון יכול לסטות. מודדים הפרשים **בתוך אותו שרת** כשאפשר, או משתמשים ב-Tracing שמטפל בזה.

> [!tip] מה Senior יודע: הוא מתחיל משאלות – כמה חיבורים בו-זמנית? כמה הודעות לשנייה? מה מותר לאבד ומה לא? – ורק אז בוחר Pub/Sub או Streams. הוא מגדיר **Latency Budget** לכל Hop ומודד ב-p99, מוציא כל דבר איטי מה-Hot Path, מתכנן Deploy בלי Thundering Herd, ושומר את מקור האמת ב-Database – כך שכל שרת WebSocket הוא "נטול זיכרון" וניתן להחלפה.

// npm i ioredis ws
import Redis from 'ioredis';
import { WebSocket } from 'ws';

const redis = new Redis(process.env.REDIS_URL!);      // לפקודות רגילות
const sub = new Redis(process.env.REDIS_URL!);        // חיבור נפרד – במצב Subscribe אי אפשר לשלוח פקודות אחרות

// חדרים → הסוקטים המקומיים בשרת הזה בלבד
const localRooms = new Map<string, Set<WebSocket>>();

// 1) כל שרת נרשם לערוץ השידור
await sub.psubscribe('room:*');
sub.on('pmessage', (_pattern, channel, raw) => {
  const roomId = channel.slice('room:'.length);
  for (const socket of localRooms.get(roomId) ?? []) {
    if (socket.readyState === WebSocket.OPEN) socket.send(raw); // רק ללקוחות המקומיים
  }
});

// 2) הודעה חדשה מלקוח: שמירה ב-Stream (לReplay) + Publish (לשידור חי)
export async function publishMessage(roomId: string, from: string, text: string) {
  const sentAt = Date.now();
  const streamId = await redis.xadd(
    `stream:room:${roomId}`, 'MAXLEN', '~', '10000', '*', // שומרים ~10K אחרונות
    'from', from, 'text', text, 'sentAt', String(sentAt),
  );
  const event = { type: 'chat.message', id: streamId, payload: { roomId, from, text, sentAt } };
  await redis.publish(`room:${roomId}`, JSON.stringify(event)); // Fire-and-forget
}

// 3) Resume: לקוח חוזר עם lastEventId – שולחים את מה שפספס מה-Stream
export async function replay(socket: WebSocket, roomId: string, lastEventId: string) {
  const entries = await redis.xrange(`stream:room:${roomId}`, `(${lastEventId}`, '+', 'COUNT', 500);
  for (const [id, fields] of entries) {
    const f = Object.fromEntries(chunk(fields)); // ['from','dana','text','hi'] → {from, text}
    socket.send(JSON.stringify({ type: 'chat.message', id, payload: { roomId, ...f } }));
  }
  if (entries.length === 500) socket.send(JSON.stringify({ type: 'resync' })); // פער גדול → Snapshot
}

function chunk(arr: string[]): [string, string][] {
  const out: [string, string][] = [];
  for (let i = 0; i < arr.length; i += 2) out.push([arr[i], arr[i + 1]]);
  return out;
}

## הסבר שורה אחרי שורה

- **שני חיבורי Redis** – חיבור שנמצא במצב Subscribe "שמור" רק לקבלת הודעות. לכן `sub` מאזין ו-`redis` מבצע את כל השאר.
- **`localRooms`** – כל שרת יודע רק על **הסוקטים שלו**. זה ה-State המקומי היחיד, והוא נבנה מחדש מעצמו כשלקוחות מתחברים.
- **`psubscribe('room:*')`** – הרשמה לפי תבנית: כל הערוצים שמתחילים ב-`room:`. (במערכת גדולה נרשמים רק לחדרים שיש בהם לקוחות מקומיים, כדי לא לקבל תעבורה מיותרת.)
- **`pmessage`** – הודעה הגיעה מ-Redis. השרת שולח אותה **רק** ללקוחות המקומיים בחדר. כך כל שרת עושה חלק קטן מה-Fan-out.
- **`xadd ... MAXLEN ~ 10000 *`** – מוסיף רשומה ל-Stream של החדר. `*` = Redis מייצר ID עולה (כמו `1731764400000-0`). `~` אומר "בערך" – Redis חותך ביעילות. ה-ID הזה הופך ל-`id` של האירוע, וזה ה-`lastEventId` שהלקוח ישמור.
- **`sentAt`** – Timestamp לאורך הדרך, כדי למדוד Latency מקצה לקצה.
- **`publish`** – שידור לכל השרתים. Fire-and-forget: אם שרת לא היה מחובר ברגע הזה – הוא פספס, אבל ההודעה עדיין ב-Stream.
- **`xrange ... (${lastEventId} + COUNT 500`** – כל מה ש**אחרי** ה-ID האחרון שהלקוח ראה (הסוגר `(` אומר "לא כולל"). עד 500 הודעות.
- **`resync`** – אם הגענו ל-500, כנראה הפער גדול מדי: אומרים ללקוח לטעון **Snapshot** מלא מה-API ואז להמשיך מהסוף.

> [!note] שים לב לסדר: קודם `XADD` ורק אז `PUBLISH`. כך כל הודעה שמישהו ראה בשידור החי קיימת גם ב-Stream, ו-Resume תמיד ימצא אותה. ובמערכת אמיתית – לפני שניהם – שמירה ב-PostgreSQL.

## פתרון לדוגמה

**1. הארכיטקטורה:**

1. **WebSocket Gateway** (כמה שרתים, בלי Sticky) – מחזיקים חיבורים של לקוחות ונציגים, מאמתים עם Ticket.
2. הודעת לקוח ← Gateway ← **PostgreSQL** (מקור אמת) ← **`XADD stream:chat:<id>`**.
3. **Rules Consumer** (מהיר) – קורא מה-Stream עם Consumer Group, מריץ כללים (מילות מפתח כמו "העברה דחופה", סכומים חריגים, חשבון יעד חדש). אם יש התאמה ← `PUBLISH agent:<agentId>` עם התראה בסיסית.
4. **AI Consumer** (איטי, אסינכרוני) – Consumer Group **נפרד** על אותו Stream. שולח את ההקשר למודל שפה, ובתשובה ← `PUBLISH agent:<agentId>` עם ניתוח מעמיק.
5. ה-Gateway שבו הנציג מחובר מקבל את ה-Publish ושולח לו ב-WebSocket.

**2. Latency Budget (יעד p99 < 200ms להתראה הבסיסית):**

| Hop | תקציב |
|---|---|
| לקוח ← Gateway | 30ms |
| שמירה ב-PostgreSQL + XADD | 25ms |
| Rules Consumer קורא ומעבד | 30ms |
| PUBLISH ← Gateway של הנציג | 10ms |
| Gateway ← נציג | 30ms |
| מרווח | 75ms |
| **סה״כ** | **200ms** |

ניתוח ה-AI (1–3 שניות) **לא** בתקציב – הוא מגיע כהתראה שנייה.

**3. מה קורה כש...**
- **Gateway נופל:** הלקוחות שלו מתנתקים, מתחברים מחדש (Backoff + Jitter) ל-Gateway אחר, ושולחים `lastEventId` ← Replay מה-Stream.
- **Deploy:** Graceful Drain – הפסקת קבלת חיבורים, הודעת `reconnect` בקצב מבוקר, סגירה כשמתרוקן.
- **שירות ה-AI איטי או נופל:** ההתראות הבסיסיות ממשיכות לעבוד; ה-Consumer של ה-AI מדביק את הפער כשהוא חוזר, כי ה-Stream שומר את ההודעות.

**4. מדידה:** כל שלב מוסיף Timestamp (`receivedAt`, `rulesDoneAt`, `deliveredAt`). מודדים Histogram של `deliveredAt - receivedAt` ב-p50/p95/p99, ומתריעים אם p99 עובר 200ms.
